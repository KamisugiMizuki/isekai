# 世界设定层（WORLD_SETTING_SPEC）

> 上游总设计：[`DESIGN.md`](DESIGN.md)（总纲） · 本文为「世界设定层」模块设计文档
> 来源：2026-09-19 总设计对话整理拆分（V1.9 收敛内容）；未决细则在模块设计阶段补齐。

本模块职责：世界包（结构、生成）、世界实例（创建、锁死、黑箱）、多世界与角色拓扑、用户位置与通讯方式、导入导出与跨端同步。

## 一、世界包

### 1.1 内容范围

#### 世界包

世界设定以“世界包”为单位组织。一个世界包描述一个完整世界，包括但不限于：

- 世界背景与基本规则
- 时间体系与时间流速
- 地理范围与活动区域
- 社会结构、文化、信仰、科技/魔法水平
- 重要历史事件与当前局势
- 可出现的角色类型与角色模板
- 角色与用户之间的通讯方式及其限制
- 初始事件、传闻、未解之谜

总设计层面不定义具体字段，只确定：**世界包是结构化、可版本化、可被用户独立修改的模块。**

### 1.2 生成方式

#### 两种生成方式并存

| 方式 | 说明 | 适用场景 |
|---|---|---|
| **表单式生成** | 用户按结构化字段填写世界设定 | 用户已有明确构想 |
| **对话式生成** | 用户用自然语言描述，AI 生成候选世界包 | 用户只有模糊想法 |

两种方式可混合：用户可先对话式生成，再表单式修改。

#### 表单式生成

提供结构化字段，用户逐项填写。字段覆盖：

- 世界背景与基本规则
- 时间体系
- 地理范围
- 社会结构
- 文化信仰
- 科技/魔法水平
- 重要历史事件
- 角色模板
- 通讯方式
- 初始事件与传闻

#### 对话式生成

用户输入自然语言描述，AI 生成候选世界包。生成结果：

- 结构化
- 可编辑
- 可版本化
- 需用户确认后生效

#### 生成原则

- 生成结果必须可编辑，不是黑箱。
- 生成结果需与已有世界包版本保持一致。
- 世界包修改只影响此后**新建的世界实例**；已创建的世界实例与其时间线不受影响（无关联原则，见 §二 世界包与世界实例）。

## 二、世界包与世界实例

### 2.1 两个对象的区分

- **世界包是本地文件。**
- **世界包文件可修改，仅保留最新一版。**
- **世界包文件作为模板存在，可被反复加载。**
- **用世界包创建世界后，该世界的设定被完全锁死，不允许任何修改。**
- 锁死的是**世界实例**，不是世界包文件。

#### 修订后的模型

| 对象 | 可变性 | 版本 | 说明 |
|---|---|---|---|
| **世界包文件** | ✅ 可修改 | 仅保留最新版 | 本地文件，作为模板 |
| **世界实例** | ❌ 创建后完全锁死 | 不适用 | 从世界包加载后冻结 |
| **世界运行状态** | ✅ 可变 | 版本管理 | 时钟、角色状态、事件日志 |

#### 生命周期

```
世界包文件（本地，可修改）
        │
        │ 用户选择加载
        ▼
世界实例（创建后设定完全锁死）
        │
        │ 时间线推进
        ▼
世界运行状态（版本管理，可提交、可回滚）
```

#### 设计含义

- 世界包文件是“世界的模板”，可以有多个，可独立修改。
- 世界实例是“某个模板的一次实例化”，实例化后设定冻结。
- 同一世界包文件可被多次加载，创建多个世界实例。
- 修改世界包文件不影响已创建的世界实例。
- 世界实例的设定修改：不允许。需要新设定则创建新世界实例。

### 2.2 无关联原则

- 世界包文件与世界实例之间**无关联**。
- 修改世界包文件不影响任何已创建的世界实例。
- 删除世界包文件不影响任何已创建的世界实例。
- 世界实例不记录其来源世界包文件的引用。
- 世界实例创建后，其设定完全自包含，不依赖外部文件。

#### 设计含义

- 世界包文件是“模板”，用完即弃。
- 世界实例是“成品”，自包含、自洽、锁死。
- 用户可以自由修改、删除、替换世界包文件，不影响已有世界。
- 用户如需基于修改后的世界包创建新世界，直接加载即可。

### 2.3 设定锁死

#### 规则

- 世界包文件加载并创建世界实例后，该世界的设定被**完全锁死**。
- 不允许任何修改，包括：
  - 世界背景
  - 地理范围
  - 社会结构
  - 文化信仰
  - 科技/魔法水平
  - 角色卡
  - 通讯方式
- 没有任何例外，没有“非语义修改”通道。

#### 修改世界设定的唯一路径

- 创建新世界实例。
- 新世界实例可使用修改后的世界包文件。
- 已创建的世界实例不受影响。

#### 与世界运行状态的区别

- 世界实例设定：锁死。
- 世界运行状态：可变，通过时间线演化。
- 区分：设定是“世界的公理”，运行状态是“公理下的历史”。

### 2.4 完全黑箱

#### 规则

- 世界实例创建后，其内部数据**完全黑箱**。
- 用户不可直接查看、不可编辑世界实例的内部数据（不提供查看 / 编辑接口）。
- 世界实例可作为**整体导出 / 导入**（封装包；不加密，接受用户解压查看，项目不提供支持与解释）。
- 用户与世界实例的交互仅通过对话、版本管理操作与整体导入导出进行。

#### 用户可操作的部分

| 操作 | 是否允许 |
|---|---|
| 与角色对话 | ✅ |
| 提交（自动/手动） | ✅ |
| 回滚 | ✅ |
| 创建时间线 | ✅ |
| 切换时间线 | ✅ |
| 激活/冻结时间线 | ✅ |
| 查看世界实例内部数据 | ❌ |
| 编辑世界实例内部数据 | ❌ |
| 修改世界实例设定 | ❌ |
| 整体导出 / 导入世界实例 | ✅（见 §六 世界实例导入导出） |

#### 设计含义

- 世界实例是自包含的、不可窥探的整体。
- 用户通过对话“体验”世界，而非“检查”世界。
- 世界的内部一致性由系统保证，不由用户验证。
- 黑箱设计强化了“世界是真实的”这一体验。

## 三、多世界与角色拓扑

#### 支持层级

| 层级 | 支持 | 说明 |
|---|---|---|
| 多世界 | ✅ | 用户可拥有多个世界，各自独立 |
| 同一世界多角色 | ✅ | 同一世界可包含多个角色 |
| 同一世界角色切换 | ✅ | 用户可在同一世界内切换对话角色 |
| 同一世界角色间交互 | ❌（当前） | 未来开放世界方向再设计 |
| 跨世界角色共享 | ❌ | 角色绑定世界，不跨世界 |

#### 实现分期

- 阶段 5 之前按**单角色**运行（简化实现起步）；多角色能力在阶段 5 落地。
- 架构始终按多角色设计，预留：
  - 世界与角色的一对多关系
  - 角色切换时的会话隔离
  - 未来角色间交互的扩展点

## 四、用户位置与通讯方式

#### 用户在世界外

用户不是世界内居民。用户不占据世界中的地理位置，不直接参与世界事件。用户是：

- 观察者
- 联络者
- 对话者

用户可以通过角色间接影响世界，但影响路径是“用户 → 角色 → 世界”，而不是“用户 → 世界”。

#### 特殊双向联络

角色拥有某种“仅能与用户双向联络”的特殊通讯方式。该通讯方式由世界设定定义，例如：

- 宇航员的量子通讯终端
- 王都居民的魔法传讯石
- 货车司机的某个神秘聊天软件
- 其他符合世界观的解释

通讯方式的特点：

- 仅连接用户与角色
- 不连接世界内其他存在
- 其存在本身可以是世界设定的一部分
- 其限制可以影响角色认知

## 五、跨端同步

#### 无云同步

- 项目**不提供云同步服务**。
- 不依赖任何云端存储。
- 不自动同步任何数据。

#### 手动同步

- 所有跨端同步由**用户手动完成**。
- 同步方式：通过世界实例的导出与导入。
- 用户在桌面端导出世界实例，在安卓端导入；反之亦然。
- 同步是用户主动行为，系统不介入。

#### 设计含义

- 项目保持本地优先，无外部依赖。
- 用户完全掌控数据的迁移。
- 与黑箱设计一致：导出的是封装包，用户不编辑内部。

## 六、世界实例导入导出

#### 导出包格式

- 单一文件。
- 不加密。
- 具体格式由实现决定。
- 接受用户可能通过解压等方式查看内部数据。
- 封装世界实例的完整状态，包括世界包快照、世界运行状态、时间线、提交历史、角色状态。

#### 世界包名称存储

- 世界包名称嵌入世界包快照中。
- **系统以世界包快照中的原始名称为准。**
- **用户对世界包文件中名称的任何修改，系统视为未发生。**
- 导入时读取的是系统记录的原始名称，而非用户修改后的名称。
- 这意味着系统需在世界包快照中保留一份原始名称的独立记录，不受文件层修改影响。

#### 导出内容范围

- 仅包含世界实例本身。
- 不包含激活状态信息。
- 导入后，激活状态由导入端进行设置。

#### 导入语义

- 导入始终创建一个新的世界实例。
- 导入不修改、不覆盖、不影响任何已有世界实例。
- 新实例与原有实例完全独立。
- 各副本此后独立演化，互不影响。
- 不支持世界合并。

#### 导入实例命名

- 导入时，从导出包的世界包快照中读取**原始世界包名称**。
- 基于该名称自动生成一个候选名称。
- **全局不允许同名世界实例。**
- **同名约束全局不区分世界。** 即无论实例属于哪个世界，名称均不可重复。
- 若候选名称与已有任何实例同名，系统自动追加序号。
- **序号格式为 `名称_2`、`名称_3`，依此类推。**
- 名称生成后，交给用户进行调整、决定。
- 用户确认后，新实例以该名称创建。
- 若用户修改后的名称仍与已有实例同名，系统拒绝并提示用户。
- 用户需提供一个全局唯一的名称。

#### 版本兼容检查

- 仅在导入时检查。
- 导出时不检查版本兼容性。
- 导入时，将导入包声明的版本与当前版本比对。
- 若存在兼容性差异，向用户提示导出时的版本、当前版本、可能受影响的方面。

#### 版本不兼容的处理

- 若版本差异极大且无转换工具，拒绝导入。
- 向用户提示：建议使用对应兼容版本的项目程序进行运行。
- 不提供强制导入选项。
- **不允许手动部分迁移。**
- **仅提示使用兼容版本。**
- 有转换工具时，自动检测并提示用户确认后转换。

#### 导出包与对话体验的关系

- 导出包包含世界实例的内部真相。
- 对话体验是用户通过角色认知接口获得的局部视图。
- 两者存在差异是设计使然，不是 bug。
- 不需要提示，不需要干预。

#### 世界包文件修改责任

- 用户可对导出世界包文件进行修改。
- 项目不提供任何支持。
- 修改出现的问题，后果由用户自行承担。
- 已创建的世界实例与导出世界包文件无关联。
- 修改世界包文件不影响任何已创建的世界实例。
- **世界包名称以系统记录的原始值为准，用户修改不生效。**
