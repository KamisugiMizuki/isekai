# isekai 早期条款（V0.1 原文，未被后续版本修订）

> 来源：2026-09-19 总设计对话 V0.1。以下条款未在后续版本被重申或修订，保留原文备查。
> 注意：个别表述属早期口径（如技术选型），供模块设计阶段参考，未进入总设计正式结论。

### 组织、角色与资源需求

#### 你的角色

你是**世界设计者 + 系统架构师 + 最终验收者**。Agent assisted 模式下，你不需要写每一行代码，但需要：

- 定义世界规则和设定层的结构。
- 决定“什么算自洽”“什么算碎片化体验达标”。
- 在 Agent 产出的方案之间做取舍。

#### Agent 分工建议

| 角色 | 职责 |
|---|---|
| **架构 Agent** | 设计世界层与对话层的接口、数据结构、tick 调度机制 |
| **实现 Agent** | 按架构方案编写世界时钟、状态存储、事件系统 |
| **设定 Agent** | 协助生成和维护设定层内容（结构化世界设定） |
| **验证 Agent** | 编写一致性检查、时间同步测试、设定冲突检测 |

#### 技术选型参考

- **语言：** 沿用 Python（与现有 Veranima 一致）。
- **存储：** SQLite 起步（与现有记忆系统一致），世界状态可独立于角色记忆存储。
- **时间同步：** 不依赖网络时间，使用系统单调时钟 + 持久化基准时间。
- **LLM 调用：** 世界模拟的叙事增强部分可复用现有 LLM 通道，但**时钟推进不等待 LLM**。

### 关键假设与风险

| 假设/风险 | 影响 | 应对 |
|---|---|---|
| **假设：** 世界不需要图形化也能提供足够的沉浸感 | 高 | MVP 先验证文本层；如果体验不足，再考虑最小可视化 |
| **假设：** 角色认知接口的约束不会让对话变得“太窄” | 中 | 设定层的设计需要足够丰富，使局部认知仍有探索空间 |
| **风险：** 世界状态与角色记忆产生矛盾 | 高 | 世界层是“真相源”，角色记忆从世界层派生；定期一致性检查 |
| **风险：** LLM 生成的世界事件与已有设定冲突 | 中 | 事件生成受设定层约束；新事件必须通过一致性校验才能写入 |
| **风险：** 长期运行后世界状态膨胀，检索效率下降 | 中 | 事件日志分级：近期事件全量保留，远期事件归档为摘要 |
| **风险：** 个人项目节奏不稳定，长期搁置 | 低（已接受） | 设计时确保每个阶段可独立运行和验证 |

### 治理机制与决策原则

- **世界层是真相源。** 任何世界信息冲突时，以世界层存储为准。
- **设定变更需要“从已有设定推导”。** 不允许 Agent 直接插入与已有设定无关的新设定。
- **时钟优先。** 任何功能如果会导致时钟暂停或跳变，原则上不允许。
- **阶段门禁。** 每个阶段的验证标准未通过，不进入下一阶段。

### 评估、迭代与退出机制

- **每阶段结束后，做一次 30 分钟的“体验测试”**：你以用户身份与角色对话，记录能否感受到世界的存在、时间在走、信息在碎片化地出现。
- **如果某个阶段连续两次验证失败**，回到上一阶段重新审视设计，而非强行修补。
- **如果项目最终只有阶段 0 和阶段 1 可运行**，它仍然有价值：一个有持续位置状态的角色，已经比“对话即全部”的陪伴系统更接近“生活在世界里”的体验。
