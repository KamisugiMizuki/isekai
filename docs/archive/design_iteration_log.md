**V0.1（初版）**（消息 #4）

- 修订范围：初版：基于原始想法与 veranima-companion 现状产出《项目总设计》。
- 用户裁定（前一条原文）：原始想法：我想要做一个完整的异世界，现在暂时的想法是支持用户与一个设定在这个世界内的虚拟角色的对话，要求通过对话，用户可以拼凑出这个世界的历史、人文、重要事件等细碎设定，你可以理解为某种碎片化叙事。具体要求是角色与用户共享时间推进，现实世界每推进一秒，虚拟世界也推进一秒。 背景：我之前做了一个虚拟角色对话的项目：https://github.com/KamisugiMizuki/veranima-companion，经过一定时间的停顿与思考，我认为这个角色需要有一个完整、连续的背景世界来支撑其形象。 时间预期：无预期，作为个人兴趣项目进行推进。 这个项目我准备通过agent assisted进行制作。

**V0.2**（消息 #6）

- 修订范围：—
- 用户裁定（前一条原文）：首先，这个项目我准备基于现有的veranima-companion项目内容进行设计，但我希望做成的结果是包含了聊天功能但与原项目独立的一个项目。 我希望这个项目中，世界设定是某一个可以由用户进行独立修改的模块，在不同的世界设定下，角色可以是某一个在外太空的宇航舱里独自生活、仅通过聊天软件与用户进行交流的宇航员，其生活范围仅有宇航舱内的数十平方米，也可以是某个剑与魔法世界内王都的居民，日常活动范围为王都及其周边区域，或是现代世界内的货车司机，活动范围为整个国家。 世界设定我希望支持ai通过用户的描述进行自动生成。 角色的认知约束应当符合角色的设定，一般来说应当是软性的，除非该角色被设定为与外界无信息交流。 在当前仅作为交流软件的部分时，用户应当是该世界外的人，即你可以理解为该虚拟角色拥有某种特殊的仅能与用户双向联络的交流方式。

**V0.3**（消息 #8）

- 修订范围：这一版替代 V0.2 中关于聊天通道、角色与世界关系、多世界多角色、生成方式、世界修改与版本机制的相关部分。
- 用户裁定（前一条原文）：1. 聊天的通道应当是与聊天的内容生成部分间解耦的，项目应当支持快速的从项目提供的聊天界面切换到qq、discord等聊天软件。 2. 在我的设想内，角色应当是与世界高耦合的，以保证能使用户建立一个深入世界内的体验。 3. 项目应当支持不同世界与同一世界中不同角色的切换。后续如果做成开放世界游戏形式的话也许会需要做到同一世界内不同角色间的交互，现在先设定为同一世界仅包含一个角色吧。 4. 两者都有。 5. 世界设定应在初始就设定完成，后续如果用户需要修改则应当通过引入世界事件的方式创建时间线分支机制进行修改。世界重置可以支持，这部分我在想是不是可以学习git版本管理那种，隔一段时间进行commit、出现时间线分支时就创建branch等方式。

**V0.4**（消息 #10）

- 修订范围：这一版替代 V0.3 中关于分支推进、激活分支数量、版本管理作用域、提交频率、通道适配器形态、多角色对话历史可见性的相关部分。
- 用户裁定（前一条原文）：1. 仅激活分支推进。 2. 允许激活多个分支。 3. 版本管理作用在世界运行状态层面，世界包仅保留最新一版，支持用户自行导出备份。 4. 提交频率支持自动提交与用户手动提交。 5. 通道适配器应为插件式。 6. 在我与角色主动说明后可见，角色间不会主动表露。

**V0.5**（消息 #12）

- 修订范围：这一版替代 V0.4 中关于角色与时间线关系、对话上下文隔离、世界包可变性、提交配置、通道插件开放性、披露撤回的相关部分。
- 用户裁定（前一条原文）：1. 这部分确实不好想。我原本的想法是角色卡和世界卡都以某种类似diff的方式进行保存，在共通中仅保存所有世界线共有的内容，在每一处分支上保存该分支的所有子分支共有的内容，每一条子分支仅保留与所有兄弟分支均不同的内容。但我又想了一下，发现角色卡中即使性格也应当随着事件的发展出现变化。 2. 对话上下文随时间线进行隔离。 3. 在创建世界后就不支持修改加载好的世界包了。 4. 全局统一。 5. 允许第三方开发，应向开发者提供接口文档。 6. 撤回披露的信息应当通过将世界重置到某一个commit来实现。

**V0.6**（消息 #14）

- 修订范围：这一版替代 V0.5 中关于世界包与世界实例、角色定义与状态分离、角色状态复制方式、世界包锁定、插件沙箱、回滚语义、多角色角色卡的相关部分。
- 用户裁定（前一条原文）：在这些问题前，我需要对你的某个理解偏差进行澄清。我上一轮对话说的在创建世界后不支持修改已加载的世界包与前几轮说的世界包仅保留最新版不冲突。我的设想是世界包作为某一个文件保存在本地，创建世界时选择本地的世界包文件进行加载，在加载好世界包创建世界后该被创建的世界中的世界设定是不允许修改的，但本地的世界包文件应当是支持修改的，且仅保存最新一版世界包文件。 1. 不设定定义性格与状态性格间的区别，通过置信度等变量来控制角色性格单元的生成、变化、消失。 2. 通过类似git的diff方式来实现。 3. 在使用世界包创建世界后，该世界的设定被完全锁死，不允许任何修改。 4. 仅接口约束。 5. 被回滚操作覆盖。 6. 同一世界多角色时，不同角色间应有不同的角色卡。

**V0.7**（消息 #18）

- 修订范围：这一版替代 V0.6 中关于置信度更新规则、性格单元驱动阈值、压缩策略、世界包与世界实例关联、多角色时钟、插件进程隔离与版本兼容的相关部分。
- 用户裁定（前一条原文）：1. 置信度取值范围为0-1连续值，更新规则这部分我不是很确定，请你帮我设计一份。 2. 性格单元允许由事件、对话、时间等因素驱动，但事件驱动生成的性格单元的置信度的上下限阈值应高于对话、时间等驱动生成的性格单元的置信度上下限阈值。 3. 自动压缩，压缩策略这部分我认为应当在实现后根据表现进行相应处理。 4. 无关联。 5. 同一世界的多角色间应共享世界时钟。 6. 若接口设计发生改变则向用户提示该插件依赖于就接口版本，可能与当前版本不兼容，并尝试运行插件，若无报错信息则正常使用，若有报错信息则将其反馈给用户，同时停止插件进程。另，第三方插件应作为单独进程进行运行，以防止其出现错误时连带主程序崩溃。

- 用户裁定（前一条原文）：1. 你说的这三个不是正好把三个驱动方式包括全了么。 2. ai自动生成。 3. 实际上在现实中与某一个人很久不见之后也会出现很难认出ta的情况，我认为需要给角色加上一些可辨识的锚点，包括但不限于行事风格、说话句式、口癖等。 4. 这部分在具体实现时进行确定。实际上我有一个想法是这个项目后续可能会移植到安卓端进行运行。 5. 内建聊天窗口作为核心进程的一部分。 6. 完全黑箱。
