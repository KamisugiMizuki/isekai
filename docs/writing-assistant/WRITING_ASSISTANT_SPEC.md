## 一、定位

Writing Assistant 是面向小说创作的上层叙事约束编排模块，负责把作者给定的故事大纲、创作意图和观察视角转换成可执行的叙事约束，并在 WorldRuntime 变化后返回符合视角的信息和候选表达。

GM 辅助不是它的首要设计目标，而是同一套“大纲约束 + 世界观察 + 候选编排”能力在 TRPG 主持场景中的一种应用方式。小说作者是默认用户；GM 使用时需要额外接入玩家视角、规则裁定和主持提交权限。


| 模式 | 用户 | 输入 | 输出 |
|---|---|---|---|
| GM 辅助 | GM | 故事大纲、场景安排、直接变化、主持要求 | 玩家观察到的情况、场景候选、待确认世界变化 |
| 小说写作辅助 | 作者 | 故事大纲、章节目标、人物安排、写作指令 | 可选情节推进、角色视角材料、场景草稿 |

两种模式共享大纲约束、世界观察和候选编排，但不共享提交权限：GM 只能通过 TRPG 规则层的 GM 直接变化路径提交主持声明；小说写作辅助默认只生成候选或草稿，明确批准后才进入 WorldRuntime 的 preview / commit。

Writing Assistant 不是 WorldRuntime 的第二个事实层，也不是自动保证故事“按大纲发生”的强制引擎。它通过约束、偏离检测、候选提议和显式批准帮助故事靠近大纲；玩家选择、角色行为、规则裁定和世界后果仍可能导致偏离。

## 二、与三个相邻模块的关系

```text
OC 故事层
  -> 用户不提供故事大纲，消费角色合法视图并进行联络

TRPG 规则层
  -> 玩家提供行动，规则插件裁定，公共模块提交世界后果

Writing Assistant
  -> 创作者提供大纲和叙事约束，观察世界 / 场景结果，提出或提交下一步
```

Writing Assistant 与 OC 故事层都可能产生自然语言表达，但入口语义不同：OC 是“角色向用户表达已经存在的生活”；Writing Assistant 是“创作者编排故事目标并观察可行的推进”。不能用角色对话入口偷偷解释创作者指令。

## 三、大纲模型

大纲不是一串强制事件列表，而是分层约束：

| 层级 | 内容 | 默认强度 |
|---|---|---|
| 主题约束 | 作品关注的冲突、主题、情绪方向 | 软约束 |
| 必达节点 | 必须发生或必须被揭示的关键节点 | 硬约束 |
| 禁止事项 | 不得发生的事实、关系或结局 | 硬约束 |
| 角色弧线 | 角色需要面对的选择和变化方向 | 中约束 |
| 节奏目标 | 场景阶段、章节目标、悬念释放窗口 | 中约束 |
| 可变素材 | 地点、遭遇、对白、过场和实现方式 | 软约束 |

每条大纲条目都要有：

- 稳定标识；
- 约束类型和强度；
- 适用范围：世界、时间线、章节、场景或角色；
- 前置条件；
- 成功判据；
- 允许的替代路径；
- 当前状态：未开始、进行中、已达成、已偏离、已放弃。

“主角必须在第三章知道真相”是节点约束；“第三章必须在车站通过某句对白知道真相”是过度指定。系统优先守住叙事功能和因果，不强行复现某个表面场景。

## 四、大纲状态与世界事实分离

Writing Assistant 维护的是大纲定义、时间线上的达成状态、候选、草稿和创作者决定，不拥有世界事实：

```text
大纲定义
  -> 绑定实例 / 时间线 / 观察视角
  -> 读取 WorldRuntime 一致快照与认知投影
  -> 评估达成、偏离、冲突和缺口
  -> 生成候选或观察材料
  -> 作者 / GM 选择
      ├─ 锁定文本草稿
      ├─ 在分支中试演
      └─ 形成结构化变化，走 preview -> commit
```

### 4.1 四类长期对象

| 对象 | 所有者 | 是否事实 | 版本范围 | 作用 |
|---|---|---:|---|---|
| 大纲定义 | Writing Assistant | 否 | 可跨时间线复用 | 主题、节点、禁止事项、角色弧线和节奏目标 |
| 大纲状态 | Writing Assistant | 否 | 实例 + 时间线 | 当前条目是未开始、进行中、已达成、已偏离或已放弃 |
| 候选 / 决定 | Writing Assistant | 否 | 快照 / 时间线 | 建议、选择、接受偏离和创作者理由 |
| 世界事实 | WorldRuntime | 是 | 实例 + 时间线 | 只有合法变化提交后才存在 |

文本草稿是独立的表达产物。它可以引用世界快照，但不会因为被锁定、导出或放入章节就变成世界事实；同样，世界事实提交成功也不会自动生成一段合格散文。

### 4.2 大纲条目的最小语义

每条条目必须有稳定标识、类型、约束强度、适用范围、前置条件、成功判据、允许的替代路径和当前状态。条目还应记录其依赖条目与最近一次评估所依据的世界快照。

条目状态只由可追溯的世界事实、角色认知、规则结果或创作者决定推动：

```text
unstarted -> in_progress -> achieved
                      ├-> deviated
                      └-> abandoned
```

`deviated` 不等于 `achieved`。只有明确选择替代路径、改写条目或接受偏离，状态才可变化；自然语言草稿、模型判断和“看起来像发生了”都不能单独推动硬约束达成。

### 4.3 候选与草稿生命周期

候选引用一个固定快照和可见材料，至少标明适用条目、事实 / 因果 / 大纲依据、受众、来源水位、可能变化和未解决问题。候选生命周期为：

```text
proposed -> selected -> approved -> committed
       ├-> rejected
       ├-> deferred
       └-> stale / conflict
```

`approved` 只表示创作者同意采用该方案，不表示世界已经改变；只有 `runtime.change.commit` 返回 `committed` 或 `duplicate`，候选中的世界变化才可被描述为已发生。文本候选可以在 `approved` 后直接形成草稿，但仍保留“未提交世界”的标记。

## 五、GM 辅助模式

### 5.1 GM 直接输入

GM 可以输入三种不同内容：

| 输入 | 处理 | 权威结果 |
|---|---|---|
| 世界变化声明 | 形成 `source=gm_declaration` 的待提交结构化后果 | 只有联合提交成功才成为世界事实 |
| 故事意图 | 生成候选行动 / 场景推进，不直接改世界 | Writing Assistant 候选或草稿 |
| 玩家观察请求 | 根据当前角色视角生成可见情况，不新增事实 | 当前快照上的观察结果 |

例如“城门已被毁”是世界变化声明；“我希望这一章让玩家感到被追踪”是故事意图；“玩家现在看到什么”是观察请求。三者不可混为一条自由文本命令。Writing Assistant 不直接调用世界写入口；GM 批准后由 TRPG 规则层的 GM 直接变化路径继续处理。

### 5.2 GM 输出

GM 辅助输出分为三层：

1. **玩家观察层**：玩家角色在当前视角下看到、听到、推断或不知道什么；
2. **主持依据层**：哪些世界事实、认知边界和大纲条目支持这个观察；
3. **下一步编排层**：候选场景、NPC 反应、可能推进和需要 GM 决定的分歧。

玩家观察层可直接用于主持；主持依据层默认只给 GM；下一步编排层必须标注候选，不得伪装成已发生。Writing Assistant 可以提供结构化内容和草稿，GM / 客户端决定最终表达；本模块不承担通用 GM 文本生成器的所有权。

### 5.3 GM 的控制点

- 接受或修改故事候选；
- 确认直接世界变化；
- 选择玩家观察视角；
- 调整大纲条目的软约束；
- 暂停推进并补充创作条件；
- 创建分支试演不同后果。

硬约束冲突时系统应阻止或明确要求 GM 选择“改大纲 / 改世界 / 接受偏离”，不能自动牺牲任一方并继续讲下去。

## 六、小说写作辅助模式

小说模式默认运行在草稿世界或只读投影中。作者可以：

- 输入章节目标、人物焦点和叙事视角；
- 查看角色按自身认知能观察到的素材；
- 让系统提出多条情节推进和冲突后果；
- 固定采用某条候选，形成章节草稿；
- 在提交前比较不同分支；
- 把确定的世界事件 / 角色经历提交到作品时间线。

小说模式生成的对白、场景描写和章节草稿是表达产物，不会自动成为世界事实。作者确认的“作品中采用”仍要区分：仅锁定文本，还是同时向作品世界提交事件和角色经历。

## 七、偏离检测

偏离检查分三类：

- **事实偏离**：候选或新提交与已固化世界事实冲突；
- **因果偏离**：结果缺少前置条件、跳过必要变化或破坏时间顺序；
- **大纲偏离**：未达成必达节点、触发禁止事项或角色弧线长期离轨。

偏离不是一律错误：创作者可以明确接受偏离并把大纲条目标记为替代路径、改写或放弃。系统要记录决定及其原因，不能静默把偏离重新解释成达成。

## 八、时间线与分支

Writing Assistant 的世界观察和达成状态绑定实例与时间线。试演候选优先在新分支中运行；项目不提供世界线合并：作者只能选择一条线继续，或把候选重新表达为当前线上的新变化并再次经过 preview / commit。生成文本草稿可以脱离世界分支存在，但引用的事实必须标注来源水位。

回滚世界不自动回滚作者已经导出的文本；文本回滚也不自动回滚世界。两者需要分别确认，避免“删掉一段草稿”意外改变持续世界。大纲定义可以跨分支复用，但每条线的达成、偏离和接受决定必须独立记录。

## 九、与 TRPG 的结合

GM 辅助模式可以接在 TRPG 规则层外侧：

```text
玩家行动
  -> TRPG 规则独占转接插件
  -> TRPG 规则共用模块
  -> WorldRuntime 提交
  -> Writing Assistant 读取新状态
  -> 输出玩家观察与大纲偏离
```

GM 的直接变化不伪装成玩家行动，也不由 Writing Assistant 自己写世界。Writing Assistant 只负责把创作者意图整理成待确认的结构化请求；实际提交进入 TRPG 规则层的 GM 直接变化路径，由公共模块和 WorldRuntime 做同一套校验：

```text
GM 直接变化意图
  -> Writing Assistant 结构化为待确认候选
  -> GM 明确批准
  -> TRPG 规则层 / Campaign Runtime 的 gm.change
  -> TRPG 规则共用模块
  -> WorldRuntime preview / commit
```

这样 GM 辅助不会与 OC 故事层重合：OC 消费角色表达；Writing Assistant 编排创作者目标并维护大纲；TRPG 规则层维护行动、裁定和 GM 提交；WorldRuntime 统一拥有事实。

## 十、设计不变式

1. 大纲是约束和目标，不是已经发生的事实。
2. Writing Assistant 不拥有世界真值。
3. 玩家观察只能来自对应视角能获得的世界材料。
4. 候选、草稿和主持建议必须标明未提交状态。
5. GM 直接声明与规则裁定走不同来源，但共享结构化后果校验与 WorldRuntime 提交。
6. 大纲偏离可以被明确接受，不能被静默掩盖。
7. 试演优先走分支；接受、选定继续的世界线、回滚和文本导出分别确认，世界线之间不提供合并。
8. 小说模式默认不直接修改持续世界。
9. OC 故事层不承担大纲维护，Writing Assistant 不承担普通角色联络。

## 十一、推荐分期

### W0：只读大纲与观察

建立大纲、绑定角色 / 时间线、读取合法视图、输出玩家观察和偏离提示。不提交世界变化。

### W1：GM 直接变化

支持结构化 GM 声明、WorldRuntime 校验、玩家视角观察和提交前的待确认状态。已提交变化不提供旁路撤回；需要反转时走明确的分支或回滚语义。覆盖事实冲突、认知隔离和版本冲突。

### W2：TRPG GM 辅助

接入规则共用模块，读取玩家行动结果，维护大纲状态，生成场景候选和主持依据。规则裁定与 GM 声明都保留来源。

### W3：小说写作辅助

加入草稿分支、章节目标、候选比较、文本锁定和世界提交分离。先做单作者，不做多人协作和自动出版。

## 十二、行为验收

| 场景 | 必须观察到的结果 |
|---|---|
| 新建大纲 | 条目可区分主题、必达、禁止、角色弧线、节奏与可变素材；每条有稳定标识、范围、前置和判据 |
| 只读观察 | Writing Assistant 只能看到给定实例 / 时间线 / 观察者在一致快照上的合法投影 |
| 未达成硬约束 | 报告缺口或提出候选，不自动制造世界事实，不把候选标成已达成 |
| 候选批准 | 候选进入 `approved` 或文本草稿；在 WorldRuntime `commit` 成功前仍标为未提交 |
| 事实冲突 / 因果缺口 | 候选进入 rejected / needs_review / conflict，并给出需要修改的依据 |
| GM 直接变化 | Writing Assistant 只形成待批准结构；批准后经 TRPG GM 变化路径、公共模块和 WorldRuntime 提交 |
| 玩家行动结果 | 读取 TRPG 已固化结果后更新大纲状态；规则成功但世界提交失败时不标记达成 |
| 分支试演 | 新线可观察候选后果，主线不被污染；项目不提供世界线合并 |
| 世界回滚 | 大纲状态按目标时间线重新评估；已导出的文本不被自动删除，文本操作不反向回滚世界 |
| 快照过期 | 候选在写入前被 `generation.check` 判为 stale / conflict，不写回旧世界 |
| 受众隔离 | 玩家观察不包含 GM 私有依据、其他角色私密内容、未获知事实或规则状态正文 |

以上场景必须通过真实 WorldRuntime 接口边界验证；Writing Assistant 的设计状态不等于功能已实现。

| §4.3 候选生命周期 | `candidates.py` + `wa.candidate.propose/decide/commit` | 七个状态，`approved` 明确属于「未提交」；带世界变化的候选先过 `change.preview`——指名条目的拒绝与版本冲突才算驳回，通配拒绝与 `needs_review` 留在待确认；提交前再跑 `generation.check`（世代变了判 `stale`，不写回旧世界），并按当前水位**重新预览**一次后落库 |
| §六 模型提议（W3） | `wa.suggest` | 一次便宜调用产出多条推进提议，落成 `proposed` 候选（带适用条目与未解决问题）；提议不写世界、不推状态、不改达成 |
| §八 时间线与分支 | `wa.branch` | 只编排 `runtime.fork` + 把同一份大纲绑到新线：定义跨线复用，达成 / 偏离决定各自独立（新线从「未开始」记）。文案与规范一致：不提供世界线合并 |
| §4.1 四类长期对象归属 | `store.py` 三张表（`wa_outline` / `wa_state` / `wa_candidate`） | 大纲定义是作者资产（跨线复用）；达成状态与候选按实例 + 时间线独立；**不随世界回滚消失**（规范要求的是「回滚后重新评估」，不是自动恢复旧状态）；锁定过的文本因此不受回滚影响，并随实例删除清理 |
