# TRPG 客户端规范

> 状态：已定稿 v1.0（2026-09-22）。
>
> 本文是 `docs/trpg-client/` 下 TRPG 客户端产品层的唯一规范。它只定义玩家 / GM 的产品职责、状态、视角、行动流程、结果表达和行为验收；不设计桌面壳连接方式，不定义 Tauri / UMP / WebSocket / 管理面接线，也不代表客户端代码已经实现。
>
> 本文不把客户端章节拆复制到规则插件、公共模块或 Campaign Runtime 的 SPEC 中。其他 SPEC 只维护各自拥有的协议与运行时契约；客户端引用这些契约，客户端的产品流程、视角、确认和表达语义由本文维护。
>
> 归属关系：
>
> - 本文：玩家 / GM 产品模式、场景与视角、行动确认、结果表达、失败体验、恢复交互、客户端行为验收；
> - `TRPG_RULES_LAYER_SPEC.md`：规则层的跨模块编排边界；
> - `TRPG_CAMPAIGN_RUNTIME_SPEC.md`：战役、场景、行动、待选择、规则状态和联合提交的权威运行时语义；
> - `TRPG_RULE_PLUGIN_SPEC.md`：规则插件进程与请求 / 响应协议；
> - `TRPG_RULE_COMMON_MODULE_SPEC.md`：规则私有裁定到通用世界后果的转换与校验；
> - `WORLD_RUNTIME_INTERFACE_SPEC.md`：世界快照、认知投影、变化提交和版本边界。
>
> 其他 SPEC 需要新增字段或状态时，必须回到其所属边界修改；本文只同步客户端如何呈现和消费它。

## 一、产品定位

TRPG 客户端是一个**战役游玩与主持编排界面**。它把用户的自然语言行动转成待确认的行动声明，把 Campaign Runtime 的场景投影和规则插件的裁定结果组织成玩家或 GM 能继续使用的新局面。

```text
WorldRuntime
  世界事实、时间、认知、版本、结构化世界后果

TRPG Campaign Runtime
  战役、场景、行动生命周期、待选择、受众、规则节拍

规则插件
  属性、技能、资源、骰点、职业、状态、规则私有裁定

TRPG 客户端
  视角、行动输入、确认、结果解释、主持介入、下一选择
```

客户端是应用层编排者，不是世界真值所有者。客户端可以决定用户怎样输入和查看一次行动，但不能因为界面上显示了“成功”就把行动说成已经改变世界。客户端只有在联合提交返回 `committed` 或 `duplicate` 后，才可以把世界后果表达为已经发生。

客户端首版针对单机、单用户和一个活动玩家角色设计。首版不把同一用户控制多个角色作为默认队伍模型；多角色队伍与角色切换属于 C4。GM 可以查看玩家视角与主持视角，但两者仍通过受众隔离，不自动合并角色认知。

## 二、设计目标与非目标

### 2.1 目标

1. 用户不用先学习规则书，也能用自然语言声明行动。
2. 每个关键行动在裁定前都有可理解的行动确认点。
3. 用户能持续知道当前地点、在场者、已知事实、风险和等待的选择。
4. 规则复杂度可以展开查看，但默认阅读路径先回答“发生了什么、为什么、现在怎么办”。
5. 成功、部分成功、失败、待补充和待主持确认都有不同的产品状态。
6. 规则私有状态、世界事实、角色认知和 GM 私有依据不会混成一份“剧情文本”。
7. 结果提交失败时，客户端清楚表达“裁定完成但世界尚未落地”，不把失败润色为故事结果。
8. 同一行动、选择、提交重试时，客户端能够回到原结果，不重复制造一轮行动。
9. 场景结束后，用户总能回到一个新的可行动局面，或者明确知道为什么暂时不能行动。

### 2.2 非目标

首版不包含：

- 桌面壳、移动壳、窗口、托盘、登录、连接和通道设计；
- 在线多人同步、房间、邀请、玩家账号和权限协商；
- 全规则书导入、自然语言自动编译规则书；
- 通用地图编辑器、战斗网格编辑器、视线和路径渲染器；
- 完整战役自动生成器；
- 用户浏览 GM 实情、全部事件、全部记忆或规则状态正文；
- 由 LLM 直接决定世界事实、替玩家确认关键行动或绕过规则插件；
- 将所有规则统一成属性、生命、回合、骰池或资源面板；
- 把客户端连接层和桌面壳管理页当成同一个产品面。

地图、战斗格和复杂规则状态如果以后加入，属于客户端的可替换视图与对应规则插件能力，不应反向扩展 WorldRuntime 的题材字段。

## 三、用户模式

客户端提供两个明确的工作模式。模式改变输入语义、可见材料和允许的提交路径；同一段文本在两个模式下不能默默套用另一种解释。

| 模式 | 用户身份 | 主要输入 | 客户端负责 | 关键确认 |
|---|---|---|---|---|
| 玩家模式 | 玩家 / 单个活动玩家角色的操作者 | 自然语言行动、选择、补充条件 | 展示角色视角、形成行动声明、请求裁定、展示结果 | 关键行动确认；玩家不被代替选择 |
| GM 辅助模式 | 主持人 / 创作者 | 场景安排、结构化直接变化、规则裁定请求、玩家观察请求 | 管理场景、表达玩家视角、提交 GM 变化、保留主持依据 | 争议事实、直接变化和故事候选必须明确批准 |

GM 模式中的三类输入必须在入口上分开：

- **规则行动**：玩家或 NPC 按规则尝试做事，调用规则插件。
- **GM 直接变化**：主持人声明一个已经决定成立的结构化世界变化，走 `gm_declaration`，不伪造骰点。
- **故事意图**：主持人希望某种悬念、节奏或场面出现，只形成候选或提示，不直接写世界。

客户端不能把“我希望玩家发现有人跟踪”当成已发生事实，也不能把“城门已经被毁”误送进玩家行动骰点流程。

### 3.1 默认责任模式

首版采用**辅助裁定**，并固定两种提交语义：

- **玩家模式**：用户确认行动后，客户端自动调用规则裁定并在结果合法时自动发起 `trpg.commit`。玩家不需要对同一行动再点一次“批准提交”；联合提交失败则停在明确的失败 / 待审状态。
- **GM 模式**：GM 可以查看裁定结果并决定是否提交；`needs_review`、GM 直接变化、争议事实和故事候选必须经过 GM 明确操作。

两种模式共用 Campaign Runtime 和 WorldRuntime 的状态机，不建立第二套写入路径。首版的“表达”是结构化结果、受众允许的公开摘要和主持人提供的文本；客户端不在 C0–C2 自己生成 GM 散文。

客户端在玩家模式中负责：

- 帮助解析行动、显示风险、调用插件、展示结果；
- 保留关键行动确认；
- 合法裁定后自动完成联合提交；
- 让用户看到提交失败的真实状态。

插件负责规则裁定，Campaign Runtime 负责行动状态和场景转换，WorldRuntime 负责世界后果，客户端负责把已提交结果表达为下一局面。

自动主持与共同主持不属于首版的独立后台模式。它们作为未来责任模式扩展保留；新增时必须复用同一行动确认、联合提交和受众边界。

## 四、客户端持有的状态

客户端状态是可丢弃、可重建的产品状态，不是真值副本。需要长期恢复的对象由 Campaign Runtime、规则状态附件和 WorldRuntime 持有；客户端只保存当前视角、草稿和显示状态。

### 4.1 当前工作区

```text
workspace
  mode                 player | gm
  campaign_id
  instance_id
  timeline_id
  audience              public_party | character:<id> | player:<id> | gm_only
  active_character_id?  当前声明行动的玩家角色
  selected_scene_id
  selected_action_id?
  selected_choice_id?
  draft_text
  draft_revision
  view_revision
```

`instance_id`、`timeline_id`、`campaign_id` 和 `audience` 每次读取 / 写入都显式传递。客户端的“当前战役”选择只是界面状态，不能替代接口调用中的作用域。

### 4.2 服务端权威投影

客户端每次进入战役、切换场景、提交动作或从错误恢复时，重新读取以下投影：

```text
campaign_view
  campaign_id / ruleset_id / ruleset_version
  status / state_revision / current_scene_id
  participant references

scene_view
  scene_id / kind / locations
  world snapshot reference
  public facts
  private views allowed for current audience
  active risks
  available actions
  turn / phase state
  open choices

action_view
  action_id / action_revision
  actor / target / method / intent
  confirmation / status
  visible risks / failure code
  committed reference when available

rule_view
  ruleset identity
  state revision only
  public result summaries present in the current result (if any)

world_view
  observed revision / world time
  player- or character-scoped observations
  public history references needed to explain the current scene
```

规则状态正文和插件原始 `resolution` 默认属于 `gm_only`。玩家界面只能消费规则插件或客户端生成的、明确标记为玩家可见的摘要。

### 4.3 客户端派生状态

以下内容可以存在于客户端本地，但丢失后可从权威投影重建：

- 输入框草稿；
- 行动确认卡的展开 / 折叠状态；
- 裁定摘要是否展开；
- 最近阅读位置；
- 客户端生成的加载、错误和重试状态；
- 当前页面布局和筛选条件。

客户端不得把自己的 `scene summary`、`available actions` 缓存当成事实。缓存过期、战役 revision 变化或运行世代变化时，直接标记旧投影失效并重新读取。

## 五、核心产品面

客户端不按“数据库表”组织用户界面，而按用户正在完成的任务组织为四个面。

```text
战役选择
  ├─ 战役列表 / 规则版本 / 状态
  └─ 新建或恢复战役

场景面
  ├─ GM 叙述 / 当前局面
  ├─ 场景事实、风险、在场者
  ├─ 行动输入与确认
  └─ 待选择 / 结果 / 下一局面

队伍面
  ├─ 当前玩家角色
  ├─ 角色可见状态与受众
  └─ 队伍公开信息与角色私密信息边界

主持面
  ├─ 玩家可见预览
  ├─ GM 直接变化
  ├─ 裁定摘要与提交状态
  └─ 暂停、待审、版本阻断、恢复
```

这是产品层结构，不规定具体窗口、导航栏、页面路由或桌面壳承载形式。

### 5.1 战役选择

战役列表至少显示：

- 战役名称或说明；
- 所属世界实例 / 时间线的用户可识别名称；
- 规则系统和规则版本；
- `preparing`、`active`、`waiting`、`paused`、`blocked`、`archived` 状态；
- 当前场景名称或“尚未建立场景”；
- 上次可继续的工作位置。

玩家看到 `blocked` 时只能读取原因、导出或等待主持处理，不能看到规则状态正文。`waiting` 时列表明确提示“等待选择 / 补充输入 / 主持确认”，避免用户误以为输入框失灵。

新建战役需要依次完成：

1. 选择世界实例与时间线；
2. 选择已登记的规则插件与规则版本；
3. 选择当前玩家角色；
4. 建立首个场景或进入 `preparing`；
5. 显示规则版本和视角约束；
6. 用户确认后进入战役。

客户端不在此阶段编辑规则字段，也不要求用户手工填写插件的 opaque state。

### 5.2 场景面

场景面是用户最常停留的工作区。首屏从上到下只回答三件事：

1. 现在发生在哪里、谁在场、已知什么；
2. 当前有哪些危险、限制和等待中的选择；
3. 用户下一步可以做什么。

推荐结构：

```text
┌─────────────────────────────────────────────┐
│ 战役名 · 场景名 · 世界时刻 · 当前角色 / 受众 │
├─────────────────────────────────────────────┤
│ GM / 场景表达                                │
│ 已确认事实 · 在场者 · 当前风险               │
│                                             │
│ 待处理选择（有则置顶）                       │
│                                             │
│ 行动结果时间线                               │
│                                             │
│ [描述你要做什么]                   [提交行动] │
└─────────────────────────────────────────────┘
```

上面的线框只表达信息层级，不绑定具体 UI 实现。

场景面必须区分：

- **事实**：当前受众可确认、能追溯到 WorldRuntime 或已提交结果的内容；
- **未知**：用户知道这里存在疑问，但没有得到答案；
- **风险**：可能影响行动的危险、限制或有效后果；
- **候选行动**：系统 / 插件 / GM 建议的入口，不代表用户已经选择；
- **行动结果**：已裁定或已提交的历史；
- **下一选择**：玩家尚未做出的分支，不是世界事实。

场景面不显示全量事件日志或全量世界内部数据。用户需要复盘时，展开一项行动的裁定摘要即可。

### 5.3 队伍面

队伍面属于 C4，不是首版 C0–C3 的必需面。C0–C3 只显示当前活动玩家角色、该角色的受众和队伍公开材料；不提供同一用户控制多名角色的切换流程。

C4 加入多角色队伍后，队伍面显示：

- 当前战役参与者；
- 当前由谁声明行动；
- 谁处于场景中、谁只是世界实体引用；
- 队伍公开材料；
- 当前角色可见的私密材料；
- 角色切换后的受众变化提示。

切换角色不会把角色 A 的认知、私密材料或行动历史复制到角色 B。客户端切换的是 `audience` 与 `actor_id`，不是给用户发一份全知视图。

规则属性、资源、装备、状态和能力由插件定义。客户端只在插件声明可公开投影时显示它们；未声明的字段不因“有一个状态面板”而被客户端自行推断。

### 5.4 主持面

主持面提供更完整的结构化信息，但仍不允许旁路写世界。

主持面包括：

- 当前场景的 GM 投影；
- 玩家视角预览；
- 行动状态和失败原因；
- 原始裁定的受限摘要 / 展开内容；
- 规则状态 revision 与版本兼容状态；
- 待主持审查的结果；
- GM 直接变化的结构化输入；
- 当前战役的暂停 / 恢复 / 归档入口；
- 分支试演和回滚入口的明确危险提示。

主持面可以看到 `gm_only` 材料，但它不应把 GM 事实自动复制到玩家预览。玩家预览是一个独立的受众投影，提交前必须明确检查一次。

## 六、行动输入与确认

自然语言是入口，结构化行动声明是裁定边界。

### 6.1 输入阶段

用户输入：

> 我想调查礼拜堂墙面，看看有没有机关。

客户端发送的不是“把墙面状态改成已调查”，而是生成一个待确认行动草稿：

```text
原始描述：我想调查礼拜堂墙面，看看有没有机关。
行动者：当前玩家角色
目标：礼拜堂墙面
方法：调查 / 搜索
意图：寻找机关或异常
期望结果：获得关于机关的可用信息
可见风险：可能触发已有危险，可能消耗时间
确认状态：待确认
```

客户端可以调用一个上层意图解析能力，但解析失败或关键字段不明确时，必须把缺口显示出来，让用户补充。客户端不能用模型猜出行动者、目标或代价后直接进入裁定。

### 6.2 确认卡

关键行动在调用规则插件前显示确认卡，至少包含：

- 行动者；
- 目标 / 对象；
- 方法；
- 意图；
- 预期结果；
- 已知前置条件；
- 用户可见风险；
- 可能消耗的时间或已公开的代价；
- 当前场景与行动 revision。

操作：

- **确认行动**：进入 `confirmed`；
- **修改行动**：提高 `action_revision`，回到解释 / 确认阶段；
- **放弃行动**：进入 `abandoned`，不调用有状态裁定、不写世界；
- **补充信息**：保留原始描述，增加或修改可裁定字段。

旧 revision 的确认卡在用户修改后失效。客户端不能用旧卡上的按钮提交新行动。

### 6.3 低风险行动

首版不提供“低风险自动确认”开关。所有会进入规则裁定的玩家行动都先经过一次用户确认；C3 之后若真实使用证明低风险自动确认有价值，再作为责任模式扩展设计，并复用同一 action revision 与联合提交语义。

## 七、行动生命周期与客户端状态

状态映射使用 Campaign Runtime 的实际状态集合。`interpreted` 和 `awaiting_confirmation` 都显示为“等待行动确认”；`snapshotting` 与 `resolving` 都显示为“正在裁定”。客户端不创造一个独立的 `interpreting` 状态。

```text
received
  → interpreted
  → awaiting_confirmation
  → confirmed
  → snapshotting
  → resolving
  → reviewing
  → awaiting_choice / awaiting_gm_review / committing
  → committed
  → transitioned
```

### 7.1 用户可见状态表

| 核心状态 | 用户文案 | 可操作内容 | 禁止的客户端行为 |
|---|---|---|---|
| `received` / `interpreted` | 正在理解行动 | 补充、取消 | 显示为已裁定 |
| `awaiting_confirmation` | 等待确认 | 确认、修改、放弃 | 调插件或提交世界 |
| `confirmed` | 已确认，等待裁定 | 查看、取消（若状态仍允许） | 修改成另一个 action_id |
| `snapshotting` | 正在取得当前世界与规则状态 | 等待 | 重新发起随机裁定 |
| `resolving` | 规则裁定中 | 等待 / 查看阶段说明 | 猜测骰点或结果 |
| `reviewing` | 裁定完成；玩家模式自动尝试提交，GM 模式等待主持操作 | 查看摘要；GM 可提交、拒绝或转待审 | 在提交成功前说成世界已经改变 |
| `awaiting_choice` | 等待玩家选择 | 只能处理对应 choice | 声明下一关键行动 |
| `awaiting_gm_review` | 等待主持确认 | 主持批准、修改或拒绝 | 玩家端自行提交 |
| `committing` | 正在写入规则状态与世界后果 | 等待 | 分开重试其中一半 |
| `committed` | 结果已固化 | 查看结果、进入新局面 | 再扣一次资源 |
| `transitioned` | 已进入新局面 | 声明下一行动 | 把旧局面继续当当前局面 |
| `plugin_failed` | 规则裁定失败 | 查看原因、显式重试 / 修改 | 自动重跑随机结果 |
| `conflict` | 当前状态已变化 | 重新读取、重新确认 / 裁定 | 套用旧 patch |
| `stale` | 这次结果已过期 | 丢弃旧结果、重新读取场景 | 写回旧世界 |
| `rejected` | 行动被规则或世界约束拒绝 | 修改、放弃、补充条件 | 改成成功叙述 |
| `interrupted` | 核心在裁定中断 | 显式恢复 / 重试 | 自动重跑不完整裁定 |

“重试”必须区分两类：

- **恢复原提交**：带原 `idempotency_key`，只查询和重放原结果；
- **重新裁定**：只有用户明确要求，且产生新的行动 revision / 新幂等身份，才允许再次调用可能产生随机结果的插件。

## 八、裁定结果的表达结构

客户端对一次结果至少提供四层信息，默认显示第一层和第二层，其他内容可展开。

### 8.1 第一层：玩家可读结果

```text
结果：成功 / 部分成功 / 失败 / 无法裁定 / 等待选择
发生了什么：已经提交结果的自然语言说明
当前局面：地点、在场者、风险和新的等待状态
下一步：用户现在能做的行动或选择
```

这层只使用当前受众可见材料。没有提交成功的结果不能使用“已经发生”“门已经打开”等确定措辞。

### 8.2 第二层：裁定理由

```text
行动理解：本次按什么行动处理
规则依据：规则系统与公开可见的规则类别
结果等级：插件允许公开的 outcome / degree
代价：已确认的资源、时间或世界后果
提交状态：committed / duplicate / rejected / needs_review / stale
```

难度、秘密修正、GM 私有骰点或其他 `gm_only` 材料只在相应主持视角可见。客户端不为了“解释清楚”泄露玩家不应知道的真相。

### 8.3 第三层：审计摘要

主持人或拥有权限的复盘视角可展开：

- `action_id`、`action_revision`；
- ruleset / plugin manifest / ruleset version；
- 世界 snapshot / revision；
- 规则状态 base revision 与新 revision；
- 原始 `resolution` 引用；
- world consequence 数量与引用；
- scene transition；
- joint commit id；
- 失败代码和恢复入口。

玩家面默认不显示原始骰点、秘密难度、隐藏修正和完整插件上下文；插件可以通过明确的公开摘要提供结果等级、公开骰点或其他可见解释。客户端不新增“公开骰点”协议，先消费插件现有的受众标记。

### 8.4 第四层：原始材料

只对 GM 或调试 / 复盘视角开放，并标明“规则插件原始材料”。它不能直接进入玩家聊天、场景事实或 WorldRuntime 世界历史。

## 九、结果分类与失败体验

### 9.1 成功

成功必须同时满足：

- 插件返回合法裁定；
- 公共后果通过结构检查；
- WorldRuntime 目标、效果、时间、认知和版本校验通过；
- 规则状态与世界后果联合提交成功。

玩家模式下客户端在裁定结果合法时自动发起联合提交；GM 模式下由 GM 明确发起提交。客户端显示结果时把“规则成功”和“世界已固化”分成两个可核对状态，避免只看插件响应。

### 9.2 部分成功 / 带代价

部分成功由插件声明结果等级和结构化后果。客户端显示：

- 达成的部分；
- 已发生的代价；
- 还未达成的目标；
- 新增的风险或选择。

如果插件没有返回合法代价，客户端不能自己编一个代价来让故事更完整。

### 9.3 失败

失败至少落入一个可理解分支：

- 失败但获得信息；
- 失败并消耗时间 / 资源 / 位置优势；
- 失败触发合法的危险或 NPC 反应；
- 失败但局面没有变化，并明确说明没有变化；
- 行动条件不足，等待用户补充；
- 规则结果等待用户选择。

客户端不把“失败但没有后果”自动渲染成“剧情暂时没推进”，除非提交结果明确说明世界没有变化。

### 9.4 无法裁定 / 待审

`needs_input`、`needs_choice`、`needs_review` 和 `awaiting_gm_review` 必须独立显示。

- `needs_input`：补充行动条件或规则输入；
- `needs_choice`：玩家在候选中作出选择；
- `needs_review`：规则后果无法映射、世界目标不合法或需要主持确认；
- `awaiting_gm_review`：插件已经返回结果，但主持人尚未批准提交。

这些状态都不应显示失败骰点，也不应推进世界时间。

## 十、待选择与行动窗口

待选择是客户端重要的交互入口，但不是世界事实。

### 10.1 待选择卡

待选择卡至少包含：

- 选择提示；
- 当前场景；
- 选项及其公开说明；
- 选择的受众；
- 是否有时限；
- 由哪次行动产生；
- 当前选择 revision；
- 选择后是否会继续裁定或仅改变场景。

用户选择前，客户端不能显示某个选项已经发生的后果。选项文字可以说明“可能承担风险”，不能把未选分支的事实泄露出来。

### 10.2 选择提交

选择请求带 `choice_id`、当前 scene revision 和幂等键。成功后：

1. 读取选择结果；
2. 重新读取战役与场景投影；
3. 若仍有 open choice，保持 `waiting`；
4. 若选择仅完成当前等待，回到 `active`；
5. 不自动替用户声明下一行动。

选择重复提交返回原结果。客户端不需要“自动续接行动”按钮；用户可以在新局面上再次声明行动。

## 十一、世界时间与规则时间

客户端要同时显示两种时间，但不能把它们画成一个钟：

| 时间 | 所有者 | 客户端含义 |
|---|---|---|
| 世界时间 | WorldRuntime | 当前世界事实所在时刻、地点和历史顺序 |
| 规则时间 | Campaign Runtime / 插件 | 回合、轮次、阶段、行动窗口、进度时钟 |

规则回合结束不自动推进世界时间。只有裁定结果中有合法 `world_time_request`，并且联合提交成功，客户端才表达“世界时间已消耗”。

若一次行动包含时间消耗，结果中分开展示：

```text
规则节拍：阶段 / 回合已推进
世界时间：已前进 N 秒，原因为……
事实结算：时间前移后产生的世界结果
```

非法时间请求进入待审，不在客户端静默忽略，也不显示时钟已移动。

## 十二、认知、受众与信息安全边界

客户端至少维护以下视角：

```text
GM_ONLY
  主持依据、完整规则裁定、世界实情引用（若调用方有权限）

PUBLIC_PARTY
  队伍明确公开的材料

CHARACTER:<id>
  指定玩家角色可知的材料

PLAYER:<id>
  未来多人扩展的玩家受众，首版仅保留协议位置

NPC:<id>
  规则或主持流程需要的 NPC 视角材料
```

首版单用户也不能把 `character:<a>` 和 `character:<b>` 自动合并。客户端控制“当前查看谁”，但不凭用户身份提升受众。

客户端要做的最后一道显示闸门：

1. 读取 Campaign Runtime 的受众投影；
2. 读取 WorldRuntime 的角色认知投影；
3. 合并前确认材料受众和观察者都允许；
4. GM 表达只使用允许材料；
5. 玩家文本中不出现 GM 私有 resolution、未获知事件、其他角色私密内容或 opaque state 私有字段。

客户端不建立第二套秘密复制库。披露、转述、认知变化和回滚仍使用既有 WorldRuntime / Session 语义。

## 十三、GM 直接变化

GM 直接变化是主持工具，不是玩家行动的快捷绕过。

入口要求 GM 明确选择：

```text
来源：GM 直接裁定
变化目标：已登记世界实体
变化类型：公共闭集中的结构化类型
操作：set / change / reveal / advance / ...
受众：public_party / character:<id> / gm_only
原因或主持备注
幂等键
```

客户端调用 `trpg.gm.change`，让 Campaign Runtime 与 WorldRuntime 走和玩家行动相同的校验、版本和联合提交边界。客户端不生成虚假骰点，不把 GM 备注写成玩家角色已知事实。玩家模式的行动结果可以自动进入联合提交；GM 直接变化永远由 GM 明确提交。

GM 直接变化结果必须显示：

- 已提交 / 被拒 / 待审；
- 来源为 `gm_declaration`；
- 哪些玩家视角会看到；
- 是否推进世界时间；
- 当前场景是否需要重新读取。

故事意图不走这个入口。故事意图只能形成主持候选，待 GM 明确转成结构化变化后才可提交。

## 十四、战役恢复、分支与版本阻断

### 14.1 恢复

客户端恢复战役时按以下顺序：

1. 读取 campaign info；
2. 检查战役状态和规则版本；
3. 读取当前 scene view；
4. 读取开放 choice；
5. 读取未完成 action；
6. 根据状态显示继续、补充、重试或只读入口；
7. 不自动重跑随机裁定；
8. 不自动替玩家选择。

`resolving` / `snapshotting` 进入 `interrupted` 后，客户端给“显式重试”而不是“继续上一次骰点”的文案。`reviewing` 重新显示待提交结果，不重跑插件。`committing` 查询联合提交账本，确认是否已经提交。

### 14.2 分支

分支是主持人 / 创作者工具，不是玩家界面上的普通撤销。

客户端在分支操作前显示：

- 来源提交；
- 新时间线不会接收源线之后的行动、选择和规则状态；
- 未提交 action、开放 choice 和插件进程不会被带入；
- 用户必须明确选择新线是否激活；
- 原线仍保留。

客户端不在本地复制场景或规则状态，分支由 WorldRuntime / Campaign Runtime 创建后再重新读取。

### 14.3 回滚

回滚是覆盖历史的破坏性操作，只在主持 / 创作权限下出现。确认内容至少说明：

- 哪些行动、选择、规则状态和场景派生会失效；
- 已投递的外部表达不能保证消失；
- 运行世代会变化，迟到裁定会失效；
- 回滚后需要重新读取当前场景；
- 若跨过战役创建点，战役可能进入 `orphaned` / `blocked`。

回滚完成后客户端清空旧场景缓存、旧待选择、旧行动草稿和旧结果展开状态，重新读取目标提交处的权威投影。

### 14.4 规则版本阻断

插件声明版本与规则状态写入版本不兼容时，客户端显示：

```text
战役已暂停：当前规则插件不能安全解释这份规则状态。
可用操作：查看原因、导出、选择转换器、人工接受新版本、归档。
不可用操作：继续裁定、提交行动、假设状态已迁移。
```

人工接受新版本不是自动转换。客户端必须把它显示为主持人承担的明确决定，并保留记录。

## 十五、客户端与现有运行时的契约映射

客户端不增加旁路 API，优先消费当前已经存在的战役管理能力。

| 产品动作 | 现有运行时入口 | 客户端使用语义 |
|---|---|---|
| 新建战役 | `trpg.campaign.create` | 创建战役并可同时建立首场景 |
| 列出战役 | `trpg.campaign.list` | 战役选择页 |
| 查看战役状态 | `trpg.campaign.info` | 状态条、阻断、恢复 |
| 变更战役状态 | `trpg.campaign.status` | 暂停、恢复、归档、人工接受规则版本 |
| 打开场景 | `trpg.scene.open` | GM 建立新可行动局面 |
| 读取场景 | `trpg.scene.view` | 场景面、队伍面、受众投影 |
| 声明行动 | `trpg.action.declare` | 从自然语言形成行动草稿 |
| 确认 / 修改行动 | `trpg.action.confirm` | 确认卡提交 |
| 放弃行动 | `trpg.action.abandon` | 取消未完成行动 |
| 调用规则插件 | `trpg.action.resolve` | 仅对已确认行动做裁定；返回后停在待提交 / 待审 |
| 联合提交 | `trpg.commit` | 规则状态、世界后果和场景转换一起固化 |
| 选择分支 | `trpg.choice.select` | 处理当前 open choice，不自动声明下一行动 |
| 读规则状态 | `trpg.rule_state.read` | 主持视角只读 revision / 版本，默认不向玩家显示正文 |
| GM 直接变化 | `trpg.gm.change` | 不伪造骰点的结构化主持提交 |
| 恢复在途状态 | `trpg.recover` | 重启 / 恢复页的状态整理 |
| 规则版本迁移 | `trpg.campaign.migrate` | 主持人显式转换，不静默变更 |
| 世界一致视图 | `runtime.scope.inspect` / `runtime.snapshot.read` | 当前世界时刻、revision、公共快照 |
| 角色视角 | `runtime.cognition.project` | 玩家 / 角色可见事实与未知 |
| 世界主体状态 | `runtime.subject.state.read` | 只在受众允许且插件声明公开时显示 |
| 世界历史 | `runtime.history.read` | 受限复盘引用，不做全量内部浏览器 |

现有实现证据表明：

- `CampaignRuntime.view()` 已经能返回 campaign、scene、当前未闭合行动、recent action、open choices 和规则状态 revision；
- `action_view()` 对玩家面隐藏原始 resolution，对 `gm_only` 才返回；
- `scene_view()` 已按 audience 裁剪公共材料、可行动作与 private views；
- `trpg.action.resolve` 的战役路径只保存裁定结果，不写世界；
- `trpg.commit` 是规则状态 patch、世界后果、场景转换和时间请求的联合提交入口；
- `tests/test_trpg_campaign.py` 已用真 WebSocket、真 SQLite 和真实插件子进程验证确认闸、联合提交、幂等、待选择、恢复、版本阻断和时间消耗。

这些是客户端可以依赖的运行时事实，不等于客户端已经存在。当前桌面前端没有 `trpg.*` 消费者，因此本文设计的是缺失的应用层。

## 十六、最小端到端流程

### 16.1 玩家行动

```text
1. 用户进入战役
2. 客户端读取 campaign + scene + 当前活动玩家角色的 audience projection
3. 客户端显示当前局面和可行动入口
4. 用户输入自然语言
5. 客户端形成行动声明草稿
6. 用户确认或修改
7. 客户端调用 trpg.action.declare / confirm
8. Campaign Runtime 保存唯一 action revision
9. 客户端调用 trpg.action.resolve
10. 插件返回 resolution / rule_state_patch / consequences / scene_transition
11. 客户端显示「裁定完成」；合法结果自动调用 trpg.commit
12. 联合提交成功后读取新的 scene view 与角色视角
13. 客户端表达结果并交还下一选择
14. 联合提交失败则保留 reviewing / conflict / stale / needs_review 的真实状态
```

### 16.2 待选择

```text
1. 联合提交返回 open_choices
2. 战役进入 waiting
3. 客户端把 choice 卡置于场景首位
4. 其他关键行动入口锁定
5. 用户选择一个合法选项
6. 调用 trpg.choice.select
7. 重新读取 campaign + scene
8. 仍有 open choice → 继续 waiting
9. 没有 open choice → 回到 active
10. 用户自行声明下一行动
```

### 16.3 GM 直接变化

```text
1. GM 在主持面选择“直接变化”
2. 填写结构化目标、变化、受众和幂等键
3. 客户端预览玩家视角
4. GM 明确提交 `trpg.gm.change`
5. WorldRuntime / Campaign Runtime 共同校验
6. committed → 重新读取场景与玩家视角
7. needs_review / rejected → 停在主持面，不进入玩家已发生表达
```

### 16.4 OC / TRPG 共用世界

```text
同一实例 / 时间线
  ├─ OC 故事层读取角色认知并表达角色生活
  └─ TRPG 客户端读取战役场景、角色认知并提交行动后果

两条路径共享：世界事实、世界时间、认知、说法、版本和提交
两条路径不共享：用户输入语义、行动确认、规则状态、GM 表达和场景流程
```

TRPG 行动造成的世界后果可以被 OC 角色之后通过合法认知路径感知；OC 对话不会因为文本里提到一件事就自动成为 TRPG 行动或世界事实。

## 十七、首版实现分期

### C0：客户端只读场景壳

目标：先证明客户端能消费真实 Campaign Runtime。

- 战役选择；
- 场景 view；
- 受众切换；
- public facts / risks / pending choices；
- action / recent 投影；
- `gm_only` 与玩家面字段隔离；
- 空战役、冻结、waiting、blocked、archived 空态。

不允许在 C0 中把“聊天输入框”直接接成行动提交。

### C1：单玩家行动闭环

- 自然语言行动草稿；
- action 声明、确认、修改、放弃；
- 真实插件裁定；
- reviewing / needs_review / plugin_failed 状态；
- 联合提交；
- 成功、失败、无变化和新场景；
- action_id / action_revision / idempotency_key 重试语义。

### C2：待选择、时间和恢复

- waiting 闸门；
- choice 展示与选择；
- 规则时间 / 世界时间双轨展示；
- 时间消耗结果；
- 核心重启恢复投影；
- interrupted / committing / stale 的显式恢复。

### C3：GM 辅助

- GM 受众；
- 原始裁定的受限展开；
- 玩家视角预览；
- GM 直接变化；
- needs_review 工作区；
- 战役暂停、归档、版本阻断和人工接受。

### C4：队伍与差异化规则视图

- 单用户多角色切换；
- public_party / character 受众隔离；
- 插件现有公开摘要的差异化展示；
- 不同规则插件的差异化行动表单 / 结果摘要；
- 以 CoC 作为第二个差异化规则插件，验证客户端基础流程没有把第一套规则的属性、资源或骰点字段写死。

### C5：主持创作与分支

- 从提交创建战役分支；
- 回滚 / 导出前的风险确认；
- 场景草稿与主持候选；
- 结构化结果的人工表达入口；
- 只在真实使用中证明有需求后再增加地图、战斗网格、自动主持或模型生成 GM 文本。

## 十八、产品不变量

1. 行动声明不是世界事实。
2. 未确认的关键行动不调用会改变规则状态或世界状态的裁定链。
3. 玩家模式下合法裁定可以自动进入联合提交；GM 直接变化和 GM 待审结果必须由 GM 明确提交。
4. 插件返回成功不等于规则状态或世界后果已提交。
5. 规则状态 patch 与必要世界后果只能一起成功或一起失败。
6. 待选择不是世界事实，未选择分支不得进入玩家表达。
7. 一个行动 revision 只有一个确认版本；修改行动必须增加 revision。
8. 重试已处理幂等键只返回原结果，不重新扣资源、不重复写世界。
9. 重新裁定必须是显式的新行动版本，不能藏在普通重试里。
10. 客户端显示的世界事实必须来自 WorldRuntime 投影或已提交结果。
11. 客户端不复制世界真值、角色认知库或规则私有状态作为第二份权威。
12. GM 私有材料、其他角色私密信息和未获知世界事实不会进入玩家面。
13. 规则时间与世界时间分开所有、分开显示、分开提交。
14. 失败必须给出代价、信息、待补充条件、待选择或明确无变化。
15. 回滚 / 分支 / 版本迁移是主持或创作操作，不是普通玩家的撤销按钮。
16. 客户端不依赖某一套规则字段才能完成基础流程。
17. 客户端连接方式可替换，不能改变上述行动、视角、提交和恢复语义。

## 十九、行为验收

### C0 场景投影

- 读取真实战役后，客户端能显示当前场景、公开事实、风险、参与者、可行动作和 open choice。
- 玩家受众看不到 `gm_only` resolution、其他角色私密材料或未获知世界事实。
- `waiting` 战役只显示对应 choice 入口，关键行动输入被锁定。
- `blocked` / `paused` / `archived` 有明确只读状态，不显示可提交按钮。
- 当前场景 revision 变化后，旧客户端投影被丢弃并重新读取。

### C1 行动闭环

- 用户自然语言能形成行动者、目标、方法、意图和风险的确认卡。
- 用户修改行动后 action revision 增加，旧 revision 不会进入裁定或提交。
- 用户放弃行动后不调用有状态插件、不写规则状态、不写世界后果。
- 未确认行动无法进入 `trpg.action.resolve`。
- 真实插件返回裁定后，玩家模式自动发起合法的 `trpg.commit`；GM 模式停在 reviewing，等待 GM 操作。
- `trpg.commit` 成功后，客户端读取新的 scene view，再显示世界后果和下一局面。
- 联合提交失败时，客户端不显示规则状态或世界后果已经成立。

### C2 失败、选择与恢复

- 插件崩溃、超时、非法 JSON 时，客户端显示 plugin_failed / interrupted，不猜骰点结果。
- 非法世界后果进入 needs_review / rejected，规则状态也不落半条。
- 相同幂等键重试返回原 joint commit，不重复扣资源或写事件。
- open choice 只允许合法选项；重复选择返回原结果。
- 世界时间请求非法时，客户端不移动世界时钟。
- 核心重启后 resolving 行动进入 interrupted，committing 按账本判断，不重跑随机裁定。
- 规则版本不兼容后，客户端阻止继续裁定并提供转换 / 人工接受 / 只读出口。

### C3 GM 与视角

- GM 直接变化标记为 `gm_declaration`，不伪造骰点。
- GM 直接变化与玩家行动使用同一个世界校验和提交边界。
- 玩家预览不包含 GM 私有变化依据。
- 规则原始 resolution 默认只对 GM 可见；玩家只看到允许公开的摘要。
- GM 选择故事意图时不会直接写入世界事实。

### C4 多角色与跨应用

- 同一用户控制多个角色时，切换角色只切换 actor / audience，不合并私密认知。
- 同一实例 / 时间线上的 TRPG 提交能被 OC 角色在合法认知路径上感知。
- 普通 OC 对话不会静默创建 TRPG action 或 WorldRuntime 事件。
- 使用第二个真实规则插件（CoC）时，客户端基础流程不要求读取第一套规则的属性、资源或骰点字段。

这些验收需要真实 Campaign Runtime、真实 SQLite、真实规则插件进程和真实客户端边界。只测试客户端 reducer、只调用纯函数或只让模型生成一段 GM 文本，都不能证明 TRPG 客户端闭环成立。

## 二十、定稿决策

1. **首版玩家范围**：单用户、单个活动玩家角色；多角色队伍和角色切换属于 C4。
2. **玩家行动提交**：用户确认行动一次；合法裁定由客户端自动发起联合提交，不重复要求玩家批准同一提交。
3. **GM 提交责任**：GM 直接变化、`needs_review`、争议结果和主持候选必须由 GM 明确提交或批准。
4. **公开裁定信息**：玩家默认看到结果等级、公开理由、公开代价和公开摘要；原始骰点 / 秘密难度 / 隐藏修正由插件受众决定，客户端不另造公开骰点协议。
5. **规则表单**：首版不增加通用插件能力声明协议，不制作通用角色表；行动先以自然语言为主，规则专属表单在 C4 按真实插件需要增加。
6. **GM 表达**：C0–C2 只表达结构化结果和主持人提供的文本，不引入 LLM GM 文本生成；模型表达属于 C5 候选，不是事实提交路径。
7. **差异化验证**：第二个真实规则插件选 CoC，用来验证客户端不依赖第一套规则的属性、资源或骰点字段。
8. **范围边界**：桌面连接、移动端承载和通道接线另行设计，不在本规范内展开。

### 两条实现口径（规范内部有张力，写明取哪一边）

1. **玩家面的「结果等级」**（§20.4 与 §4.2 / §8.3 之间）：现有插件协议里 `resolution` 没有公开标记，
   因此按 §8.3「先消费插件现有受众标记」处理——等级（`outcome` / `degree`）进 GM 面，
   玩家面用**已提交的公开世界后果 + 公开说法**表达「已经发生什么」。要让玩家看到等级，要么插件把摘要
   写成公开材料，要么由 Campaign Runtime 增加公开摘要字段（属运行时契约变更，不在客户端里发明）。
2. **「批准」的成立条件**（§7.1 `awaiting_gm_review` 一行）：只有**有裁定**的待提交状态
   （`reviewing` / `conflict` / `stale`）能批准；公共层判死的待审（`needs_review`，没有可提交载荷）
   只能**补充条件重跑裁定或拒绝**——客户端如实说明，不假装批准已发生。
