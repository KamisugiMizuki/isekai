# isekai 后续演进草案：完整异世界模拟与应用层分块

> 状态：草案 v0.1，未定稿
>
> 本草案不改变项目代码，也不替代现有 SPEC。定稿后应拆分并并入 `WORLD_RUNTIME_SPEC`、`EVENT_ENGINE_SPEC`、`NARRATIVE_LAYER_SPEC` 与 `TRPG_RULE_PLUGIN_SPEC`。

## 一、根目标

isekai 的根目标是构建一个持续运行的完整异世界模拟。

世界不依赖用户在线而存在，拥有自己的时间、地点、角色、社会关系、资源、事件、生活过程、历史和因果后果。用户可以通过不同应用方式进入这个世界：

- 通过 OC 故事层，与世界中的角色交流并逐步发现世界；
- 通过 TRPG 场景，以玩家行动、规则裁定和主持表达参与世界；
- 未来可以通过其他客户端或应用方式观察、影响或讲述同一个世界。

TRPG 不是项目根目标，也不是 WorldRuntime 的唯一消费者。OC 故事与 TRPG 是并列应用场景，共同依赖同一个世界模拟。

## 二、总体结构

```text
                         ┌──────────────────────┐
                         │      OC 客户端         │
                         └──────────┬───────────┘
                                    │
                         ┌──────────▼───────────┐
                         │      OC 故事层         │
                         │  认知过滤 · 叙事表达   │
                         └──────────┬───────────┘
                                    │
┌──────────────────┐      ┌─────────▼──────────┐      ┌──────────────────┐
│   TRPG 客户端     │─────▶│    WorldRuntime     │◀─────│   其他应用场景    │
└────────┬─────────┘      │   完整异世界模拟    │      └──────────────────┘
         │                └─────────▲──────────┘
         ▼                          │
┌──────────────────┐                │
│  TRPG 规则程序    │────────────────┘
│  规则裁定与规则态 │
└──────────────────┘
```

数据方向不是“TRPG 驱动 WorldRuntime”，而是所有应用共同读写同一个世界。TRPG 规则程序只负责把某套规则下的行动转成世界可接受的变化请求。

## 三、四个边界

### 3.1 WorldRuntime

WorldRuntime 是世界事实与世界演化的唯一所有者。

负责：

- 世界时间、地点和空间关系；
- 世界实体、角色、群体、组织、资源与关系；
- 角色生活、行动、计划和行动后果；
- 世界事件、因果链、持续状态和状态变化；
- 事实、公共说法、角色认知及信息传播；
- 世界分支、历史提交、回滚、重放和一致性；
- 向不同应用提供受约束的世界视图；
- 接收外部应用提交的结构化行动结果并验证、固化。

不负责：

- 某套 TRPG 的骰子、属性、职业、技能或战斗规则；
- OC 角色应该说什么；
- TRPG 客户端如何展示规则或组织玩家流程；
- 把任意外部文本直接写成世界事实。

WorldRuntime 的判断标准是：某个能力是否属于“这个世界无论由谁观察都应该成立的事实或演化”。属于，就进入 WorldRuntime；只属于某种玩法，就留在应用层。

### 3.2 OC 故事层

OC 故事层是世界的角色表达与叙事消费层。

负责：

- 根据角色当前认知、经历、处境和性格生成表达；
- 将世界事实转化为对话、回忆、传闻、观察和故事片段；
- 保持角色不知道不应知道的内容；
- 让世界变化通过角色生活和叙事到达用户；
- 在不改变事实的前提下选择措辞、视角、节奏和表达方式。

不负责：

- 私自创造未被 WorldRuntime 固化的世界事实；
- 越过认知边界读取世界全量真相；
- 代替规则程序裁定 TRPG 行动；
- 用角色台词反向伪造世界事件。

OC 故事层可以提出角色意图或行动候选，但实际世界变化必须返回 WorldRuntime 验证和固化。

### 3.3 TRPG 规则程序

TRPG 规则程序是某一套具体 TRPG 规则的实现边界。每套规则可以拥有独立程序或独立规则包。

负责：

- 角色卡中的规则属性、技能、职业、资源和能力；
- 骰点、修正、难度、对抗、成功等级和随机种子；
- 回合、行动、反应、战斗顺序等规则语义；
- 伤害、治疗、状态、技艺、地形和召唤物的规则裁定；
- 规则专属的规则态、重放信息和审计数据；
- 将规则裁定转换为通用的世界行动或世界变化请求。

不负责：

- 直接修改 WorldRuntime 数据库；
- 定义世界的通用时间、历史、实体或认知真值；
- 假设所有 TRPG 都拥有相同的属性、回合、资源或战斗模型；
- 要求 WorldRuntime 认识某一套规则的私有字段。

规则程序不是普通通道插件。它可以通过独立进程和协议运行，也可以在其他宿主中运行，但不能依赖 Tauri、OC 客户端或某个具体 UI。

### 3.4 TRPG 客户端

TRPG 客户端是玩家、主持人和规则程序之间的应用编排层。

负责：

- 展示世界场景、角色状态和玩家可见信息；
- 收集玩家声明、目标、行动和选择；
- 调用对应规则程序并展示规则结果；
- 组织回合、场景、战斗、暂停和主持流程；
- 将规则结果提交给 WorldRuntime；
- 读取 WorldRuntime 固化后的世界变化，交给 GM 或叙事表达层。

不负责：

- 把客户端自己的显示状态当成世界真值；
- 绕过 WorldRuntime 直接写入世界；
- 把某套规则的界面需求强加给 OC 故事层；
- 把 GM 的自然语言直接当成已发生事实。

## 四、真值归属

| 内容 | 唯一所有者 | 其他模块的关系 |
|---|---|---|
| 世界时间与世界历史 | WorldRuntime | 读取或提交受约束变化 |
| 世界实体、地点、组织、资源 | WorldRuntime | 通过世界视图访问 |
| 角色认知与已发生经历 | WorldRuntime | 故事层消费，客户端展示 |
| 角色表达与叙事措辞 | OC 故事层 / GM 表达层 | 不反向成为事实 |
| 规则属性、骰点、职业和技艺 | 对应 TRPG 规则程序 | 客户端展示，核心不解释 |
| TRPG 场景和回合编排 | TRPG 客户端 | 调用规则程序和 WorldRuntime |
| 规则裁定审计信息 | 对应规则程序产生，WorldRuntime保存 | 仅用于审计、重放和表达 |
| 世界变化 | WorldRuntime | 必须经过统一校验与固化 |

## 五、统一交互链

### OC 故事链

```text
世界时间推进
  → WorldRuntime 产生或固化世界变化
  → 角色认知与经历更新
  → OC 故事层读取合法视图
  → 角色表达 / 故事片段
```

### TRPG 行动链

```text
玩家行动
  → TRPG 客户端组织请求
  → 对应规则程序裁定
  → 生成规则结果与世界变化请求
  → WorldRuntime 校验并固化
  → 更新世界、角色、认知和历史
  → TRPG 客户端 / GM 表达结果
```

TRPG 的“行动成功”不等于世界变化已经成立。只有 WorldRuntime 接受并固化的变化，才是世界事实。

## 六、后续改进方向

### 第一阶段：稳住世界真值边界

- 明确世界实体、地点、关系、资源和状态的通用表达；
- 让持续状态具有开始、持续、结束、清除和回滚语义；
- 将外部行动统一归入“行动请求 → 校验 → 世界变化 → 固化”；
- 保持现有时间线、事件、认知、叙事和版本能力不被 TRPG 特化。

### 第二阶段：补齐世界模拟能力

- 角色和其他主体的自主行动；
- 地点与空间关系；
- 资源持有、消耗、转移与恢复；
- 角色关系和组织关系的世界后果；
- 并行行动、冲突和行动顺序；
- 持续效果、条件触发和因果链；
- 世界离线推进、补算、重放和确定性复现。

这些能力必须能同时服务 OC 和 TRPG，不能以某套 TRPG 的术语命名。

### 第三阶段：完善 OC 故事层

- 让角色表达稳定消费 WorldRuntime 的认知视图；
- 区分亲历、听闻、传闻、误解和世界真相；
- 让世界事件通过角色生活、记忆和关系产生可见后果；
- 保持叙事层无事实写权限，所有事实变化回到 WorldRuntime。

### 第四阶段：完善规则程序边界

- 保持一套规则一套规则程序；
- 为规则程序提供稳定的行动请求和世界变化协议；
- 支持规则程序携带规则专属状态、随机种子和重放信息；
- 仅在第二套真实规则证明协议不足时扩展协议；
- 不为了提前支持所有 TRPG 而设计空泛的万能规则模型。

### 第五阶段：建设 TRPG 客户端

- 场景、地图、角色状态、行动声明和主持流程；
- 规则程序选择与规则结果展示；
- 世界事实视图与规则状态视图分离；
- GM 表达不越过 WorldRuntime 直接写事实；
- 支持从同一个世界实例中开启 TRPG 场景，并在场景结束后保留世界后果。

## 七、暂不做

- 不把 WorldRuntime 改造成某一套 TRPG 的战斗引擎；
- 不为每种规则复制一套世界时间、事件、认知和版本系统；
- 不把 OC 故事层和 TRPG 客户端合并成一个表达层；
- 不先制作完整 TRPG UI，再反推世界模型；
- 不把规则书自然语言批量自动编译成可信规则代码；
- 不在没有第二套真实规则验证前扩展复杂的通用规则抽象。

## 八、设计不变量

1. 同一个世界事实，无论由 OC 故事层还是 TRPG 客户端观察，都来自同一个 WorldRuntime。
2. 规则程序可以替换，世界真值不能因此换一套存储和历史。
3. OC 故事层可以改变表达，不可以绕过 WorldRuntime 改变事实。
4. TRPG 客户端可以组织流程，不可以把界面状态当成世界真值。
5. WorldRuntime 不需要理解具体 TRPG 的骰子、职业或技艺名称。
6. 规则结果只有经过 WorldRuntime 校验并固化，才会成为世界后果。
7. 世界模拟能力的新增必须能说明如何同时服务至少一个 OC 场景和一个 TRPG 场景；否则暂不进入核心。

## 九、草案后的决策点

定稿前需要确认：

- 是否将“资源、持续状态、主体行动、空间关系”作为 WorldRuntime 下一阶段的四个优先方向；
- TRPG 场景是否直接运行在世界时间线上，还是允许建立临时场景时间；
- TRPG 中的规则角色与世界中的长期角色如何绑定；
- TRPG 规则造成的伤害、死亡、地形和资源变化是否全部持久化到世界；
- OC 故事层是否允许提出行动候选，以及候选被接受时采用何种审批边界。
