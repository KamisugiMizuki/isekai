## 一、项目定位与背景

### 1.1 背景与问题定义

#### 现有基础

现有 Veranima Companion 已实现相当完整的角色陪伴能力：QQ 私聊主通讯、长期记忆（SQLite + FTS5 + 向量检索）、虚拟日程与昼夜节律、有限虚拟空间与地点池、角色卡 V3、PAD 人格与关系状态。这意味着**角色层**已经基本可用。

#### 核心问题

现有系统缺少的是**角色所生活的那个世界**。角色有日程、有地点、有记忆，但这些记忆和日程的**背景**——这个世界的历史是什么、有哪些重要事件发生过、社会结构如何、文化特征是什么——没有独立的、可被探索的载体。

用户在对话中问“你们那里最近有什么大事吗”，角色无法给出一个有世界观纵深的回答，因为世界本身没有被建模。

#### 问题的本质

这不是一个“角色缺少设定”的问题，而是一个**世界观缺少独立运行机制**的问题。现有的世界信息如果只是写在 prompt 里，它是静态的、被动的、不可探索的。本项目要做的是一个**世界模型**，角色生活其中，用户通过角色对话进入其中，碎片化地发现其中内容。

### 1.2 愿景与总体目标

#### 愿景

创建一个**自洽的、持续运行的、可被碎片化发现的异世界**。这个世界不依赖用户在线而存在。用户每次与角色对话，都是在“探访”一个一直在运转的世界，而不是“启动”一个对话场景。

#### 总体目标

| 层级 | 目标 |
|---|---|
| **短期（MVP）** | 世界时钟与系统时间同步运行；角色在世界中的行为产生事件；事件被记录并可被对话引用 |
| **中期** | 世界拥有一套最小可用的“历史-人文-事件”设定层，用户可通过多轮对话逐步拼凑出这些设定 |
| **长期** | 世界具备自演化能力：世界状态因角色行动和内部逻辑而持续变化，新设定从已有设定中“长出来”，而非预写 |

### 1.3 项目定位

**项目代号：isekai**

这是一个**独立于 veranima-companion 的新项目**，包含自己的聊天功能，不以原项目为运行依赖。原项目作为设计参考、资产来源和理念基础，但新项目独立仓库、独立部署、独立演进。

核心定位：

> 一个支持多世界设定、可由用户修改、可由 AI 根据描述自动生成世界包的虚拟世界对话系统。用户作为世界外存在，通过角色特有的双向联络方式，与生活在不同世界中的虚拟角色持续对话，并通过碎片化叙事逐步拼凑出该世界的历史、人文与重要事件。

关键词：

- 独立项目
- 内建聊天功能
- 世界设定可插拔、可修改
- AI 辅助生成世界设定
- 现实时间与世界时间可调倍率同步（默认 1:1）
- 角色认知软约束
- 用户位于世界外
- 碎片化叙事

### 1.4 独立项目策略

#### 与原项目的关系

- 新项目独立仓库、独立部署、独立演进。
- 原项目作为设计参考与资产来源。
- 可选择性移植或重写：角色卡、记忆、PAD、关系状态、日程等。
- 不直接依赖原项目运行。

#### 新项目包含

- 内建聊天功能
- 世界设定模块
- AI 世界包生成
- 世界时钟
- 角色认知接口
- 事件日志
- 碎片化叙事分发

#### 新项目不包含

- 图形化世界地图（总设计层面不包含）
- 多用户共享世界
- 完整世界编辑器 UI（初期可用文件/配置编辑）
- 重写原项目全部功能
- 追求世界规模

### 1.5 设计理念：碎片化叙事的结构性保证

#### 碎片化叙事的结构性保证

碎片化叙事的核心不是“把信息拆成碎片”，而是**信息在时空中的自然分布**。在本项目中，这意味着：

- 角色知道的世界信息，取决于角色**在世界中的位置和经历**。
- 同一世界的不同角色，可能知道不同的事。
- 角色对世界的认知是**局部的、有视角的**，而非全知的。
- 用户通过**与不同角色对话、在不同时间对话、询问不同话题**，逐步拼凑出世界的完整图景。

这需要世界层提供一个**角色认知接口**：给定角色 ID 和查询主题，返回该角色“应该知道”的世界信息子集。认知范围由角色在世界中的经历（去过哪里、见过谁、经历过什么事件）决定。

## 二、核心设计原则

### 2.1 收敛声明

总设计已收敛；本纲只保留**原则级结论**与跨模块机制。模块级细则不在本文展开——细则的现行归属见 §四 模块表与 §2.3。

### 2.2 核心设计原则

1. **独立项目**：独立仓库、独立部署、独立演进；不依赖原项目运行（原项目 = 设计参考、资产来源）。
2. **世界为主体，角色为表达面**：世界是独立运行的数据面；角色说的每句话由其处境、经历与认知决定。
3. **用户在世界外**：用户通过角色的双向联络方式与其对话，是世界的观测者，不是世界成员。
4. **世界不依赖用户在线**：世界时钟独立推进；应用不在时世界照常运转，重开时按确定性规则追赶（补算）。
5. **碎片化叙事的结构性保证**：认知接口按角色返回信息子集（软约束为默认）；同一世界不同角色知道不同的事；碎片化不靠提示词伪装。
6. **双轨内容**：世界内容分「实情层 / 公共叙事层」；角色只使用经认知接口获得的说法与自身经历，不直接读取实情层——误解与传闻是设计素材。
7. **世界包可修改、实例锁死**：世界包是模板（可修改，仅保留最新版）；实例创建即设定锁死、与世界包脱钩；角色集合可在运行期通过补卡扩充，公理与既有角色卡不可改。
8. **修改走「新时间线」**：在既定公理内改变局势 = 引入世界事件 + 创建新时间线，不改写原线过去；修改锁定公理或角色卡则须编辑模板后创建新实例。版本管理（提交 / diff / 回滚 / 压缩）只作用于世界运行状态。
9. **黑箱**：实例内部数据（事件、角色状态、记忆）不可见、不可编辑；世界内容只通过当前查看的激活线时钟与对话呈现。必要的名称、提交关系、运行状态等管理元数据可见，不开放内部快照浏览。
10. **AI 生成、用户审定**：世界包与角色卡均可 AI 生成；以用户确认的最终版本为准。
11. **性格 = 性格单元 + 置信度**：四种驱动（锚点 > 事件 > 对话 > 时间）；锚点保证跨时间线可辨识；驱动迁移隐式存在、不对用户可见。
12. **通道与生成解耦**：统一消息协议（UMP）；通道是适配器；内建聊天 = 官方通道客户端（随应用发行），第三方插件 = 独立进程（仅桌面端）。
13. **多端一致**：桌面端与安卓端共享协议与世界包生成器；不提供云同步，跨端同步由用户手动完成。
14. **确定性优先**：可复算机制（世界时钟、历法换算、事件骨架）实现为确定性函数——同一锁定设定、前序状态与固化输入，任何消费者同答案；不确定性只保留给语言生成环节，生成产物一旦采纳即固化，重放不重抽。

## 五、跨模块机制概览

（各节为速览，机制细则见对应 SPEC。）

### 5.1 世界与实例
- 世界包 = 本地模板文件（可修改，仅保留最新版）；世界实例 = 模板的一次实例化（创建后**设定锁死**、**内部黑箱**、与世界包**无关联**）。
- 实例的角色集合可在运行期**补卡**扩充：新角色一直存在（不凭空出现）、可自定义加入事件、可声明与既有角色已相识；补卡不修改既有设定与历史，可回滚退出。详见 `WORLD_SETTING_SPEC.md` §3.7。
- 世界包内容分「实情层 / 公共叙事层」**双轨**：角色经认知接口读取已获知说法与自身经历，实情层不越层泄漏（误解是设计素材）。
- 支持多世界；世界实例支持整体导入导出；**不支持世界合并**；全局不允许同名实例（不区分世界）。
- 详见 `WORLD_SETTING_SPEC.md`。

### 5.2 角色与性格单元
- 角色绑定世界；每个角色一张独立角色卡（含初始性格单元集合、认知边界、通讯方式）。
- 性格由「性格单元 + 置信度」构成；置信度控制生成、变化、消失；四种驱动方式：**锚点 > 事件 > 对话 > 时间**。
- 锚点驱动保证跨时间线的角色可辨识性；驱动迁移隐式存在、不对用户可见。
- 详见 `CHARACTER_CARD_SPEC.md`、`WORLD_RUNTIME_SPEC.md`（性格单元引擎）。

### 5.3 时间与版本
- 世界时钟独立推进：`当前世界时间 = 基准世界时间 + (现实流逝) × 倍率`；倍率按时间线独立、自然整秒生效、上限全局配置。
- 时间线 = 平行世界线（与 Git 分支的差异见 SPEC）；**仅激活时间线推进**，激活集合与当前查看线分开；版本管理只作用于世界运行状态。
- 本机退出后按原激活集合补算；冻结期不补算。回滚、重新激活和导入新副本须重新锚定现实时间，不能复用历史基准追赶回已撤销的进展。
- 提交 / 回滚（覆盖语义）/ diff 存储 / 自动压缩；对话上下文随时间线隔离；披露撤回 = 回滚。
- 详见 `WORLD_RUNTIME_SPEC.md`、`SESSION_CORE_SPEC.md`。

### 5.4 通道与平台
- 通道与内容生成解耦；所有通道遵循统一消息协议；第三方插件独立进程（仅桌面端）。
- 内建聊天 = 官方通道客户端，遵循同一协议、随应用发行、可拆为插件形态；安卓端始终内建、独立维护、**不开放插件**。
- 桌面壳（Tauri）：单窗口侧栏式（聊天 / 管理 / 设置）；默认托盘常驻，显式退出后下次启动补算。详见 `DESKTOP_SPEC.md`。
- 详见 `CHANNEL_PLUGIN_SPEC.md`、`ANDROID_SPEC.md`。

### 5.5 认知与碎片化叙事
- 认知默认为**软约束**：角色知道什么由设定、叙事处境、经历、信息渠道、对话历史共同决定，允许有依据的推测与主观解释；数据可访问范围始终隔离。与外界无通常信息交流的角色可声明硬约束，进一步限定来源。
- 世界层提供**角色认知接口**：按角色返回信息子集——碎片化是结构性的，不靠提示词伪装。
- 详见 `CHARACTER_CARD_SPEC.md`（约束规则）、`WORLD_RUNTIME_SPEC.md`（认知接口）。

### 5.6 事件与记忆
- 世界事件：确定性骨架（按世界包**必填密度档**抽样）+ 生成一次固化的文本；每件事件可带「公共说法层」；事件是主动发言与认知接口的共同上游。详见 `EVENT_ENGINE_SPEC.md`。
- 角色记忆：以**角色经历**为中心（三层数据域：对话原文 / 经历 / 规范记忆）；混合召回（全文 + 向量，向量化走远程 API）；随时间线版本化；黑箱不可见。详见 `MEMORY_SPEC.md`。

### 5.7 世界连续性与探索体验（2026-09-20 补充并入）
- **世界连续性**：事件效果须声明失效方式（随诱因结束 / 需合法事件解除 / 有条件的自然恢复）；仍有效的后果继续参与生活安排与后续前置条件，直到被解除或转为新常态。错误说法可以促成真实措施，澄清不自动撤销措施或抹去已发生的损失。详见 `EVENT_ENGINE_SPEC.md` §二 / §3.1。
- **人物连续性**：角色的打算与判断跨轮延续，并可在相关节点重议；获知、采信与表达取舍分层处理——听到不等于相信，相信不等于必须说出，且都不新增好感值、信任分或状态面板。详见 `WORLD_RUNTIME_SPEC.md` §十一 / §十三、`SESSION_CORE_SPEC.md` §4.4 / §5.1、`MEMORY_SPEC.md` §4.2 / §5.1。
- **理解连续性**：碎片化不止要求「片段可获得」，还要求「片段能相互解释」；互释属内容质量目标，不为保证拼完而补造真相，也不新增题材必填配额。详见 §6.1 阶段 3 验收。
- **按题材启用**：制度连续性与文化惯例演化在世界包声明时生效（`WORLD_SETTING_SPEC.md` §2.1–2.2、`EVENT_ENGINE_SPEC.md` §3.1 / §四），未声明即不适用；用户仍只通过对话感知世界，不新增内部状态展示面。

## 六、实施路径

### 6.1 阶段路线图

#### 阶段 0：独立项目骨架 + 核心进程 + 内建聊天客户端

- 新建独立项目
- 定义统一消息协议
- 实现内建聊天客户端（官方通道客户端，遵循统一消息协议；随桌面壳发行）
- 桌面壳与核心进程监督（sidecar 拉起 / 就绪握手 / 托盘常驻）
- 实现最小会话核心
- 定义第三方插件接口与文档（后置；见 `CHANNEL_PLUGIN_SPEC.md` 实施分期）
- 实现第三方插件进程隔离机制（后置；随外部通道需求启用）

验证：内建聊天客户端通过统一消息协议对话。

#### 阶段 1：世界包 + AI 生成 + 多世界 + 角色卡 + 导入导出

- 世界包文件结构定义
- 世界包生成器（表单式 + 对话式）
- 世界包文件可修改，仅保留最新版
- 世界包名称嵌入世界包快照，原始名称独立记录
- 从世界包文件创建世界实例
- 世界实例设定完全锁死，与世界包文件无关联
- 世界实例内部黑箱，世界时钟公开
- 世界实例导入导出（单一文件，不加密；导入时版本检查；不兼容拒绝导入；转换工具自动检测 + 用户确认；导入创建新实例；名称基于原始世界包名称自动生成 + 用户调整；全局不允许同名；重名自动追加 `_2` 等序号）
- 多世界支持
- 角色卡独立，支持用户自定义或 AI 生成 + 用户检查，仅保留最终确认版本

验证：修改世界包文件 → 创建新世界实例 → 旧世界实例不受影响；导入创建新实例且不影响原有实例；版本不兼容时拒绝导入；全局同名被拒绝；自动追加序号从 `_2` 起始；用户修改世界包名称不生效。

#### 阶段 2：世界时钟 + 倍率 + 角色认知 + 性格单元

- 世界时钟与系统时间同步，仅展示当前激活时间线时间
- 世界时钟倍率实现，每时间线独立，默认 1
- 倍率上限全局配置，默认 2592000，仅开发者可配置
- 倍率在自然整秒时更新生效，归属以输入时刻为准，整秒瞬间输入归属下一整秒
- 同一世界多角色共享世界时钟
- 角色状态存入世界运行层
- 性格单元置信度模型实现（四种驱动方式）
- 驱动迁移隐式存在，不对用户可见
- 认知接口按角色设定返回信息子集
- 角色集合扩充（补卡）：新角色一直存在、时间锚定补入时刻，个人史与初始知识按同一认知契约投影

验证：角色不会无理由知道全局设定；性格单元随四种驱动漂移；锚点驱动不归档；驱动迁移不可见；倍率在整秒生效且归属正确；倍率上限仅开发者可配置。

#### 阶段 3：事件日志 + 碎片化叙事

- 角色行动产生事件
- 事件写入日志
- 对话中按认知范围检索事件与设定

验证：用户通过 ≥ 5 轮对话获取 ≥ 3 条需拼凑的世界设定，且其中至少一处能与先前提到的片段相互解释（不是各自独立的设定名词）；角色不越过自身认知替用户公布答案。

#### 阶段 4：版本管理 + 时间线 + diff 存储

- 提交机制（全局统一自动 + 手动）
- 时间线创建、激活、冻结
- 多条时间线同时激活
- 角色状态 diff 存储与合并（含四种驱动的性格单元）
- 自动压缩（策略实现后确定）
- 回滚（覆盖语义）
- 对话上下文随时间线隔离

验证：创建多条时间线并同时激活；diff 合并正确；回滚覆盖原状态；对话上下文隔离；自动压缩生效；倍率随时间线独立。

#### 阶段 5：多角色披露机制

- 角色间披露与多角色端到端隔离验收（补卡能力自阶段 2 起可用；每角色独立角色卡，共享世界时钟）
- 对话历史隔离
- 用户主动披露
- 角色不主动表露
- 披露撤回通过回滚实现

验证：角色间默认隔离；披露后可见；回滚后披露消失。

#### 阶段 6：世界自演化

- 世界规则驱动事件生成
- 新设定从已有设定中推导
- 世界在无用户互动时也持续变化

验证：运行一周后，世界状态有自洽变化。

#### 阶段 7（可选）：安卓移植评估

- 评估跨平台方案
- 安卓端不开放插件，始终使用内建聊天实现，遵循统一消息协议，独立维护
- 安卓端与桌面端共享世界包生成器
- 安卓端支持世界实例创建、对话、世界包修改（表单式 + 对话式）、导入导出、倍率调整
- 评估运行时方案
- 跨大版本不兼容时先查找转换器；无转换器则提示使用兼容版本
- 无云同步，跨端同步手动完成

验证：核心功能在安卓端可运行；世界包修改可用；世界包生成器共享；倍率调整可用；导入导出可用；无插件接入入口；跨版本处理符合规则。

## 八、主要风险与应对

### 8.1 风险清单

| 风险 | 应对 |
|---|---|
| 性格单元置信度模型不稳定 | 阈值与步长可配置；人工抽检；实现后调参 |
| 驱动迁移规则导致性格突变 | 迁移渐进；隐式存在；人工抽检 |
| 锚点驱动单元不足以保证可辨识性 | 角色卡初始集合 + 演化连续性共同保证 |
| 锚点驱动单元无上限导致膨胀 | AI 在依据约束下判断新增，合并重复语义与来源；物理压缩不得删除或归档锚点 |
| diff 链过长导致状态读取性能下降 | 自动压缩；压缩策略实现后确定 |
| diff 合并实现复杂 | 阶段 4 前先用全量快照验证机制，再引入 diff |
| 极高倍率下世界状态快速膨胀 | 默认上限 2592000；仅开发者可配置；用户需注意；可通过版本管理回退 |
| 倍率归属边界不明确 | 以输入时刻为准；严格对齐自然整秒；整秒瞬间输入归属下一整秒；测试边界条件 |
| 世界实例黑箱导致用户无法排查问题 | 世界时钟公开；系统内部保证一致性 |
| 导出包不加密，用户查看内部数据 | 接受用户查看；内部数据仍不可编辑 |
| 用户修改世界包文件出问题 | 项目不提供支持；后果自负；已创建实例不受影响；名称修改不生效 |
| 跨版本导入不兼容 | 导入时检查；不兼容拒绝导入；建议使用兼容版本；不允许手动部分迁移 |
| 转换工具缺失导致旧实例无法使用 | 重大变更版本必须提供转换工具；无转换器则提示用兼容版本 |
| 无云同步导致跨端体验割裂 | 明确告知用户手动同步方式；导出导入流程简洁 |
| 导入创建新实例导致多端副本分散 | 界面明确提示；用户自行管理副本 |
| 不支持世界合并 | 用户需理解副本独立演化；无合并路径 |
| 同名实例冲突 | 全局不允许同名；自动追加 `_2` 等序号；用户改名仍需保证唯一 |
| 倍率上限被误改导致异常 | 仅开发者可配置；用户不可见配置入口 |
| 插件进程隔离在安卓上受限 | 安卓端不开放插件，规避该问题 |
| 插件接口版本变化导致兼容问题 | 版本号显式声明；提示 + 尝试 + 报错反馈 |
| 内建聊天拆分后桌面端与安卓端实现分叉 | 两端独立维护；共享协议与参考实现 |
| 回滚覆盖导致用户丢失进度 | 界面明确提示；要保留当前进展，先从当前提交创建保留时间线或整体导出，单独提交不等于备份 |
| 多时间线同时激活导致资源消耗 | 未激活时间线冻结；激活数可配置上限 |
| 多角色共享世界时钟导致状态复杂 | 世界时钟统一；角色状态独立存储 |
| 软认知约束被 LLM 绕过 | 认知上下文注入 + 后验一致性检查 |

## 附录 A：传统 roguelike 世界模拟的取舍与保留方向

> 性质：判断记录（2026-09-19 讨论整理）。不新增阶段、不改变任何 SPEC 义务；涉及归属的表述只用于防止实现时走偏。

### A.1 两作不是同一类东西

| 对象 | 「复杂」的真正来源 |
|---|---|
| Dwarf Fortress | 三段拼装：worldgen（离线批量、粗粒度实体模拟 → 冻结成历史）· 局部微模拟（在格子上直接渲染）· legends（历史查询层）。玩家感到的厚度主要在**记录**，而非**智能**。 |
| Elona | 世界几乎不动：靠**不可逆后果**（NPC 死了就是死了）+ **固定物**（节庆、天气、随机事件）+ 玩法动词的互锁撑起故事量。不是模拟。 |

### A.2 对本项目的判断

- 引擎不可抄，数据模型与纪律可抄。本项目的设计形态等价于「worldgen + legends」，只是把 legends 的查询出口换成了角色的嘴。
- 开放世界游戏需要的四样（空间、玩家身体与动词、渲染粒度的状态、交互循环）全在**消费者侧**：新增它们不动世界引擎——引擎的对外契约（稳定指涉 + 事件日志 + 闭集效果）恰好是游戏层要读的东西。
- 贵的一半（时间基元、确定性、因果链、版本 / 回滚）已在设计内；便宜的一半现在也建不对，只应保证不阻断。

### A.3 三条可迁移的纪律

1. **历史在生成期批量产出，不在运行期逐 tick 长出来。**
   - 归属：世界包生成器（创建期一趟 pass）+ 事件规则复用；落在既有阶段（生成器随阶段 1、规则复用随阶段 3），不新增阶段。设计见 `WORLD_SETTING_SPEC.md` §3.6 与 `EVENT_ENGINE_SPEC.md` §三；初期口径与缺口已就近标注。
   - 这条**当前就到期**，不止服务游戏方向：§1.1 的「世界观纵深」与 §1.2「新设定从已有设定中长出来，而非预写」要的就是它。
   - 体量陷阱：历史 pass 的粒度不等于运行期密度（现为每历法日 0–5 件世界级事件），不能按跨度线性放大——十年就是万件量级。
   - 形态已定（2026-09-19）：创建期回填 + 既有条目的惰性展开；分档、口径与缺口见 `WORLD_SETTING_SPEC.md` §3.6。
2. **空间可以从种子推导，不必写进包里。** 实例创建已固化世界种子（见 `WORLD_SETTING_SPEC.md` §3.2）；种子 + 叙事地理 → 程序化地图是确定性纯函数。未来的地图不欠债，现在不写一行。
3. **玩家的动词才是乘数。** Elona 的世界几乎不动，是「玩家能做什么」撑起故事量。真做游戏时第一个要定的是动词集与代价——那是体裁设计，不是引擎设计。

### A.4 数据面上的两条不阻断

两条都对当前产品独立成立，游戏方向只是搭便车；过不了这个标准的「预留」一律往后放。

| 项 | 当前价值 | 现状 |
|---|---|---|
| 地点 / 组织 / 物件是可指涉实体，不是散文 | 碎片要能拼，靠的是共同指涉物 | 已定：实情 / 说法 / 实体 / 渠道稳定引用，**地点与重要物件按用途登记**（见 `WORLD_SETTING_SPEC.md` §2.2）。 |
| 事实保持骨架化、量化（规模 / 效果 / 有效期），文本单独固化 | 一致性校验靠它 | 已有（`EVENT_ENGINE_SPEC.md` §二「事实骨架」）。 |

- 若启动，需要改写的是交付面（聊天 → 渲染）、用户位置（世界外 → 世界内）、空间模块与动词集；不需要改写时间 / 事件 / 因果 / 认知 / 版本。
- 成本提醒：DF 是一个人干了二十年的产物。保留方向的正确成本是零；一旦开始为它省着花当前预算，它就是负收益。
