## 一、项目定位与背景

### 1.1 背景与问题定义

#### 现有基础

你已有的 Veranima Companion 已经实现了相当完整的角色陪伴能力：QQ 私聊主通讯、长期记忆（SQLite + FTS5 + 向量检索）、虚拟日程与昼夜节律、有限虚拟空间与地点池、角色卡 V3、PAD 人格与关系状态。这意味着**角色层**已经基本可用。

#### 核心问题

现有系统缺少的是**角色所生活的那个世界**。角色有日程、有地点、有记忆，但这些记忆和日程的**背景**——这个世界的历史是什么、有哪些重要事件发生过、社会结构如何、文化特征是什么——没有独立的、可被探索的载体。

用户在对话中问“你们那里最近有什么大事吗”，角色无法给出一个有世界观纵深的回答，因为世界本身没有被建模。

#### 问题的本质

这不是一个“角色缺少设定”的问题，而是一个**世界观缺少独立运行机制**的问题。现有的世界信息如果只是写在 prompt 里，它是静态的、被动的、不可探索的。你要做的是一个**世界模型**，角色生活其中，用户通过角色对话进入其中，碎片化地发现其中内容。

### 1.2 愿景与总体目标

#### 愿景

创建一个**自洽的、持续运行的、可被碎片化发现的异世界**。这个世界不依赖用户在线而存在。用户每次与角色对话，都是在“探访”一个一直在运转的世界，而不是“启动”一个对话场景。

#### 总体目标

| 层级 | 目标 |
|---|---|
| **短期（MVP）** | 世界时钟与系统时间同步运行；角色在世界中的行为产生事件；事件被记录并可被对话引用 |
| **中期** | 世界拥有一套最小可用的“历史-人文-事件”设定层，用户可通过多轮对话逐步拼凑出这些设定 |
| **长期** | 世界具备自演化能力：世界状态因角色行动和内部逻辑而持续变化，新设定从已有设定中“长出来”，而非预写 |

### 1.3 项目定位

**项目代号：Veranima World（暂名）**

这是一个**独立于 veranima-companion 的新项目**，包含自己的聊天功能，不以原项目为运行依赖。原项目作为设计参考、资产来源和理念基础，但新项目独立仓库、独立部署、独立演进。

核心定位：

> 一个支持多世界设定、可由用户修改、可由 AI 根据描述自动生成世界包的虚拟世界对话系统。用户作为世界外存在，通过角色特有的双向联络方式，与生活在不同世界中的虚拟角色持续对话，并通过碎片化叙事逐步拼凑出该世界的历史、人文与重要事件。

关键词：

- 独立项目
- 内建聊天功能
- 世界设定可插拔、可修改
- AI 辅助生成世界设定
- 现实时间与世界时间可调倍率同步（默认 1:1）
- 角色认知软约束
- 用户位于世界外
- 碎片化叙事

### 1.4 独立项目策略

#### 与原项目的关系

- 新项目独立仓库、独立部署、独立演进。
- 原项目作为设计参考与资产来源。
- 可选择性移植或重写：角色卡、记忆、PAD、关系状态、日程等。
- 不直接依赖原项目运行。

#### 新项目包含

- 内建聊天功能
- 世界设定模块
- AI 世界包生成
- 世界时钟
- 角色认知接口
- 事件日志
- 碎片化叙事分发

#### 新项目不包含

- 图形化世界地图（总设计层面不包含）
- 多用户共享世界
- 完整世界编辑器 UI（初期可用文件/配置编辑）
- 重写原项目全部功能
- 追求世界规模

### 1.5 设计理念：碎片化叙事的结构性保证

#### 碎片化叙事的结构性保证

碎片化叙事的核心不是“把信息拆成碎片”，而是**信息在时空中的自然分布**。在你的场景中，这意味着：

- 角色知道的世界信息，取决于角色**在世界中的位置和经历**。
- 同一世界的不同角色，可能知道不同的事。
- 角色对世界的认知是**局部的、有视角的**，而非全知的。
- 用户通过**与不同角色对话、在不同时间对话、询问不同话题**，逐步拼凑出世界的完整图景。

这需要世界层提供一个**角色认知接口**：给定角色 ID 和查询主题，返回该角色“应该知道”的世界信息子集。认知范围由角色在世界中的经历（去过哪里、见过谁、经历过什么事件）决定。

## 二、核心设计原则（最终版）

### 2.1 总设计收敛声明

本版是总设计的**收敛版本**。以下内容已在本轮确认完毕，不再作为待确认项：

- 倍率上限为全局配置，仅开发者可配置。
- 倍率上限默认 2592000。
- 同名实例自动追加序号从 `_2` 起始。
- 同名约束全局不区分世界。
- 世界包名称以系统记录的原始值为准，用户修改不生效。
- 跨大版本不兼容且无转换器时，仅提示使用兼容版本，不允许手动部分迁移。
- 倍率上限的配置方式、存储位置、生效范围等，属于模块设计，不在总设计层面展开。
- 世界包原始名称的存储位置、已删除实例的名称释放、用户手动操作导出包的边界等，属于模块设计，不在总设计层面展开。

**总设计层面不再新增待确认项。** 后续如需细化，进入模块设计阶段处理。

---

### 2.2 核心设计原则

1. 项目独立。
2. 聊天通道与内容生成解耦，通道为插件式适配器。
3. 世界包文件可修改，仅保留最新版；世界实例创建后设定完全锁死。
4. AI 生成，用户审定。
5. 用户在世界外。
6. 角色与世界高耦合。
7. 认知软约束为默认。
8. 时间同步是基础设施；世界时钟与现实时间存在可调倍率关系。
9. 世界设定初始确定，后续修改通过引入世界事件 + 创建时间线进行。
10. 版本管理作用于世界运行状态层面。
11. 仅激活时间线推进；允许同时激活多条时间线。
12. 角色性格由性格单元构成，置信度控制生成、变化、消失。
13. 性格单元有四种驱动方式：事件、对话、时间、锚点。
14. 锚点驱动是性格单元的一种驱动方式，不再有独立的锚点模型。
15. 对话上下文随时间线隔离。
16. 通道插件开放第三方开发，第三方插件作为独立进程运行（仅桌面端）。
17. 披露撤回通过时间线回滚实现。
18. 内建聊天窗口作为核心进程的一部分，遵循统一消息协议；拆分后仅保留插件版本。
19. 世界实例内部数据完全黑箱；世界时钟作为公开信息展示，仅展示当前激活时间线的时间。
20. 支持世界实例导入导出；导出包不加密，接受用户可能查看内部数据。
21. 安卓端不开放插件；安卓端支持世界实例创建、对话与世界包文件修改；支持表单式与对话式两种方式。
22. 项目不提供云同步服务，所有跨端同步由用户手动完成。
23. 驱动迁移隐式存在，不显式记录，不对用户可见。
24. 角色卡初始支持用户自定义或 AI 根据描述生成，AI 生成后需用户检查，仅保留最终确认版本。
25. 导入始终创建新世界实例，不修改或覆盖任何已有实例。
26. 内建聊天窗口拆分后，安卓端始终使用内建聊天实现，与桌面端插件版本并行；安卓端内建实现遵循统一消息协议；保持独立。
27. 不支持世界合并。
28. 世界时钟倍率在每一自然整秒时更新生效；倍率归属以用户输入时刻为准；若输入时刻恰为整秒，归属下一个整秒。
29. 安卓端与桌面端共享世界包生成器；当前版本生成的世界包保证在当前版本可运行；两端版本不同时按各自版本规则处理；跨大版本不兼容时先找转换器，无转换器则提示使用对应兼容版本运行。
30. 导出包包含世界包名称信息；导入实例名称基于此自动生成。
31. 倍率上限可扩展；默认上限 2592000；全局配置；仅开发者可配置。
32. 世界包名称嵌入世界包快照中；系统以原始名称为准，用户修改不生效。
33. 全局不允许同名世界实例，不区分世界。
34. 用户对导出世界包文件的修改，项目不提供任何支持，后果由用户自行承担；已创建的世界实例与世界包文件无关联。

## 四、世界设定模块

### 4.1 世界包（内容范围）

#### 世界包

世界设定以“世界包”为单位组织。一个世界包描述一个完整世界，包括但不限于：

- 世界背景与基本规则
- 时间体系与时间流速
- 地理范围与活动区域
- 社会结构、文化、信仰、科技/魔法水平
- 重要历史事件与当前局势
- 可出现的角色类型与角色模板
- 角色与用户之间的通讯方式及其限制
- 初始事件、传闻、未解之谜

总设计层面不定义具体字段，只确定：**世界包是结构化、可版本化、可被用户独立修改的模块。**

### 4.2 世界包生成方式

#### 两种生成方式并存

| 方式 | 说明 | 适用场景 |
|---|---|---|
| **表单式生成** | 用户按结构化字段填写世界设定 | 用户已有明确构想 |
| **对话式生成** | 用户用自然语言描述，AI 生成候选世界包 | 用户只有模糊想法 |

两种方式可混合：用户可先对话式生成，再表单式修改。

#### 表单式生成

提供结构化字段，用户逐项填写。字段覆盖：

- 世界背景与基本规则
- 时间体系
- 地理范围
- 社会结构
- 文化信仰
- 科技/魔法水平
- 重要历史事件
- 角色模板
- 通讯方式
- 初始事件与传闻

#### 对话式生成

用户输入自然语言描述，AI 生成候选世界包。生成结果：

- 结构化
- 可编辑
- 可版本化
- 需用户确认后生效

#### 生成原则

- 生成结果必须可编辑，不是黑箱。
- 生成结果需与已有世界包版本保持一致。
- 用户修改后，世界运行层按新版本推进。
- 世界包变更不追溯已发生事件，除非用户明确创建时间线分支或重置世界。

---

### 4.3 世界包与世界实例的区分

#### 上一版的理解偏差

V0.5 把“世界包创建后不可修改”理解为世界包文件本身不可修改。你的实际设想是：

- **世界包是本地文件。**
- **世界包文件可修改，仅保留最新一版。**
- **世界包文件作为模板存在，可被反复加载。**
- **用世界包创建世界后，该世界的设定被完全锁死，不允许任何修改。**
- 锁死的是**世界实例**，不是世界包文件。

#### 修订后的模型

| 对象 | 可变性 | 版本 | 说明 |
|---|---|---|---|
| **世界包文件** | ✅ 可修改 | 仅保留最新版 | 本地文件，作为模板 |
| **世界实例** | ❌ 创建后完全锁死 | 不适用 | 从世界包加载后冻结 |
| **世界运行状态** | ✅ 可变 | 版本管理 | 时钟、角色状态、事件日志 |

#### 生命周期

```
世界包文件（本地，可修改）
        │
        │ 用户选择加载
        ▼
世界实例（创建后设定完全锁死）
        │
        │ 时间线推进
        ▼
世界运行状态（版本管理，可提交、可回滚）
```

#### 设计含义

- 世界包文件是“世界的模板”，可以有多个，可独立修改。
- 世界实例是“某个模板的一次实例化”，实例化后设定冻结。
- 同一世界包文件可被多次加载，创建多个世界实例。
- 修改世界包文件不影响已创建的世界实例。
- 世界实例的设定修改：不允许。需要新设定则创建新世界实例。

---

### 4.4 世界包与世界实例：无关联原则

#### 无关联原则

- 世界包文件与世界实例之间**无关联**。
- 修改世界包文件不影响任何已创建的世界实例。
- 删除世界包文件不影响任何已创建的世界实例。
- 世界实例不记录其来源世界包文件的引用。
- 世界实例创建后，其设定完全自包含，不依赖外部文件。

#### 设计含义

- 世界包文件是“模板”，用完即弃。
- 世界实例是“成品”，自包含、自洽、锁死。
- 用户可以自由修改、删除、替换世界包文件，不影响已有世界。
- 用户如需基于修改后的世界包创建新世界，直接加载即可。

---

### 4.5 世界实例设定锁死

#### 规则

- 世界包文件加载并创建世界实例后，该世界的设定被**完全锁死**。
- 不允许任何修改，包括：
  - 世界背景
  - 地理范围
  - 社会结构
  - 文化信仰
  - 科技/魔法水平
  - 角色卡
  - 通讯方式
- 没有任何例外，没有“非语义修改”通道。

#### 修改世界设定的唯一路径

- 创建新世界实例。
- 新世界实例可使用修改后的世界包文件。
- 已创建的世界实例不受影响。

#### 与世界运行状态的区别

- 世界实例设定：锁死。
- 世界运行状态：可变，通过时间线演化。
- 区分：设定是“世界的公理”，运行状态是“公理下的历史”。

---

### 4.6 世界实例完全黑箱

#### 规则

- 世界实例创建后，其内部数据**完全黑箱**。
- 用户不可直接查看世界实例的内部数据。
- 用户不可导出世界实例的内部数据。
- 用户与世界实例的交互仅通过对话与版本管理操作进行。

#### 用户可操作的部分

| 操作 | 是否允许 |
|---|---|
| 与角色对话 | ✅ |
| 提交（自动/手动） | ✅ |
| 回滚 | ✅ |
| 创建时间线 | ✅ |
| 切换时间线 | ✅ |
| 激活/冻结时间线 | ✅ |
| 查看世界实例内部数据 | ❌ |
| 导出世界实例内部数据 | ❌ |
| 修改世界实例设定 | ❌ |

#### 设计含义

- 世界实例是自包含的、不可窥探的整体。
- 用户通过对话“体验”世界，而非“检查”世界。
- 世界的内部一致性由系统保证，不由用户验证。
- 黑箱设计强化了“世界是真实的”这一体验。

---

### 4.7 多世界与多角色

#### 支持层级

| 层级 | 支持 | 说明 |
|---|---|---|
| 多世界 | ✅ | 用户可拥有多个世界，各自独立 |
| 同一世界多角色 | ✅ | 同一世界可包含多个角色 |
| 同一世界角色切换 | ✅ | 用户可在同一世界内切换对话角色 |
| 同一世界角色间交互 | ❌（当前） | 未来开放世界方向再设计 |
| 跨世界角色共享 | ❌ | 角色绑定世界，不跨世界 |

#### 当前阶段约束

当前阶段设定为：**同一世界仅包含一个角色。** 这是简化实现的阶段性约束，不是架构限制。

架构上应预留：

- 世界与角色的一对多关系
- 角色切换时的会话隔离
- 未来角色间交互的扩展点

#### 切换语义

| 切换类型 | 影响 |
|---|---|
| 切换世界 | 会话切换到新世界的角色；世界时钟独立；状态独立 |
| 同一世界切换角色 | 会话切换到同一世界内另一角色；世界时钟共享；认知隔离 |

---

### 4.8 多角色角色卡

#### 修订内容

同一世界多角色时，**不同角色间应有不同的角色卡。**

#### 规则

- 每个角色拥有独立的角色卡。
- 角色卡包含身份、背景、活动范围、信息渠道、通讯方式、初始性格单元集合。
- 角色卡属于世界实例，创建后锁死。
- 不同角色的角色卡互不共享。
- 不同角色的角色状态独立演化。

#### 与时间线的关系

- 每条时间线持有每个角色各自的状态。
- 创建时间线时，各角色状态分别复制（通过 diff）。
- 同一时间线内，各角色状态独立演化。
- 角色间交互（未来）将基于各自状态进行。

---

### 4.9 多角色共享世界时钟

#### 规则

- 同一世界内的多个角色**共享同一世界时钟**。
- 世界时钟按时间线独立推进。
- 同一时间线下，所有角色处于同一世界时间。
- 不同时间线的世界时钟独立。

#### 设计含义

- 角色间的时间一致性由世界时钟保证。
- 用户在同一时间线下与不同角色对话时，世界时间是统一的。
- 角色状态随时间线隔离，但共享该时间线的时间基准。
- 未来角色间交互时，共享世界时钟是基础。

## 五、角色模型

### 5.1 性格单元与四种驱动方式

#### 四种驱动方式

| 驱动类型 | 强度来源 | 生成下限 | 生成上限 | 变化速率 | 衰减速率 |
|---|---|---|---|---|---|
| **锚点驱动** | 角色核心辨识特征 | 0.75 | 0.99 | 极慢 | 极慢 |
| **事件驱动** | 事件的重要程度 | 0.40 | 0.95 | 快 | 慢 |
| **对话驱动** | 对话的情感强度 | 0.15 | 0.70 | 中 | 中 |
| **时间驱动** | 时间跨度的长度 | 0.05 | 0.50 | 慢 | 快 |

**关键规则：**

- 锚点驱动的置信度上下限阈值最高，衰减最慢。
- 事件驱动次之，对话驱动再次，时间驱动最低。
- 阈值顺序：锚点 > 事件 > 对话 > 时间。

### 5.2 驱动强度

#### 强度计算

- 驱动强度 `s` 为 `[0, 1]` 连续值。
- 每类驱动有各自的强度计算方式，具体算法在实现阶段确定。
- 强度参与置信度更新公式：`c_new = clamp(c_old + Δ × s, 下限, 上限)`。

### 5.3 生成与更新规则

#### 生成规则

- 当某个性格单元首次被触发时，根据触发它的驱动类型，赋予一个初始置信度。
- 初始置信度落在该驱动类型的生成阈值范围内。
- 事件驱动生成的单元初始置信度更高，对话驱动次之，时间驱动最低。

#### 更新规则

每次驱动事件发生时，相关单元的置信度按以下公式更新：

```
c_new = clamp(c_old + Δ × 驱动强度, 该驱动类型的下限, 该驱动类型的上限)
```

其中：

- `Δ` 为变化步长，由驱动类型的“变化速率”决定。
- `驱动强度` 为 `[0, 1]` 的连续值，表示该次驱动的强弱。
- `clamp` 将结果限制在该驱动类型的阈值范围内。

**方向性：**

- 同向驱动（强化已有单元）：置信度上升。
- 反向驱动（削弱已有单元）：置信度下降，下降幅度由“衰减速率”决定。

### 5.4 驱动迁移（隐式）

#### 驱动迁移

- 驱动迁移**隐式存在**，不显式记录。
- 迁移是置信度范围变化的结果，不作为独立事件记录。
- 迁移**不对用户可见**。用户无法看到“某个性格单元从对话驱动固化为锚点驱动”。
- 用户仅通过角色表达感受角色的变化，不通过界面查看迁移过程。

### 5.5 驱动方式之间的转化

#### 驱动方式之间的转化

性格单元可以在驱动方式之间迁移：

| 迁移方向 | 触发条件 | 效果 |
|---|---|---|
| 事件 → 锚点 | 长期稳定、反复强化 | 阈值范围上移至锚点级 |
| 对话 → 锚点 | 长期稳定、反复强化 | 阈值范围上移至锚点级 |
| 时间 → 锚点 | 极长时间跨度 | 阈值范围上移至锚点级 |
| 事件 → 对话 | 事件影响减弱 | 阈值范围下移 |
| 对话 → 时间 | 对话影响消退 | 阈值范围下移 |

**迁移是渐进的，不是突变的。** 一个性格单元可以从事件驱动开始，经过长期稳定，最终固化为锚点驱动。

### 5.6 锚点驱动的特性

#### 锚点驱动的特性

- 不进入归档。
- 可新增，不跨时间线转移。
- 数量由 AI 决定。
- 依附时间线。
- 跨时间线起点由角色卡决定。

### 5.7 可辨识性与命名

#### 角色可辨识性的保证

- 角色卡中的初始锚点驱动单元集合（跨时间线共享，作为识别起点）。
- 各时间线中演化出的锚点驱动单元（可能不同，但演化有连续性）。
- 锚点驱动单元的极慢衰减。
- 性格单元的驱动迁移（长期稳定的单元固化为锚点）。

#### 命名

- 性格单元的命名与语义由 AI 自动生成。
- 锚点驱动的单元同样由 AI 自动生成。
- 不区分两套命名机制。

---

### 5.8 消失与归档

#### 消失与归档

| 驱动类型 | 是否可归档 |
|---|---|
| 锚点驱动 | ❌ 不可归档 |
| 事件驱动 | ✅ 可归档 |
| 对话驱动 | ✅ 可归档 |
| 时间驱动 | ✅ 可归档 |

- 归档单元不再参与性格表达，但保留在状态中。
- 归档单元可被后续驱动重新激活。
- 长期未被激活的归档单元可被压缩提交清理（策略实现后确定）。

---

### 5.9 消失规则（阈值与清理）

#### 消失规则

- 当 `c < 0.05` 时，该单元进入**归档状态**。
- 归档单元不再参与性格表达，但保留在状态中。
- 归档单元可被后续驱动重新激活，重新激活时从归档阈值开始上升。
- 长期未被激活的归档单元可被压缩提交清理（具体策略实现后确定）。

### 5.10 设计含义与待实现后调整的部分

#### 设计含义

- 性格变化是连续漂移，不是离散切换。
- 事件对性格的影响最深，对话次之，时间最浅。
- 角色可以同时持有相互矛盾的性格单元，置信度决定主导权。
- 性格单元集合随时间线独立演化。

#### 待实现后调整的部分

- 具体变化步长 `Δ` 的数值。
- 驱动强度的计算方式。
- 归档清理策略。
- 压缩提交的触发条件与粒度。

---

### 5.11 角色卡生成

#### 两种生成方式

| 方式 | 说明 |
|---|---|
| 用户自定义 | 用户直接定义角色卡各项内容 |
| AI 根据描述生成 | 用户给出自然语言描述，AI 生成角色卡 |

#### AI 生成后的检查

- AI 生成角色卡后，必须经过用户检查。
- 用户可修改、补充、删除生成内容。
- 用户确认后，角色卡才生效。
- **仅保留最终确认版本，不保留生成历史。**
- 未经确认的角色卡不进入世界实例。

#### 设计含义

- 生成历史不保留，避免冗余。
- 用户确认版本即最终版本。
- 与黑箱设计一致：内部生成过程不对外暴露。

---

### 5.12 角色与认知约束

#### 角色绑定世界

角色不是全局角色，而是“某个世界中的角色”。角色设定包括：

- 身份、职业、性格、背景
- 活动范围（如宇航舱、王都及周边、全国运输路线）
- 信息渠道（如通讯设备、报纸、传闻、魔法通讯）
- 与用户的通讯方式
- 认知边界与知识范围

#### 认知软约束

默认采用软约束。角色知道什么，由以下因素共同决定：

- 角色自身设定
- 角色在世界中的位置
- 角色经历过的事件
- 角色能接触到的信息渠道
- 角色与用户的历史对话

角色可以：

- 知道一部分
- 听说过但不确认
- 推测
- 完全不知道
- 给出带主观色彩的解释

角色不应：

- 无理由知道全局设定
- 说出角色不可能接触到的信息
- 以全知视角描述世界

#### 硬约束例外

当角色被设定为“与外界无信息交流”时，启用硬约束。例如：

- 独自在太空舱中的宇航员
- 与世隔绝的囚徒
- 封闭实验对象

此类角色只能知道：

- 自身直接经历
- 自身所处小环境内的信息
- 与用户通讯中获得的信息

硬约束是世界包中的显式设定，不是默认行为。

## 六、时间与版本

### 6.1 时间线模型

#### 模型语义

这里使用的“分支”更接近**平行时间线**，而非 Git 的独占式分支。关键差异：

| Git 分支 | 本项目时间线 |
|---|---|
| 同时只有一个检出 | 可同时激活多条 |
| 未检出分支不推进 | 未激活时间线冻结，激活时间线推进 |
| 分支用于开发隔离 | 时间线用于世界演化隔离 |

#### 推进规则

- **仅激活时间线推进。** 未激活时间线冻结在世界时间上，不产生新事件，不消耗模拟资源。
- **允许同时激活多条时间线。** 多条激活时间线各自独立推进，互不干扰。
- **每条激活时间线拥有独立世界时钟。** 不同时间线的世界时间可以不同。
- **时间线从创建时刻开始推进。** 创建时继承来源时间线的状态快照，此后独立演化。

#### 时间线与会话的关系

- 一个会话绑定一条时间线。
- 用户可同时开启多个会话，分别绑定不同时间线。
- 用户可在同一时间线内切换角色（若该时间线所属世界包含多角色）。
- 用户可切换某会话所绑定的时间线。

#### 时间线的创建

时间线通过以下方式创建：

1. **引入世界事件。** 用户提出修改意图，系统创建新时间线，从修改点起引入事件。
2. **手动创建。** 用户从任意提交点创建新时间线。
3. **重置。** 从某个历史提交创建全新时间线。

#### 时间线的管理

- 命名、描述、归档、删除。
- 查看所有时间线及其状态。
- 查看时间线之间的关系（来源提交、创建时间）。
- 时间线不合并。

---

### 6.2 世界时钟流速倍率

#### 倍率定义

- 世界时钟与现实时间存在可调倍率关系。
- 倍率 `rate` 为正整数。
- 含义：现实时间每推进 1 秒，世界时间推进 `rate` 秒。
- `rate = 1` 为默认值。
- 默认上限为 2592000（30 天）。
- **上限为全局配置，不随时间线走。**
- **上限仅开发者可配置，用户不可配置。**
- 用户可在 `[1, 上限]` 范围内自由调整倍率。

#### 用途

- 调试：快速流逝时间，检测时间驱动性格单元、事件生成、世界演化。
- 正式：用户可调整世界节奏，适应不同世界的叙事密度。

#### 世界时钟状态

| 字段 | 说明 |
|---|---|
| `base_real_time` | 基准现实时间 |
| `base_world_time` | 基准世界时间 |
| `rate` | 当前倍率，正整数 `[1, 上限]` |
| `pending_rate` | 待生效倍率 |
| `pending_rate_input_time` | 待生效倍率的输入时刻 |

全局配置项：

| 配置项 | 说明 |
|---|---|
| `rate_max` | 倍率上限，默认 2592000，仅开发者可配置 |

当前世界时间计算：

```
current_world_time = base_world_time + (now_real - base_real_time) × rate
```

#### 倍率调整

倍率更新在自然整秒时生效，倍率归属以用户输入时刻为准。

调整流程：

1. 用户输入新倍率，记录输入时刻 `pending_rate_input_time`。
2. 新倍率存入 `pending_rate`。
3. 系统确定该输入归属的自然整秒：
   - 若输入发生在整秒 `T` 之前（即 `T` 尚未到达），则归属整秒 `T`。
   - 若输入发生在整秒 `T` 之后（即 `T` 已过），则归属整秒 `T+1`。
   - 若输入时刻恰为整秒 `T`，则归属整秒 `T+1`。
4. 在归属的整秒时刻：
   - 计算当前世界时间。
   - 更新 `base_world_time` 为当前世界时间。
   - 更新 `base_real_time` 为该整秒时刻。
   - 将 `pending_rate` 赋给 `rate`。
   - 清空 `pending_rate` 与 `pending_rate_input_time`。

#### 倍率的作用范围

- 倍率为每条激活时间线独立配置。
- 不同激活时间线可拥有不同倍率。
- 修改某条时间线的倍率不影响其他时间线。
- 未激活时间线冻结，倍率不生效。
- **倍率上限为全局配置，所有时间线共享同一上限。**

#### 倍率与各机制的关系

| 机制 | 与倍率的关系 |
|---|---|
| 世界时钟 | 直接受倍率影响 |
| 时间驱动性格单元 | 受倍率影响 |
| 事件生成 | 受倍率影响 |
| 自动提交 | 按现实时间间隔触发，不受倍率影响 |
| 手动提交 | 用户触发，不受倍率影响 |
| 会话核心 | 不感知倍率 |
| 对话上下文 | 不受倍率影响 |
| 插件层 | 不感知倍率 |

---

### 6.3 世界时钟可见性

- 世界时钟作为公开信息展示。
- **仅展示当前激活时间线的时间。**
- 不展示其他时间线的时间。
- 用户切换激活时间线时，展示的时间随之切换。
- 世界运行状态正常提示同样仅针对当前激活时间线。

---

### 6.4 版本管理

#### 作用域

版本管理**仅作用于世界运行状态**。世界包仅保留最新一版。

| 对象 | 是否版本管理 | 说明 |
|---|---|---|
| 世界运行状态 | ✅ | 世界时钟、角色状态、事件日志、认知状态 |
| 世界包 | ❌ | 仅保留最新版，用户可自行导出备份 |
| 时间线元数据 | ✅ | 时间线的创建、来源、状态 |

#### 世界包的处理

- 世界包仅保留最新版。
- 用户修改世界包时，直接覆盖当前版本。
- 用户可自行导出世界包备份。
- 世界包的修改不进入版本历史。
- 世界包修改后，**已存在的时间线不受影响**，新时间线基于新世界包。

这意味着：世界包是“世界法则的当前版本”，时间线是“在该法则下运行出的历史”。修改法则不追溯历史，只影响未来创建的时间线。

#### 提交机制

提交对象：**世界运行状态快照**。内容包含：

- 世界时钟
- 角色状态
- 事件日志
- 认知状态
- 所属时间线元数据

提交方式：

| 方式 | 说明 |
|---|---|
| 自动提交 | 按时间间隔（如每小时）或事件数量阈值自动快照 |
| 手动提交 | 用户主动创建快照 |

自动提交参数可配置。用户可关闭自动提交。

#### 提交的作用

- 作为回滚点。
- 作为时间线创建点。
- 作为世界重置的锚点。
- 作为状态恢复的基线。

#### 与类 Git 的对应

| Git 概念 | 本项目 |
|---|---|
| 仓库 | 一个世界 |
| 提交 | 世界运行状态快照 |
| 分支 | 时间线（可多条同时激活） |
| 检出 | 激活 / 冻结时间线 |
| 标签 | 里程碑事件标记 |
| 回滚 | 回到某个提交 |
| 合并 | 不支持 |

---

### 6.5 提交配置全局统一

- 自动提交的触发阈值**全局统一**。
- 不为每个世界或时间线单独配置。
- 全局配置项例如：自动提交间隔、事件数量阈值。
- 用户可在全局层面关闭自动提交。
- 手动提交不受全局配置限制。

---

### 6.6 角色状态复制

#### 修订内容

替代 V0.5 的“全量复制”，改为：**通过类似 Git 的 diff 方式实现角色状态复制。**

#### diff 模型

- 角色状态以增量形式存储。
- 创建时间线时，新时间线从来源时间线的状态快照开始。
- 新时间线的角色状态只记录与来源时间线的差异。
- 状态读取时，沿时间线祖先链回溯，合并 diff 得到完整状态。

#### 适用对象

| 对象 | 是否 diff |
|---|---|
| 角色状态（位置、记忆、认知、关系、性格单元） | ✅ |
| 事件日志 | ✅ |
| 世界时钟 | ❌（每时间线独立计时） |
| 世界包 | ❌（不参与版本管理） |

#### 设计含义

- 存储效率提高，多时间线共享祖先状态。
- 状态读取需要回溯合并，实现复杂度上升。
- 与版本管理的提交机制统一：提交即快照，时间线即 diff 链。
- 回滚是沿 diff 链回退，不是恢复全量快照。

#### 风险

- diff 链过长时，状态读取性能下降。
- 需要定期做“压缩提交”（类似 Git 的 squash 或 gc）。
- 压缩策略需在具体设计中确定。

---

### 6.7 回滚语义

#### 修订内容

替代 V0.5 的“原时间线保留”，改为：**被回滚操作覆盖。**

#### 规则

- 时间线回滚到某个提交时，该提交之后的状态被覆盖。
- 原时间线不保留为独立时间线。
- 回滚是破坏性操作。
- 回滚后，时间线从该提交继续推进。

#### 与创建时间线的区别

| 操作 | 语义 |
|---|---|
| 创建时间线 | 从某提交分叉出新时间线，原时间线保留 |
| 回滚 | 当前时间线回到某提交，之后状态被覆盖 |

#### 设计含义

- 回滚前建议用户手动提交，以便未来参考。
- 回滚是不可逆的，除非用户之前导出过备份。
- 界面需明确提示回滚的破坏性。

#### 披露撤回的统一

- 披露撤回通过回滚实现。
- 回滚覆盖披露之后的进展。
- 与 V0.5 一致，但语义更明确：原时间线不保留。

---

### 6.8 压缩策略

- 采用**自动压缩**。
- 压缩策略在实现后根据实际表现进行相应处理。
- 总设计层面只确定：自动压缩是 diff 链的必然配套机制。
- 具体压缩触发条件、压缩粒度、压缩算法留待实现阶段确定。

---

### 6.9 对话上下文与时间线

#### 隔离原则

- 一个会话绑定一条时间线。
- 对话上下文随时间线隔离。
- 不同时间线的对话历史互不可见。
- 同一时间线内，若未来支持多角色，角色间对话历史按披露机制处理。

#### 切换时间线时的上下文

用户切换会话所绑定的时间线时：

- 原时间线的对话上下文保留在原时间线。
- 新时间线的对话上下文从该时间线已有历史继续。
- 不跨时间线拼接上下文。
- 界面显式标注当前时间线。

#### 设计意图

对话上下文是时间线体验的一部分。用户在时间线 A 与角色讨论过的事，在时间线 B 中不应自动成为共同记忆。这保证了时间线的独立性，也保证了角色认知的一致性。

---

## 七、通道与插件

### 7.1 聊天通道与内容生成解耦

#### 架构原则

聊天通道与聊天内容生成完全解耦。核心逻辑不感知消息来自何处，通道适配器不感知内容如何生成。

```
┌──────────────────────────────────────────────┐
│              通道适配层（可插拔）              │
│  内建聊天界面 │ QQ 适配器 │ Discord 适配器 │ … │
└──────────────────┬───────────────────────────┘
                   │ 统一消息协议
                   ▼
┌──────────────────────────────────────────────┐
│              会话核心层（稳定）                │
│  会话管理 · 消息路由 · 角色绑定 · 世界绑定      │
└──────────────────┬───────────────────────────┘
                   │ 查询角色认知 / 请求生成
                   ▼
┌──────────────────────────────────────────────┐
│              世界运行层（核心）                │
│  世界时钟 · 角色状态 · 事件日志 · 认知接口      │
└──────────────────┬───────────────────────────┘
                   │ 加载 / 修改 / 版本管理
                   ▼
┌──────────────────────────────────────────────┐
│              世界设定层（世界包 + 版本）        │
└──────────────────────────────────────────────┘
```

#### 统一消息协议

所有通道使用同一套消息协议。通道适配器只做两件事：

- 将外部消息转为统一协议
- 将统一协议回复转为外部消息

这意味着：

- 内建聊天界面是一种适配器
- QQ 是一种适配器
- Discord 是一种适配器
- 未来任何通道都是适配器

#### 通道切换

用户可在同一会话中快速切换通道。会话状态、世界状态、角色状态与通道无关。切换通道不中断对话，不重置世界，不改变角色认知。

---

### 7.2 聊天通道：插件式适配器

#### 架构原则

聊天通道与聊天内容生成完全解耦。所有通道以**插件**形式接入，核心项目不内嵌任何具体通道实现。

```
┌──────────────────────────────────────────────────┐
│              通道插件层（可插拔）                  │
│  聊天界面插件 │ QQ 插件 │ Discord 插件 │ …         │
└────────────────────┬─────────────────────────────┘
                     │ 统一消息协议
                     ▼
┌──────────────────────────────────────────────────┐
│              会话核心层                            │
│  会话管理 · 消息路由 · 角色绑定 · 世界绑定 · 时间线绑定│
└────────────────────┬─────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────────┐
│              世界运行层                            │
└──────────────────────────────────────────────────┘
```

#### 插件式通道

| 特性 | 说明 |
|---|---|
| 插件独立 | 每个通道适配器是独立插件，可独立安装、启用、停用 |
| 协议统一 | 所有插件遵循同一套消息协议 |
| 核心无感 | 会话核心不感知消息来自哪个通道 |
| 可并行 | 同一会话可同时通过多个通道收发 |
| 可替换 | 停用某插件不影响其他插件和会话状态 |

#### 插件职责边界

通道插件只做两件事：

- 将外部消息转为统一协议
- 将统一协议回复转为外部消息

插件不参与：内容生成、世界状态查询、角色认知、时间线管理。

#### 内建聊天界面

内建聊天界面本身也是一个插件，只是随项目默认提供。它与其他通道插件地位相同，可被停用或替换。

---

### 7.3 通道插件开放第三方

#### 开放性

- 通道插件允许第三方开发。
- 项目提供**插件接口文档**。
- 项目提供**参考实现**（内建聊天插件即为参考）。
- 第三方插件可独立发布、安装、启用、停用。

#### 接口文档内容

接口文档应包含：

- 统一消息协议规范
- 插件生命周期接口
- 消息收发接口
- 错误处理约定
- 认证与授权约定（如涉及）
- 版本兼容性说明
- 示例插件

#### 核心与插件的关系

- 核心不依赖任何具体插件。
- 内建聊天插件与其他插件地位相同。
- 第三方插件不修改核心代码。
- 插件崩溃不影响核心与其他插件。

---

### 7.4 插件进程隔离与版本兼容

#### 修订内容

替代 V0.6 的“仅接口约束”，改为：

- **接口约束 + 进程隔离。**
- 第三方插件作为**独立进程**运行。
- 插件崩溃不影响主程序。
- 接口版本变化时提示用户，尝试运行，报错则反馈并停止插件进程。

#### 进程隔离

| 特性 | 说明 |
|---|---|
| 独立进程 | 每个第三方插件运行在独立进程中 |
| 崩溃隔离 | 插件进程崩溃不影响核心进程 |
| 通信方式 | 插件与核心通过进程间通信交互 |
| 生命周期 | 核心管理插件进程的启动、停止、重启 |
| 资源限制 | 可对插件进程施加资源限制（具体实现阶段确定） |

#### 版本兼容策略

当核心接口版本发生变化时：

1. **向用户提示**：该插件依赖旧接口版本，可能与当前版本不兼容。
2. **尝试运行插件**。
3. **若无报错信息**：正常使用。
4. **若有报错信息**：
   - 将报错信息反馈给用户。
   - 停止该插件进程。
   - 不影响核心与其他插件。

#### 接口文档

- 向第三方开发者提供接口文档。
- 文档包含：统一消息协议、插件生命周期接口、消息收发接口、错误处理约定、版本兼容性说明、示例插件。
- 接口版本号显式声明，便于兼容性判断。

#### 内建聊天插件

- 内建聊天插件与其他插件地位相同。
- 内建聊天插件也运行在独立进程中（或作为核心的一部分，具体实现阶段确定）。
- 内建聊天插件作为参考实现，展示接口用法。

---

### 7.5 插件进程间通信

#### 进程间通信

- 进程间通信机制在**具体实现时确定**。
- 总设计层面不锁定具体机制。
- 候选机制：标准输入输出、本地 socket、其他。

### 7.6 内建聊天插件归属

- 内建聊天窗口作为**核心进程的一部分**。
- 内建聊天窗口不运行在独立进程中。
- 内建聊天窗口作为参考实现，展示接口用法。
- 第三方插件仍运行在独立进程中。
- 内建聊天窗口与第三方插件地位在功能上相同，但在进程归属上不同。

#### 设计含义

- 核心进程包含：会话核心、世界运行层、内建聊天窗口。
- 第三方插件进程独立于核心进程。
- 内建聊天窗口的稳定性由核心保证。
- 第三方插件的稳定性由插件自身与隔离机制保证。

---

### 7.7 内建聊天窗口

#### 当前形态

- 内建聊天窗口作为核心进程的一部分。
- 遵循统一消息协议。
- 作为参考实现。

#### 拆分后形态

- 架构上预留可拆为独立插件。
- 若拆分，桌面端仅保留插件版本，不再保留内建版本。
- 拆分后的插件与核心进程兼容。

#### 安卓端处理

- 安卓端始终使用内建聊天实现。
- 安卓端内建实现遵循统一消息协议。
- 安卓端内建实现保持独立，不随桌面端拆分而同步拆分。
- 两端的内建实现可以共享代码，但作为独立模块维护。

---

### 7.8 用户位置与通讯机制

#### 用户在世界外

用户不是世界内居民。用户不占据世界中的地理位置，不直接参与世界事件。用户是：

- 观察者
- 联络者
- 对话者

用户可以通过角色间接影响世界，但影响路径是“用户 → 角色 → 世界”，而不是“用户 → 世界”。

#### 特殊双向联络

角色拥有某种“仅能与用户双向联络”的特殊通讯方式。该通讯方式由世界设定定义，例如：

- 宇航员的量子通讯终端
- 王都居民的魔法传讯石
- 货车司机的某个神秘聊天软件
- 其他符合世界观的解释

通讯方式的特点：

- 仅连接用户与角色
- 不连接世界内其他存在
- 其存在本身可以是世界设定的一部分
- 其限制可以影响角色认知

#### 聊天功能内建

新项目自带聊天功能，包含：

- 会话界面
- 角色选择
- 世界切换
- 历史记录
- 世界时间显示
- 角色状态提示

外部通道（如 QQ、Discord）未来可作为适配器，但不是核心依赖。

## 八、世界实例导入导出与跨端同步

### 8.1 跨端同步

#### 无云同步

- 项目**不提供云同步服务**。
- 不依赖任何云端存储。
- 不自动同步任何数据。

#### 手动同步

- 所有跨端同步由**用户手动完成**。
- 同步方式：通过世界实例的导出与导入。
- 用户在桌面端导出世界实例，在安卓端导入；反之亦然。
- 同步是用户主动行为，系统不介入。

#### 设计含义

- 项目保持本地优先，无外部依赖。
- 用户完全掌控数据的迁移。
- 与黑箱设计一致：导出的是封装包，用户不编辑内部。

---

### 8.2 世界实例导入导出

#### 导出包格式

- 单一文件。
- 不加密。
- 具体格式由实现决定。
- 接受用户可能通过解压等方式查看内部数据。
- 封装世界实例的完整状态，包括世界包快照、世界运行状态、时间线、提交历史、角色状态。

#### 世界包名称存储

- 世界包名称嵌入世界包快照中。
- **系统以世界包快照中的原始名称为准。**
- **用户对世界包文件中名称的任何修改，系统视为未发生。**
- 导入时读取的是系统记录的原始名称，而非用户修改后的名称。
- 这意味着系统需在世界包快照中保留一份原始名称的独立记录，不受文件层修改影响。

#### 导出内容范围

- 仅包含世界实例本身。
- 不包含激活状态信息。
- 导入后，激活状态由导入端进行设置。

#### 导入语义

- 导入始终创建一个新的世界实例。
- 导入不修改、不覆盖、不影响任何已有世界实例。
- 新实例与原有实例完全独立。
- 各副本此后独立演化，互不影响。
- 不支持世界合并。

#### 导入实例命名

- 导入时，从导出包的世界包快照中读取**原始世界包名称**。
- 基于该名称自动生成一个候选名称。
- **全局不允许同名世界实例。**
- **同名约束全局不区分世界。** 即无论实例属于哪个世界，名称均不可重复。
- 若候选名称与已有任何实例同名，系统自动追加序号。
- **序号格式为 `名称_2`、`名称_3`，依此类推。**
- 名称生成后，交给用户进行调整、决定。
- 用户确认后，新实例以该名称创建。
- 若用户修改后的名称仍与已有实例同名，系统拒绝并提示用户。
- 用户需提供一个全局唯一的名称。

#### 版本兼容检查

- 仅在导入时检查。
- 导出时不检查版本兼容性。
- 导入时，将导入包声明的版本与当前版本比对。
- 若存在兼容性差异，向用户提示导出时的版本、当前版本、可能受影响的方面。

#### 版本不兼容的处理

- 若版本差异极大且无转换工具，拒绝导入。
- 向用户提示：建议使用对应兼容版本的项目程序进行运行。
- 不提供强制导入选项。
- **不允许手动部分迁移。**
- **仅提示使用兼容版本。**
- 有转换工具时，自动检测并提示用户确认后转换。

#### 导出包与对话体验的关系

- 导出包包含世界实例的内部真相。
- 对话体验是用户通过角色认知接口获得的局部视图。
- 两者存在差异是设计使然，不是 bug。
- 不需要提示，不需要干预。

#### 世界包文件修改责任

- 用户可对导出世界包文件进行修改。
- 项目不提供任何支持。
- 修改出现的问题，后果由用户自行承担。
- 已创建的世界实例与导出世界包文件无关联。
- 修改世界包文件不影响任何已创建的世界实例。
- **世界包名称以系统记录的原始值为准，用户修改不生效。**

## 十、披露机制（多角色对话可见性）

### 10.1 多角色与对话历史可见性

#### 当前阶段约束

当前阶段：**同一世界仅包含一个角色。** 架构上预留多角色扩展点。

#### 多角色时的对话历史规则

当同一世界包含多个角色时：

| 规则 | 说明 |
|---|---|
| 默认隔离 | 用户与角色 A 的对话历史，角色 B 默认不可见 |
| 用户主动披露 | 用户主动向角色 B 说明后，相关历史对 B 可见 |
| 角色不主动表露 | 角色之间不会主动向对方透露自己与用户的对话 |
| 披露粒度 | 按用户说明的范围披露，不自动扩散 |

#### 披露机制的含义

- 用户是对话历史的唯一授权者。
- 角色没有“互相通报”的动机或能力。
- 披露是单向的、显式的、由用户发起的。
- 披露后，角色 B 的认知中新增这部分信息。

#### 设计意图

这一机制保证了：

- 用户对多角色关系有完全控制权。
- 角色之间不会形成“信息串联”破坏沉浸感。
- 用户可以选择让角色间“知道彼此”，也可以保持隔离。

---

### 10.2 披露撤回机制

#### 修订内容

替代 V0.4 中“撤回披露”的独立机制，改为：**披露撤回通过将世界重置到某个提交来实现。**

#### 规则

- 披露信息一旦发生，即成为该时间线状态的一部分。
- 不存在“单独撤回某条披露”的操作。
- 如需撤回，用户将时间线回滚到披露发生之前的提交。
- 回滚后，从该提交创建新时间线，或继续推进。

#### 设计含义

- 披露是世界状态的一部分，不是独立可撤销的对象。
- 撤回披露 = 世界回滚。
- 这与版本管理机制统一，不引入额外机制。
- 用户需理解：撤回披露的代价是丢失该提交之后的所有进展。

#### 操作路径

1. 用户找到披露发生之前的提交。
2. 将当前时间线回滚到该提交，或从该提交创建新时间线。
3. 披露信息不再存在于新状态中。

## 十一、实施路径

### 11.1 实施路径

#### 阶段 0：独立项目骨架 + 核心进程 + 内建聊天窗口

- 新建独立项目
- 定义统一消息协议
- 核心进程内实现内建聊天窗口（遵循统一消息协议）
- 定义第三方插件接口与文档
- 实现第三方插件进程隔离机制（仅桌面端）
- 实现最小会话核心

验证：内建聊天窗口通过统一消息协议对话；第三方插件可独立进程运行；插件崩溃不影响核心。

#### 阶段 1：世界包 + AI 生成 + 多世界 + 角色卡 + 导入导出

- 世界包文件结构定义
- 世界包生成器（表单式 + 对话式）
- 世界包文件可修改，仅保留最新版
- 世界包名称嵌入世界包快照，原始名称独立记录
- 从世界包文件创建世界实例
- 世界实例设定完全锁死，与世界包文件无关联
- 世界实例内部黑箱，世界时钟公开
- 世界实例导入导出（单一文件，不加密；导入时版本检查；不兼容拒绝导入；转换工具自动检测 + 用户确认；导入创建新实例；名称基于原始世界包名称自动生成 + 用户调整；全局不允许同名；重名自动追加 `_2` 等序号）
- 多世界支持
- 角色卡独立，支持用户自定义或 AI 生成 + 用户检查，仅保留最终确认版本

验证：修改世界包文件 → 创建新世界实例 → 旧世界实例不受影响；导入创建新实例且不影响原有实例；版本不兼容时拒绝导入；全局同名被拒绝；自动追加序号从 `_2` 起始；用户修改世界包名称不生效。

#### 阶段 2：世界时钟 + 倍率 + 角色认知 + 性格单元

- 世界时钟与系统时间同步，仅展示当前激活时间线时间
- 世界时钟倍率实现，每时间线独立，默认 1
- 倍率上限全局配置，默认 2592000，仅开发者可配置
- 倍率在自然整秒时更新生效，归属以输入时刻为准，整秒瞬间输入归属下一整秒
- 同一世界多角色共享世界时钟
- 角色状态存入世界运行层
- 性格单元置信度模型实现（四种驱动方式）
- 驱动迁移隐式存在，不对用户可见
- 认知接口按角色设定返回信息子集

验证：角色不会无理由知道全局设定；性格单元随四种驱动漂移；锚点驱动不归档；驱动迁移不可见；倍率在整秒生效且归属正确；倍率上限仅开发者可配置。

#### 阶段 3：事件日志 + 碎片化叙事

- 角色行动产生事件
- 事件写入日志
- 对话中按认知范围检索事件与设定

验证：用户通过 ≥ 5 轮对话获取 ≥ 3 条需拼凑的世界设定。

#### 阶段 4：版本管理 + 时间线 + diff 存储

- 提交机制（全局统一自动 + 手动）
- 时间线创建、激活、冻结
- 多条时间线同时激活
- 角色状态 diff 存储与合并（含四种驱动的性格单元）
- 自动压缩（策略实现后确定）
- 回滚（覆盖语义）
- 对话上下文随时间线隔离

验证：创建多条时间线并同时激活；diff 合并正确；回滚覆盖原状态；对话上下文隔离；自动压缩生效；倍率随时间线独立。

#### 阶段 5：多角色 + 披露机制

- 同一世界多角色，每角色独立角色卡，共享世界时钟
- 对话历史隔离
- 用户主动披露
- 角色不主动表露
- 披露撤回通过回滚实现

验证：角色间默认隔离；披露后可见；回滚后披露消失。

#### 阶段 6：世界自演化

- 世界规则驱动事件生成
- 新设定从已有设定中推导
- 世界在无用户互动时也持续变化

验证：运行一周后，世界状态有自洽变化。

#### 阶段 7（可选）：安卓移植评估

- 评估跨平台方案
- 安卓端不开放插件，始终使用内建聊天实现，遵循统一消息协议，独立维护
- 安卓端与桌面端共享世界包生成器
- 安卓端支持世界实例创建、对话、世界包修改（表单式 + 对话式）、导入导出、倍率调整
- 评估运行时方案
- 跨大版本不兼容时先查找转换器；无转换器则提示使用兼容版本
- 无云同步，跨端同步手动完成

验证：核心功能在安卓端可运行；世界包修改可用；世界包生成器共享；倍率调整可用；导入导出可用；无插件接入入口；跨版本处理符合规则。

## 十三、主要风险与应对

### 13.1 主要风险与应对

| 风险 | 应对 |
|---|---|
| 性格单元置信度模型不稳定 | 阈值与步长可配置；人工抽检；实现后调参 |
| 驱动迁移规则导致性格突变 | 迁移渐进；隐式存在；人工抽检 |
| 锚点驱动单元不足以保证可辨识性 | 角色卡初始集合 + 演化连续性共同保证 |
| 锚点驱动单元无上限导致膨胀 | AI 自行判断；压缩提交时评估保留必要性 |
| diff 链过长导致状态读取性能下降 | 自动压缩；压缩策略实现后确定 |
| diff 合并实现复杂 | 阶段 4 前先用全量快照验证机制，再引入 diff |
| 极高倍率下世界状态快速膨胀 | 默认上限 2592000；仅开发者可配置；用户需注意；可通过版本管理回退 |
| 倍率归属边界不明确 | 以输入时刻为准；严格对齐自然整秒；整秒瞬间输入归属下一整秒；测试边界条件 |
| 世界实例黑箱导致用户无法排查问题 | 世界时钟公开；系统内部保证一致性 |
| 导出包不加密，用户查看内部数据 | 接受用户查看；内部数据仍不可编辑 |
| 用户修改世界包文件出问题 | 项目不提供支持；后果自负；已创建实例不受影响；名称修改不生效 |
| 跨版本导入不兼容 | 导入时检查；不兼容拒绝导入；建议使用兼容版本；不允许手动部分迁移 |
| 转换工具缺失导致旧实例无法使用 | 重大变更版本必须提供转换工具；无转换器则提示用兼容版本 |
| 无云同步导致跨端体验割裂 | 明确告知用户手动同步方式；导出导入流程简洁 |
| 导入创建新实例导致多端副本分散 | 界面明确提示；用户自行管理副本 |
| 不支持世界合并 | 用户需理解副本独立演化；无合并路径 |
| 同名实例冲突 | 全局不允许同名；自动追加 `_2` 等序号；用户改名仍需保证唯一 |
| 倍率上限被误改导致异常 | 仅开发者可配置；用户不可见配置入口 |
| 插件进程隔离在安卓上受限 | 安卓端不开放插件，规避该问题 |
| 插件接口版本变化导致兼容问题 | 版本号显式声明；提示 + 尝试 + 报错反馈 |
| 内建聊天窗口拆分后桌面端与安卓端实现分叉 | 两端独立维护；共享协议与参考实现 |
| 回滚覆盖导致用户丢失进度 | 界面明确提示；建议回滚前手动提交 |
| 多时间线同时激活导致资源消耗 | 未激活时间线冻结；激活数可配置上限 |
| 多角色共享世界时钟导致状态复杂 | 世界时钟统一；角色状态独立存储 |
| 软认知约束被 LLM 绕过 | 认知上下文注入 + 后验一致性检查 |

## 十六、附录 B：早期版本中未被后续修订的条款（V0.1 原文）

### 组织、角色与资源需求

#### 你的角色

你是**世界设计者 + 系统架构师 + 最终验收者**。Agent assisted 模式下，你不需要写每一行代码，但需要：

- 定义世界规则和设定层的结构。
- 决定“什么算自洽”“什么算碎片化体验达标”。
- 在 Agent 产出的方案之间做取舍。

#### Agent 分工建议

| 角色 | 职责 |
|---|---|
| **架构 Agent** | 设计世界层与对话层的接口、数据结构、tick 调度机制 |
| **实现 Agent** | 按架构方案编写世界时钟、状态存储、事件系统 |
| **设定 Agent** | 协助生成和维护设定层内容（结构化世界设定） |
| **验证 Agent** | 编写一致性检查、时间同步测试、设定冲突检测 |

#### 技术选型参考

- **语言：** 沿用 Python（与现有 Veranima 一致）。
- **存储：** SQLite 起步（与现有记忆系统一致），世界状态可独立于角色记忆存储。
- **时间同步：** 不依赖网络时间，使用系统单调时钟 + 持久化基准时间。
- **LLM 调用：** 世界模拟的叙事增强部分可复用现有 LLM 通道，但**时钟推进不等待 LLM**。

### 关键假设与风险

| 假设/风险 | 影响 | 应对 |
|---|---|---|
| **假设：** 世界不需要图形化也能提供足够的沉浸感 | 高 | MVP 先验证文本层；如果体验不足，再考虑最小可视化 |
| **假设：** 角色认知接口的约束不会让对话变得“太窄” | 中 | 设定层的设计需要足够丰富，使局部认知仍有探索空间 |
| **风险：** 世界状态与角色记忆产生矛盾 | 高 | 世界层是“真相源”，角色记忆从世界层派生；定期一致性检查 |
| **风险：** LLM 生成的世界事件与已有设定冲突 | 中 | 事件生成受设定层约束；新事件必须通过一致性校验才能写入 |
| **风险：** 长期运行后世界状态膨胀，检索效率下降 | 中 | 事件日志分级：近期事件全量保留，远期事件归档为摘要 |
| **风险：** 个人项目节奏不稳定，长期搁置 | 低（已接受） | 设计时确保每个阶段可独立运行和验证 |

### 治理机制与决策原则

- **世界层是真相源。** 任何世界信息冲突时，以世界层存储为准。
- **设定变更需要“从已有设定推导”。** 不允许 Agent 直接插入与已有设定无关的新设定。
- **时钟优先。** 任何功能如果会导致时钟暂停或跳变，原则上不允许。
- **阶段门禁。** 每个阶段的验证标准未通过，不进入下一阶段。

### 评估、迭代与退出机制

- **每阶段结束后，做一次 30 分钟的“体验测试”**：你以用户身份与角色对话，记录能否感受到世界的存在、时间在走、信息在碎片化地出现。
- **如果某个阶段连续两次验证失败**，回到上一阶段重新审视设计，而非强行修补。
- **如果项目最终只有阶段 0 和阶段 1 可运行**，它仍然有价值：一个有持续位置状态的角色，已经比“对话即全部”的陪伴系统更接近“生活在世界里”的体验。
