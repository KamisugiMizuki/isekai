## 一、定位

TRPG 规则层是玩家模式与 GM 辅助模式的应用编排层。它不直接把某套规则的结果写入 WorldRuntime，而是将输入交给对应规则独占转接插件，再由 TRPG 规则共用模块把已确认的世界后果交给 WorldRuntime。

```text
玩家行动 / GM 规则输入
  -> 规则独占转接插件
  -> TRPG 规则共用模块
  -> WorldRuntime 校验与原子提交
  -> 场景、角色认知与 GM 表达
```

规则层不是 WorldRuntime 的规则实现，也不是聊天文本生成器。具体规则插件拥有属性、骰点、难度、优势劣势和结果分级；TRPG Campaign Runtime 维护战役、场景、行动生命周期、规则状态快照引用、规则节拍和受众；规则共用模块只处理规则与世界之间的结构化交界面；WorldRuntime 拥有世界事实、时间线、认知、通用效果和提交；客户端负责玩家行动和 GM 表达。

目标不是“让 AI 更会讲故事”，而是让玩家或 GM 能确认：输入被准确理解，规则私有裁定被保留，世界后果经过统一校验并可追溯。

## 二、用户、角色与视角

首版支持两种主持结构：

| 模式 | 用户 | 输入 | 输出 |
|---|---|---|---|
| 玩家模式 | 玩家 / 玩家队伍 | 行动声明、选择、规则相关补充 | 裁定结果、世界后果、新场景 |
| GM 辅助模式 | GM | 故事大纲、场景安排、直接变化、玩家观察请求 | 玩家视角观察、结构化后果、偏离提示、候选推进 |

两种模式可以共享战役和 WorldRuntime，但输入语义不同。玩家说“我调查墙面”是待裁定行动；GM 说“墙后已经有一条通道”是待校验的主持声明；GM 说“我希望玩家怀疑这里”是叙事意图，不是世界事实。

玩家角色、NPC、GM 依据和世界实情必须分层。玩家能看到的是角色当前合法可知的内容；GM 为裁定保留的结构化依据不自动进入玩家文本；世界实情和其他角色私密信息不可越权泄露。

多玩家同步、玩家私密频道和复杂队伍权限不属于首版默认前提。未来扩展时必须在现有视角模型上增加明确受众，不能把“所有用户都看到”当默认。

## 三、模块边界

### 3.1 规则层的编排责任

规则层是跨模块语义边界，不另建一份战役或世界状态。它负责：

- 接收客户端已经明确其模式、作用域和用户意图的结构化命令；
- 按当前战役与场景状态，选择 B0 无状态 resolver、完整战役裁定或 GM 直接变化路径；
- 协调 WorldRuntime 快照、规则状态快照与插件请求的同一基准；
- 把插件返回交给规则共用模块规范化，再交给 WorldRuntime preview / commit；
- 协调规则状态、世界后果、场景转换的联合提交和幂等重放；
- 透传来源、受众、规则版本、世界 revision 和运行世代，不在上层猜测或补齐；
- 把底层结果翻译成客户端可消费的成功、失败、待审、待选择、冲突或过期状态。

客户端拥有自然语言输入、确认卡和结果表达；Campaign Runtime 拥有战役 / 场景 / 行动状态机；规则插件拥有规则语义；公共模块拥有规范化边界；WorldRuntime 拥有世界事实。规则层不得把这些所有权重新集中到一个“GM 大模型”里。

### 3.2 规则独占转接插件

每套 TRPG 规则都有自己的转接插件。插件负责解释规则输入、维护规则私有状态、完成规则裁定，并把结果转换为规则共用模块可处理的原始裁定与通用后果包。插件不直接写 WorldRuntime。

### 3.3 TRPG 规则共用模块

公共模块位于转接插件与 WorldRuntime 之间，负责规范化插件结果、检查通用后果包、区分 `confirmed` / `candidate` / `needs_review`，并产出可供联合提交的 WorldRuntime 变化意图。原始裁定由 Campaign Runtime 保存；实际提交由统一协调器执行。它不解释骰点、属性、职业、牌面或规则私有 context。

### 3.4 WorldRuntime 负责

WorldRuntime 仍是唯一事实与效果写入者，规则层只提交结构化意图：

- 校验提交幂等键、变化目标、效果类型、有效期和说法引用；
- 原子写入事件、效果、claims、认知传播和世界水位；
- 按角色视角提供后续可见事实；
- 处理回滚、分支、恢复、成员资格和运行世代；
- 在插件失败、结果非法或提交失败时不落半条结果。

Campaign Runtime 负责 `action_id`、`action_revision`、战役状态和场景状态；WorldRuntime 不把规则行动行当作自己的事实模型。规则层不能把插件响应中的自由文本直接当作世界事实。只有通过通用校验并提交的效果和说法，才可以进入后续世界与叙事链。

## 四、最小数据对象

### 4.1 场景

场景是玩家可行动局面的投影，不是事实的第二份副本。至少包括：

- 场景标识与当前地点 / 世界时刻；
- 在场角色及其可见关系；
- 玩家角色可确认的事实；
- 尚未确认或有争议的线索；
- 当前危险、后果和限制；
- 等待玩家选择的行动状态；
- 场景推进方式：即时、连续、对抗或世界推进。

场景中的每条事实都必须能追溯到 WorldRuntime 的现有视图、已提交行动结果或合法角色认知。场景摘要可以重建，已提交的行动结果不可被摘要覆盖。

### 4.2 行动声明

行动声明区分用户原文与系统可裁定的意图：

```text
原始描述
  -> 行动者
  -> 目标 / 对象
  -> 方法
  -> 期望结果
  -> 前置条件
  -> 可见风险与可能代价
  -> 是否需要玩家确认
```

“我打开门”是行动意图，不是门已打开的事实；“我想调查机关”是尝试，不是已经发现机关。解析不充分时进入待补充状态，不自动猜测关键行动。

### 4.3 裁定记录

每次行动至少保存：

- 原始行动声明与确认版本；
- 行动者和当前场景；
- 插件 manifest 与规则版本；
- action_id；
- resolution 与 rolls；
- 效果、claims、参与者和提交状态；
- 玩家 / NPC 可见范围；
- 失败原因、代价或无法裁定原因；
- 新场景局面与等待状态。

这些记录用于复盘、争议、恢复和分支，不要求全部直接显示给玩家。

## 五、核心流程

### 5.1 开场与场景建立

```text
创建 / 恢复战役
  -> 绑定实例、时间线、玩家角色
  -> 从 WorldRuntime 获取一致水位视图
  -> 建立首个场景
  -> GM 描述当前局面与可行动入口
```

GM 开场只能使用玩家角色应知的材料。无法形成可行动局面时，系统应请求必要的创作输入或明确停在待准备状态，不用气氛文本掩盖缺失条件。

### 5.2 行动确认

```text
玩家自然语言行动
  -> 识别行动者、目标、方法和意图
  -> 显示风险、条件与可能代价
  -> 玩家确认 / 修改 / 放弃
  -> 形成唯一 action_id
```

未确认的关键行动不得调用会改变世界的裁定链。低风险、明确且已授权的普通行动可以由自动主持模式直接确认，但规则层必须保留该模式的可见边界。

### 5.3 调用规则独占转接插件与公共模块

```text
已确认行动
  -> Campaign Runtime 读取世界快照与规则状态快照
  -> 规则独占转接插件
  -> resolution + rule_state_patch + world_consequences + scene_transition
  -> 规则共用模块检查结构、版本、受众和联合提交边界
  -> WorldRuntime 校验并提交世界后果
  -> Campaign Runtime 提交规则状态并切换场景
```

插件崩溃、超时、输出不是合法 JSON、协议版本不匹配、转接结果无法映射或响应缺少必要字段时，行动进入明确失败 / 待审状态，不产生世界效果，不伪造骰点结果。

### 5.4 提交与新局面

```text
合法裁定结果
  -> WorldRuntime 原子提交
  -> 获取事件标识、世界水位和写入效果数量
  -> 更新角色认知与场景投影
  -> GM 表达结果
  -> 给出新的可行动局面
```

规则插件返回成功不等于世界已经改变。只有提交成功，GM 才能把效果表达为已发生；提交失败时必须说明结果尚未落地。

### 5.5 三条入口的固定语义

规则层只能从三条入口之一开始一次处理，不在中途把一种输入改解释成另一种：

| 入口 | 适用内容 | 插件 | 是否产生行动行 | 提交路径 |
|---|---|---:|---:|---|
| B0 resolver | 单次、无持续规则状态的兼容裁定 | 是 | 否 | `trpg.action.resolve` 的无 `campaign_id` 路径 |
| 战役行动 | 已确认的玩家 / NPC 行动 | 是 | 是 | `declare → confirm → resolve → review → trpg.commit` |
| GM 直接变化 | GM 已明确决定的结构化变化、世界过程或剧本推进 | 否 | 否 | `trpg.gm.change → 公共模块 → 联合提交` |

B0 返回的成功只表示 B0 世界效果路径被接受；它不提供战役场景、持续规则状态、待选择恢复或完整 GM 产品体验。战役行动的 `resolve` 只保存裁定并停在 `reviewing` / 待审状态；只有 `trpg.commit` 成功后才更新世界、规则状态和场景。GM 直接变化不伪造骰点，也不创建一条虚假的玩家行动。

### 5.6 联合提交的责任闭包

一次战役提交以以下材料为一个不可拆分的闭包：

```text
scope = instance_id + timeline_id + campaign_id
action_id? + action_revision?
base_campaign_revision
base_world_revision / snapshot_id
base_state_revisions[]
resolution_ref
rule_state_patches[]
world_changes[]
knowledge_changes[]
scene_transition?
world_time_request?
idempotency_key
```

规则层必须保持以下顺序：

1. 读取并固定战役、世界和规则状态基准；
2. 调插件或接收 GM 结构化变化；
3. 经公共模块规范化并取得 `ready` / `needs_review`；
4. 由 WorldRuntime 预览目标、效果、认知、时间和版本；
5. 由同一协调器联合提交规则状态、世界后果和场景转换；
6. 依据一个联合结果更新行动 / 战役状态并返回客户端。

任一版本、目标、权限、规则 patch、时间或场景转换检查失败，规则状态、WorldRuntime 和 Campaign Runtime 都不能以“部分成功”落盘。已存在的失败 / 待审记录可以保存诊断，但不等于事实提交。

### 5.7 来源、受众与版本

- `source_mode` 的行动路径值为 `action`，落成事件来源 `trpg_action`；GM 直接变化可用 `gm_declaration`、`world_process` 或 `npc_script`，分别落成 `gm_declaration`、`trpg_world_process`、`trpg_npc_script`。
- `source_mode` 是审计来源，不是绕过权限的凭据；GM 直接变化也必须经过结构化目标、受众、时间和版本校验。
- 受众只使用闭集：`public_party`、`gm_only`、`player:<id>`、`character:<id>`、`npc:<id>`；多个角色的可见并集必须由上层显式传入，核心不推断 `user:<id>`。
- 插件声明的 `ruleset_id` / `ruleset_version`、规则状态写入版本、WorldRuntime revision 和运行世代都必须在提交前比对；不兼容就阻断，不静默换规则。
- `action_id` 标识一次规则行动；`action_revision` 标识该行动的确认版本；`idempotency_key` 标识一次联合提交。三者不能互相替代。

### 5.8 插件错误与失败恢复

结构化插件错误按 `needs_input`、`needs_choice`、`needs_review`、`plugin_failed`、`rejected` 处理。错误响应若携带 `rule_state_patch`、`consequences` 或 B0 `effects` 半成品，一律进入待审且不采信任何半成品。

插件在尚未发出请求前死亡，可以按协议边界重新启动；请求已经发出后死亡、超时、返回非法 JSON 或协议不匹配，不重跑可能产生随机结果的裁定，行动进入 `plugin_failed` / `interrupted`。核心重启后：`reviewing` 重新等待提交，`committing` 查询幂等账本，`resolving` 只能显式重试，不自动重掷。

## 六、GM 辅助模式

GM 辅助模式不是“替玩家自动掷骰”，而是让 GM 以结构化方式维护一个由大纲约束的战役世界。

GM 输入分为三类：

| 输入 | 处理路径 | 是否直接改变世界 |
|---|---|---|
| 规则行动安排 | 进入对应规则独占转接插件 | 经过裁定与公共层提交 |
| 直接世界变化 | `source=gm_declaration` 进入规则共用模块 | 经过公共层与 WorldRuntime 校验后提交 |
| 故事意图 / 大纲目标 | 进入 Writing Assistant 候选编排 | 否，须 GM 确认具体变化 |

例如“玩家尝试撬锁”是规则行动；“城门已经被毁”是 GM 直接变化；“我希望这一幕让玩家意识到有人跟踪”是故事意图。三者不能都当成行动声明，也不能都调用同一个规则骰点路径。

GM 输入变化后，系统从 WorldRuntime 当前水位和各玩家角色视角重建：

```text
GM 变化 / 玩家行动结果
  -> 结构化后果与 WorldRuntime 提交
  -> 更新世界事实、时间和角色认知
  -> 读取玩家角色可见视图
  -> 输出玩家们分别观察到的情况
  -> 提示大纲达成、缺口或偏离
```

GM 可以确认、修改、拒绝或分支试演候选。系统不能因为大纲要求某件事发生，就跳过前置条件直接写入世界。


每轮 GM 输出至少回答四个问题：

1. 发生了什么：行动如何被理解，裁定结果是什么；
2. 为什么这样判：使用了哪类规则、条件或风险；
3. 世界改变了什么：角色、环境、线索、资源或时间的后果；
4. 现在可以做什么：新的场景状态与等待的玩家选择。

复杂裁定提供可展开摘要，但不把 GM 私有真相全部展示给玩家。叙事表达位于裁定和状态提交之后，负责把已固化结果放进当前场景，不负责补造事实、替玩家选择或修饰失败为成功。

## 七、结果与失败语义

规则层至少支持：

- 自动成功；
- 普通成功；
- 部分成功；
- 失败但获得信息；
- 失败并产生代价；
- 当前条件不足、暂不裁定；
- 玩家放弃或改做其他行动。

失败不能只输出“失败了”而没有新局面。代价必须来自插件返回的合法通用效果或 WorldRuntime 已定义的世界路径；不能凭叙事需要凭空新增资源损失、伤害、线索或 NPC 反应。

无法裁定不是失败。它表示需要补充行动条件、场景事实、角色能力或规则输入；在此状态下不推进世界、不消费行动结果，不阻止玩家改写行动声明。

## 八、主持责任模式

| 模式 | 自动范围 | 必须保留的用户控制 |
|---|---|---|
| 辅助裁定 | 解析意图、提示风险、调用插件、解释结果 | 确认行动与关键分歧 |
| 自动主持 | 普通行动、NPC 反应和低风险推进 | 关键行动确认、战役方向、回滚 |
| 共同主持 | 提供候选和草案 | 争议事实、效果和叙事方向必须明确批准 |

推荐默认辅助裁定。自动主持不得吞掉玩家正在面对的关键选择；共同主持不得把未批准草案写进 WorldRuntime。

## 九、时间与回合

规则层支持四种推进节拍：

- **即时行动**：一项行动完成后返回玩家选择；
- **连续场景**：低风险行动可连续处理，直到风险或场景变化；
- **对抗阶段**：按规则顺序轮流声明行动；
- **世界推进**：玩家暂不行动时，环境和 NPC 依据 WorldRuntime 时间线变化。

不能把所有场景硬套成战斗回合，也不能让离线补算自动消耗玩家尚未作出的关键行动。世界推进与玩家行动必须保留不同来源标识。

## 十、隐私、认知与披露

玩家角色只看到其当前合法认知；NPC 的误解可以作为 NPC 的表达，但不能被写成 GM 已确认真相。其他角色私聊、未获知事件和 WorldRuntime 实情不得进入玩家文本。

队伍公开信息、单个玩家私密信息和 GM 私有依据必须有明确受众。首版单玩家模型可以把队伍内角色信息按“玩家角色可见 / 队伍公开 / 其他角色私有”区分，不因同一用户控制多个角色就自动共享全部记忆。

TRPG 层复用 WorldRuntime 的认知、披露和回滚语义，不建立第二套秘密复制库。

## 十一、版本、恢复与幂等

同一实例 / 时间线内的 `action_id` 是行动幂等身份。重试同一行动不能重复施加效果；核心重启后必须区分已提交、未提交、插件失败和待投递表达。

战役分支可以从提交创建；原线后续结果不回流。恢复和回滚是主持人 / 创作者的显式操作，不作为普通玩家行动的默认重试按钮。历史裁定记录不因模型或文本生成器变更而重写；规则版本不兼容时阻止继续裁定，不静默替换。

## 十二、协议约束

本模块严格消费 `TRPG_RULE_PLUGIN_SPEC.md` 与 `TRPG_CAMPAIGN_RUNTIME_SPEC.md`：

- 插件 manifest 明确 id、版本、协议版本和 entry；
- entry 按参数数组启动，不经过 shell；
- 请求和响应采用一行 JSON；
- `context` 对核心保持不透明；
- `resolution` 只作为裁定记录保存；
- `rule_state_patch` 只写插件自己的版本化命名空间；
- `world_consequences` 与 claims 先进入规则共用模块，再由 WorldRuntime 校验和原子提交；
- `scene_transition` 留在 Campaign Runtime，不把待选择分支写入世界事实；
- 插件不持有 SQLite、不读取核心凭据、不直接写世界；
- `trpg.action.resolve` 仍是 B0 无状态 resolver 入口，不是完整战斗循环或 GM 文本 API。

如果第二个真实规则插件证明协议不足，才扩展协议；但在扩展前必须先确认 Campaign Runtime 的状态生命周期、联合提交和版本兼容语义，不把无状态 resolver 的成功误认为完整战役支持。

## 十三、推荐分期

- **B0：无状态 resolver 与单场景外壳**：保留当前 `trpg.action.resolve`，只验证插件进程、行动确认、结构化世界后果、真实 WorldRuntime 提交和幂等；不宣称规则状态可持续恢复。
- **B1：Campaign Runtime 状态边界**：实现战役、场景、规则状态快照引用、行动生命周期、待选择和联合提交。
- **B2：战役连续性**：加入多个场景、NPC、延迟后果、认知隔离、提交 / 恢复和跨场景线索。
- **B3：主持自动化**：加入 NPC 自主行动、不同推进节拍和三种责任模式。
- **B4：队伍与第二插件**：在 B0-B3 稳定后处理队伍受众、复杂对抗和第二个真实规则插件。

## 十四、设计不变式

1. 规则插件拥有规则私有裁定，WorldRuntime 拥有世界事实和通用效果。
2. 未确认的关键行动不产生世界效果。
3. 插件响应成功不等于 WorldRuntime 提交成功。
4. 非法效果、非法目标和非法 claims 整次拒绝，不落半条结果。
5. 每个结果都能回溯到行动、裁定、效果、视角和新局面。
6. 失败必须有代价、信息、待补充条件或明确无变化。
7. GM 表达不得补造真相、替玩家选择或把失败改写成成功。
8. action_id 重试幂等，插件和核心重启不重复施加效果。
9. 回滚、分支和规则版本变更不污染原线历史。
10. 接入第二个真实插件前，先验证规则状态快照、联合提交和版本兼容语义；无状态 resolver 的通过不等于完整战役兼容。

## 十五、行为验收

| 场景 | 必须观察到的结果 |
|---|---|
| B0 resolver | 无 `campaign_id` 时可走兼容单次裁定；不产生 Campaign action / 规则状态生命周期假象 |
| 战役行动 | 未确认行动不能 resolve；修改增加 `action_revision`；旧版本不能提交 |
| 裁定与提交 | `resolve` 只保存裁定；只有 `trpg.commit` 成功后才表达世界已改变 |
| GM 直接变化 | 不调用骰点插件、不制造行动行；来源保留为 `gm_declaration` / `world_process` / `npc_script` |
| 联合提交失败 | 规则状态、世界后果和场景转换都不落半条；行动进入真实 conflict / stale / needs_review |
| 插件错误 | 结构化错误映射为待补充、待选择、待审、失败或拒绝；夹带半成品不采信 |
| 插件死亡 / 超时 | 请求发出后不自动重跑随机裁定；核心重启可恢复为 interrupted 或查询提交账本 |
| 规则版本变化 | 不兼容时战役 blocked；转换或人工接受有明确记录，不能静默换规则 |
| 幂等重试 | 相同 `action_id` / `idempotency_key` 返回原结果，不重复扣资源或写世界 |
| 受众隔离 | 玩家看不到 GM 私有 resolution、其他角色私密内容、未获知事实或 opaque state |
| 待选择 | 未选择分支只存在 Campaign Runtime；战役 waiting 时锁住无关关键行动 |
| 时间双轨 | 规则时间推进不自动推进世界时间；非法 `world_time_request` 不动世界时钟 |
| 分支与回滚 | 场景、规则状态和行动派生不跨线回流；迟到结果按新世代失效 |

以上场景必须使用真实 Campaign Runtime、真实规则插件进程、真实 SQLite / WebSocket 边界验证；客户端设计不等于客户端已实现。
