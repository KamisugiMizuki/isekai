# isekai 作为 TRPG 模拟 GM 工具的用户视角评价草案

> 状态：评价草案，不是产品规范，不代表新增功能已经实现。
> 评价对象：一个对 AI 和电脑都不太熟，只想用自创 OC 与世界观进行 TRPG 游戏，希望系统承担部分或大部分 GM 工作的用户。
> 证据范围：除叙事中介层外，现有能力以当前代码、行为测试和真实 CLI 链路为依据；TRPG 所需但当前没有实现的能力，按产品需求推导标注。

## 一、先回答：TRPG 角度和普通 OC 故事角度是否不同

不同，而且差异不是“故事更多”这么简单。

普通 OC 故事工具的核心问题是：

> 世界和角色如何在用户不干预时继续生活，并把合适的片段自然讲给用户。

TRPG 模拟 GM 的核心问题是：

> 玩家做出行动后，系统如何根据世界规则、角色能力、当前状态和骰子 / 随机性，公平地裁定结果，再让世界和角色对这个结果产生后果。

两者的重叠部分很多：

- 世界包与角色卡；
- 世界时钟；
- 事件与后果；
- 角色认知隔离；
- 记忆与经历；
- 时间线和回滚；
- 叙事表达。

但 TRPG 会额外要求：

- 玩家角色或队伍的明确状态；
- 玩家行动的结构化识别；
- 行动目标、风险、条件和代价；
- 规则裁定或骰点；
- NPC 与环境的反应；
- 场景边界和回合 / 阶段推进；
- 失败也必须产生可理解后果；
- GM 不能替玩家决定关键行动；
- 需要把“世界事实”和“玩家可选择的行动”持续接起来。

因此，TRPG 方向不是在普通 OC 方向上加一个“更会讲故事的模型”，而是增加一条新的交互闭环：

```text
玩家声明行动
    -> 系统识别意图与目标
    -> 检查角色能力、场景条件和风险
    -> 规则裁定 / 骰点 / 结果分级
    -> 固化世界事实与后果
    -> NPC、环境和其他角色产生反应
    -> GM 表达结果并给出可行动的新局面
```

## 二、TRPG 方向的总体结论

当前项目适合作为 TRPG 模拟 GM 的“世界状态内核”，但还不是可直接游玩的模拟 GM。

它已经拥有一部分普通 GM 很需要的底层能力：

- 世界不是只存在于 Prompt 中；
- 世界时间可以持续推进；
- 事件和后果可以固化；
- 角色知道的内容可以隔离；
- 角色生活线可以产生经历；
- 世界能够从提交点分叉与回滚；
- 角色行动和打算具有一定结构；
- 消息、会话和投递有持久化与恢复机制。

但它目前缺少 TRPG 的关键“玩家行动裁定层”。当前用户主要是和角色聊天，而不是以玩家身份向 GM 声明行动并获得规则裁定。因此系统现在更接近：

> 有世界模拟能力的角色对话系统。

还不是：

> 用户可以做出行动、承担风险、改变局面，并由系统担任 GM 的可玩 TRPG 工具。

综合评价：

| 维度 | TRPG 角度评价 |
|---|---:|
| 世界运行内核 | 8.5 / 10 |
| 事实、后果与时间连续性 | 8 / 10 |
| 角色认知和信息隔离 | 8.5 / 10 |
| 版本、回滚和实验能力 | 8.5 / 10 |
| 普通用户上手 | 4 / 10 |
| GM 裁定能力 | 2.5 / 10 |
| 玩家行动闭环 | 2.5 / 10 |
| 当前可玩 TRPG 程度 | 3.5 / 10 |
| 作为模拟 GM 基础内核的潜力 | 8 / 10 |

## 三、现有能力对模拟 GM 的帮助

### 1. 世界状态不是一次性背景板

TRPG 最怕 GM 每次都临时决定世界状态，导致前后矛盾。当前项目的世界时钟、事件、效果、生活计划、经历和认知链可以作为模拟 GM 的底层事实来源。

例如，理论上可以支持：

- 玩家来到港口时，港口确实处于封锁状态；
- 角色之前已经听到的传闻，不等于所有角色都知道；
- 玩家离线期间，某个事件可能已经改变局势；
- 一个角色的行动会留下持续后果；
- 回滚可以重新尝试某次关键决策。

这部分比单纯让 LLM“扮演 GM”可靠得多。

### 2. 角色认知隔离很适合 GM 的信息管理

GM 必须区分：

- 世界真实发生的事；
- 玩家角色看见的事；
- NPC 知道的事；
- NPC 误以为的事；
- 玩家通过调查得到的线索；
- 只有 GM 知道的幕后信息。

当前认知接口、说法与获知链、角色记忆隔离和多角色披露，已经提供了这类信息管理的基础。对 TRPG 来说，这是非常有价值的，因为调查、误导、传闻和有限视角都依赖它。

### 3. 事件后果和时间线适合承载战役连续性

TRPG 不是每个场景结束后世界重置。当前事件效果、生活计划、角色打算、角色经历和时间推进机制，可以承载：

- 未解决的威胁；
- 延迟发生的后果；
- NPC 的持续行动；
- 玩家不在场时的世界变化；
- 不同选择产生的平行发展。

提交、分叉和回滚尤其适合“试跑一次重大选择，再保留或回退”的单机 TRPG 工具。不过最终产品必须明确回滚是创作者 / 主持人功能，不应破坏普通游戏过程中的因果感。

## 四、TRPG 角度新增的核心缺口

### 1. 当前没有明确的玩家角色和玩家队伍模型

现有系统主要围绕“世界中的角色”和“用户通过联络方式与角色聊天”设计。TRPG 则需要额外区分：

- 玩家本人；
- 玩家控制的角色；
- GM / 旁白；
- NPC；
- 其他队伍成员；
- 世界和环境。

如果用户只是以现实世界的自己和角色聊天，这不等于玩家角色在场。TRPG 需要明确“谁在场、谁能行动、谁知道什么、谁承担结果”。

这是身份模型的变化，不是给聊天框加一个“骰子”按钮就能解决。

### 2. 当前没有结构化的玩家行动入口

普通聊天可以说“我想试着说服守卫”，但模拟 GM 至少需要识别：

- 行动者是谁；
- 想达到什么目标；
- 对谁或什么对象行动；
- 使用什么方法；
- 成功条件是什么；
- 失败可能付出什么代价；
- 行动是否需要骰点；
- 结果会影响哪些世界状态。

当前会话核心主要接收文本、生成回复、固化消息和处理投递，不等于已经有行动声明与裁定契约。叙事层也不能代替它，因为叙事层的职责是组织合法素材，而不是决定玩家行动是否成功。

### 3. 当前没有规则裁定层

TRPG GM 必须对玩家行动做出相对稳定的裁定。至少需要选择一种规则范围：

- 使用现成规则系统；
- 使用项目自己的轻量规则；
- 纯叙事裁定，但明确风险、代价和一致性；
- 由角色卡与世界包声明可执行的能力和效果。

当前代码的事件引擎能够按确定性规则生成世界事件，但这不等于能够裁定“玩家尝试撬锁是否成功”。事件抽样、角色打算执行和玩家主动行动是三种不同来源，不能混为一谈。

### 4. 当前没有场景和可行动局面管理

一个 GM 回复通常不仅要描述发生了什么，还要把玩家放回一个明确的决策点：

- 现在谁在场；
- 环境有哪些重要事实；
- 哪些信息已经公开；
- 当前有什么危险；
- 玩家可以继续做什么；
- 哪些选择会推进时间或触发风险。

当前项目有生活线、地点和事件等数据基础，但还没有面向玩家的“当前场景”或“可行动局面”契约。没有这一层，用户可能得到一段漂亮描述，却不知道自己应该如何继续玩。

### 5. 不能让 AI 替玩家做关键决定

普通 OC 故事可以让角色主动选择行动。TRPG 中则必须区分：

- NPC 自主行动；
- 环境自然变化；
- 玩家角色可以选择的行动；
- 玩家已经明确选择的行动。

系统可以提示风险、提出选项、询问意图，但不能因为模型认为“这样更有戏剧性”就替玩家决定关键行为。否则用户会觉得自己不是在玩，而是在看模型代替自己写同人小说。

## 五、叙事中介层在 TRPG 中会发生什么变化

### 1. 它仍然必要，但不再是核心闭环的全部

普通 OC 方向里，叙事层是把世界素材变成角色故事的关键中介。

TRPG 方向里，叙事层仍然负责：

- 描述玩家行动结果；
- 保持 NPC 表达与认知边界；
- 组织线索和伏笔；
- 让持续后果能被玩家理解；
- 在场景之间回接重要事实；
- 生成符合当前局面的 GM 叙述。

但它必须位于“裁定和状态提交”之后，而不是自己决定事实：

```text
玩家行动
  -> 行动解析与规则裁定
  -> 世界状态 / 事件 / 后果固化
  -> 角色认知过滤
  -> narrative layer 组织 GM 表达
  -> 玩家看到结果和下一可行动局面
```

### 2. TRPG 叙事层要额外保留结果结构

普通故事可以只记录一个叙事单元。TRPG 至少还要保留：

- 玩家声明的原始行动；
- 系统理解的行动意图；
- 使用的规则或裁定依据；
- 随机结果 / 骰点结果；
- 成功等级或失败类型；
- 付出的代价；
- 被改变的世界状态；
- 玩家角色和 NPC 各自知道的部分；
- 当前新的可行动局面。

这些内容不一定全部直接展示给玩家，但它们需要存在，才能解释“为什么结果是这样”。如果完全不保存，长战役很快会出现 GM 前后矛盾。

### 3. “有限编织”要从故事关系变成场景推进

普通 OC 叙事层可以把多个经历编成“她最近一直在处理某件事”。

TRPG 中，编织必须更谨慎：

- 不能为了戏剧性把两个线索强行合并；
- 不能把玩家尚未调查到的真相写进表面叙述；
- 不能把一个 NPC 的推测当成 GM 已确认事实；
- 不能把玩家没有做出的选择补出来。

它更像“把已经裁定的结果放进当前场景”，而不是“自动写剧情”。

## 六、从普通用户角度，TRPG 版本会遇到的体验问题

### 1. 规则复杂度可能压过 OC 创作乐趣

普通用户可能只想说：

> 我让我的角色试着说服守卫。

如果系统要求用户先配置属性、技能、难度、骰池、优势、劣势、资源消耗和行动类型，用户会觉得自己在填表。

因此 TRPG 版必须提供“自然语言行动 + 系统解释裁定”的入口。复杂规则应隐藏在后台；用户至少能看到：

- 我理解你想做什么；
- 这件事有多危险；
- 你可以直接尝试，也可以先调查 / 准备；
- 结果会怎样影响当前局面。

### 2. 必须让用户知道自己是在玩，而不是只是在聊天

当前桌面壳的核心体验是聊天。TRPG 版需要增加非常少但明确的游戏状态，例如：

- 当前场景名称；
- 在场角色；
- 当前目标或问题；
- 已知线索；
- 可继续行动的入口；
- 等待用户决定的状态。

这不等于建立一个复杂的状态面板。只需要让用户知道：现在轮到谁做什么，以及自己可以如何继续。

### 3. 失败必须有意义

如果系统为了让剧情顺利而总是让玩家成功，用户会感觉自己没有真正改变世界。

如果系统让玩家失败，却只回复“失败了”，用户也不知道失败带来了什么。

模拟 GM 至少需要支持：

- 成功；
- 部分成功；
- 失败但获得信息；
- 失败并产生代价；
- 暂时无法裁定，需要补充条件；
- 玩家选择承担风险或放弃。

现有事件效果闭集和后果机制可以作为基础，但需要增加“玩家行动结果”这一来源类型，不能直接复用世界随机事件。

### 4. 回滚的使用方式必须和普通故事不同

普通 OC 用户可能希望经常回滚，尝试不同剧情。

TRPG 玩家通常会把失败和意外视为游戏的一部分。若用户随时回滚，所有后果都可以被撤销，选择就没有重量。

因此 TRPG 版应把回滚定位为：

- 主持人 / 创作者的调试工具；
- 战役分支工具；
- 错误恢复工具；
- 明确开启的“重试场景”功能。

不应让普通游戏流程默认暴露为一个随时可以改写结果的按钮。

### 5. 多角色披露在 TRPG 中变成队伍信息管理

现有多角色披露设计对普通 OC 很有用：角色 A 不自动知道角色 B 的私聊。

TRPG 中它还要处理：

- 队伍公开信息；
- 某个玩家角色私下知道的秘密；
- NPC 对不同玩家的说法；
- GM 只向某个玩家显示的信息；
- 玩家之间是否共享角色视角。

现有隔离、披露和转述机制可以复用，但需要明确“用户是一个玩家还是多个玩家”，以及界面如何避免把私密信息误显示给所有人。

## 七、TRPG 方向的推荐最小产品范围

不建议一开始做完整桌游规则平台。最小可玩的模拟 GM 可以只包含：

1. 一个世界包；
2. 一个或一组玩家角色；
3. 若干 NPC；
4. 一个当前场景；
5. 自然语言玩家行动；
6. 一套轻量的风险裁定规则；
7. 明确的成功、失败、代价和新局面；
8. 角色认知隔离；
9. 事件与后果持久化；
10. 叙事层负责把裁定结果讲清楚。

第一版不必做：

- 全规则书兼容；
- 地图编辑器；
- 自动完整战役生成；
- 全局剧情图谱；
- 复杂战斗网格；
- 每个 NPC 的完整独立 AI 规划；
- 用户可见的复杂内部状态面板。

最小闭环应该是：

```text
GM 给出场景
  -> 用户声明行动
  -> 系统确认理解和风险
  -> 规则裁定
  -> 写入结果与后果
  -> GM 描述结果
  -> 给出新的可行动局面
```

## 八、当前代码可复用部分与必须新增部分

### 可复用

- 世界包与角色卡校验；
- 世界实例锁定；
- 世界时钟和时间线；
- 事件事实与效果；
- 角色认知过滤；
- 经历与记忆；
- 生活线和角色打算；
- 提交、分叉、回滚；
- UMP、会话核心和桌面壳；
- 多角色隔离与披露；
- 叙事层的来源约束、认知后验检查和有限编织设计。

### 必须新增或重新定义

- 玩家角色 / 队伍 / NPC / GM 的身份模型；
- 场景与当前可行动局面；
- 玩家行动声明和行动解析；
- 规则、骰点或轻量裁定器；
- 成功等级、失败代价和风险预览；
- 玩家行动产生的事件来源与状态变更；
- 不替玩家做关键决定的提示与等待机制；
- TRPG 战役保存和恢复语义；
- 私密信息对不同玩家的显示范围；
- 让用户能看懂当前轮到谁行动的界面表达。

## 九、最终判断

如果目标仍是“OC 角色自己生活，我通过聊天慢慢发现故事”，当前项目最缺的是叙事中介层和低门槛创作流程。

如果目标改成“我用自己的 OC 和世界观玩 TRPG，由系统模拟 GM”，最缺的就不只是叙事层，而是玩家行动与规则裁定闭环。

叙事层在 TRPG 中仍然重要，但它应当是：

> 把已经裁定并固化的结果，按照玩家知道什么、角色知道什么和当前场景需要什么，表达成可继续游玩的 GM 叙述。

它不能替代：

- 行动解析；
- 规则裁定；
- 骰点；
- 状态提交；
- 场景推进；
- 玩家选择。

因此，TRPG 方向的产品定位应改成：

> 一个拥有持续运行世界和角色认知系统的单机模拟 GM 核心，逐步补齐玩家行动、规则裁定、场景推进和叙事表达。

从当前代码基础看，这条路线是可行的，而且现有世界运行层比普通聊天模型更适合作为长期战役底座。但在没有玩家行动裁定层之前，项目只能说“适合承载 TRPG 世界”，不能说“已经是模拟 GM”。
