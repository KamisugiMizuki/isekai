# 会话核心层（SESSION_CORE_SPEC）

> 上游总设计：[`DESIGN.md`](DESIGN.md)（总纲） · 本文为「会话核心层」模块设计文档
> 来源：2026-09-19 总设计对话整理拆分（V1.9 收敛内容）；未决细则在模块设计阶段补齐。

本模块职责：会话管理、消息路由、绑定关系（世界 / 角色 / 时间线）、对话上下文隔离、披露管理。

已决定的条目见下；**会话管理与消息路由的细则待模块设计**。

## 一、绑定关系与切换语义

#### 切换语义

| 切换类型 | 影响 |
|---|---|
| 切换世界 | 会话切换到新世界的角色；世界时钟独立；状态独立 |
| 同一世界切换角色 | 会话切换到同一世界内另一角色；世界时钟共享；认知隔离 |

#### 时间线与会话的关系

- 一个会话绑定一条时间线。
- 用户可同时开启多个会话，分别绑定不同时间线。
- 用户可在同一时间线内切换角色（若该时间线所属世界包含多角色）。
- 用户可切换某会话所绑定的时间线。

## 二、对话上下文隔离

#### 隔离原则

- 一个会话绑定一条时间线。
- 对话上下文随时间线隔离。
- 不同时间线的对话历史互不可见。
- 同一时间线内，若未来支持多角色，角色间对话历史按披露机制处理。

#### 切换时间线时的上下文

用户切换会话所绑定的时间线时：

- 原时间线的对话上下文保留在原时间线。
- 新时间线的对话上下文从该时间线已有历史继续。
- 不跨时间线拼接上下文。
- 界面显式标注当前时间线。

#### 设计意图

对话上下文是时间线体验的一部分。用户在时间线 A 与角色讨论过的事，在时间线 B 中不应自动成为共同记忆。这保证了时间线的独立性，也保证了角色认知的一致性。

## 三、披露机制（多角色对话可见性）

### 3.1 多角色与对话历史可见性

#### 实现分期

多角色能力在阶段 5 落地；此前按单角色运行，架构始终预留多角色扩展点。

#### 多角色时的对话历史规则

当同一世界包含多个角色时：

| 规则 | 说明 |
|---|---|
| 默认隔离 | 用户与角色 A 的对话历史，角色 B 默认不可见 |
| 用户主动披露 | 用户主动向角色 B 说明后，相关历史对 B 可见 |
| 角色不主动表露 | 角色之间不会主动向对方透露自己与用户的对话 |
| 披露粒度 | 按用户说明的范围披露，不自动扩散 |

#### 披露机制的含义

- 用户是对话历史的唯一授权者。
- 角色没有“互相通报”的动机或能力。
- 披露是单向的、显式的、由用户发起的。
- 披露后，角色 B 的认知中新增这部分信息。

#### 设计意图

这一机制保证了：

- 用户对多角色关系有完全控制权。
- 角色之间不会形成“信息串联”破坏沉浸感。
- 用户可以选择让角色间“知道彼此”，也可以保持隔离。

### 3.2 披露撤回机制

#### 机制

披露撤回**通过将时间线回滚到某个提交来实现**（不引入独立机制）。

#### 规则

- 披露信息一旦发生，即成为该时间线状态的一部分。
- 不存在“单独撤回某条披露”的操作。
- 如需撤回，用户将时间线回滚到披露发生之前的提交。
- 回滚后，从该提交创建新时间线，或继续推进。

#### 设计含义

- 披露是世界状态的一部分，不是独立可撤销的对象。
- 撤回披露 = 世界回滚。
- 这与版本管理机制统一，不引入额外机制。
- 用户需理解：撤回披露的代价是丢失该提交之后的所有进展。

#### 操作路径

1. 用户找到披露发生之前的提交。
2. 将当前时间线回滚到该提交，或从该提交创建新时间线。
3. 披露信息不再存在于新状态中。
