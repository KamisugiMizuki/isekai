# isekai 普通 OC 用户视角评价草案

> 状态：评价草案，不是产品规范，不代表新增功能已经实现。
> 评价对象：一个对 AI 项目理解不深、电脑使用技术一般，只想创建 OC 与自创世界观并观察故事发展的用户。
> 证据范围：除叙事中介层外，均以当前工作树代码、行为测试和一次真实 CLI 链路为依据；叙事中介层按 `docs/NARRATIVE_LAYER_SPEC.md` 的设计内容预评估。

## 一、结论

isekai 当前更像“可以承载 OC 故事的世界运行内核 + 工程化管理界面”，还不是“普通用户打开后就能轻松创建角色并观看故事发展的应用”。

底层能力已经明显超过普通角色聊天工具：世界有独立时间，事件可以产生后果，角色认知存在边界，记忆和对话可以按角色与时间线隔离，实例可以提交、分叉和回滚。这些能力已经通过真实代码和行为测试落地。

但普通用户最关心的“我创建的角色接下来会怎样”“她为什么现在提起这件事”“几个片段怎样连成一段故事”，目前仍缺少叙事中介层。现有主动表达链路主要从角色已获知且仍在时效内的素材中选择单件内容，尚不能稳定形成跨轮回接、有限编织和持续故事线。

综合评价：

| 维度 | 草案评价 |
|---|---:|
| 世界观数据结构 | 8.5 / 10 |
| 世界持续运行能力 | 8 / 10 |
| 角色认知边界 | 8.5 / 10 |
| 数据隔离、提交与回滚 | 8.5 / 10 |
| 普通用户易用性 | 4.5 / 10 |
| 当前故事感 | 4 / 10 |
| 叙事中介层设计潜力 | 8 / 10 |
| 当前作为 OC 故事工具的完成度 | 5 / 10 |

上述分数是产品视角判断，不是自动化测试分数。

## 二、当前代码已经提供的价值

### 1. 不是单纯把角色卡塞进 Prompt

当前代码已经包含世界设定层、世界运行层、事件引擎、记忆系统、版本管理、会话核心和桌面壳。行为测试实际结果为 `355 passed`，并使用真实 WebSocket 与真实 SQLite，只替换 LLM。

本地运行数据中可见：13 个实例、16 条时间线、1734 个事件、5665 条经历、29 条消息、20 条记忆和 7 个提交快照。这证明项目不是只有设计文档，世界运行与持久化链路已经产生真实数据。

### 2. 角色不是全知的

认知接口按实例、时间线、角色和已完成水位提供可接触信息。事件事实、公共说法、角色获知、亲历观察和后续经历被分开处理。不同角色可以知道不同内容，用户披露也不会自动复制另一角色的全部记忆。

对于 OC 用户，这意味着角色不会只是从同一份世界百科中回答，而有机会形成各自的视角、误解和信息差。

### 3. 世界后果可以持续影响生活

事件效果带有失效方式，并可以进入后续活动和前置条件。角色打算可以处于等待、行动、延期或放弃状态；生活计划和实际经历分开；死亡后不再继续生成普通计划与经历。设计目标不是每轮随机发一个事件，而是让事件留下后果。

### 4. 时间线和回滚适合 OC 创作

用户可以保留不同发展方向，尝试一次选择后回到旧提交，或从旧提交分叉出另一条线。回滚语义还考虑了延迟任务、旧世代结果、成员资格、待执行事件和未投递消息，避免简单复制数据库造成幽灵状态。

## 三、普通用户会遇到的主要问题

### 1. 创作入口仍然像配置管理台

桌面界面提供世界包、角色卡、实例、草稿、补卡、时间线、激活、倍率、提交、回滚、披露、备份和设置等功能。对熟悉工具的人，这是完整控制能力；对普通创作者，它会带来三个问题：

- 不知道第一步应该做什么；
- 不理解“世界包”“世界实例”“时间线”的区别；
- 只是想开始聊天，却先遇到确认、选择和激活流程。

未来需要把复杂概念隐藏在创作向导背后，而不是删除底层能力。普通用户只需要看到“创建世界”“创建角色”“开始生活”这样的入口；高级用户再进入时间线和版本管理。

### 2. 世界内部过于黑箱

项目有意不直接展示事件日志、性格数值、认知条目、记忆内容和内部 diff，这能保护沉浸感。但如果完全没有创作者向反馈，用户无法判断设定是否生效、角色为何这样说、最近是否真的发生了事情。

更合适的不是开放数据库，而是提供自然语言级创作反馈，例如：

- “她最近经历了一件和港口封锁有关的事。”
- “她还没有听说北岸的消息。”
- “这个世界目前没有新的可讲述进展。”
- “你上次的选择已经改变了她接下来的日程。”

### 3. 世界会运行，不代表故事会自动变好看

`runtime/proactive.py` 当前主动素材选择主要检查：角色是否已获知、素材是否在时效内、是否已消费、是否睡眠、是否归档、是否有主动额度。它能避免越权和重复，但还不能稳定处理：

- 旧话题回接；
- 多个经历组成一段故事；
- 角色只愿意讲一部分；
- 角色暂时不想讲；
- 一个持续问题在多轮对话中逐渐发展。

`runtime/intents.py` 中的 `story_units()` 是围绕角色打算和行动事件的组合视图，不等于完整的叙事中介层。

### 4. 真实链路仍有后台异常

本轮真实运行 CLI 成功完成核心启动、WebSocket 连接、回复生成、固化和投递回执，但日志同时出现：

```text
ERROR memory settle failed
RuntimeStateError: 时间线没有时钟记录：main
```

这是阶段 0 占位会话在记忆结算时访问不存在世界时钟导致的后台错误。它没有阻止本轮回复，但说明“用户表面看到成功”与“后台全部收尾成功”还不是同一件事。长期使用时，这类错误可能表现为角色记忆偶尔没有写入。

### 5. 文档状态仍有滞后风险

总纲、README、各模块 SPEC 和当前代码的状态说明并非全部同步。一些 SPEC 仍保留“尚未实现”的旧状态，而总纲和审计记录已经说明对应模块部分或大部分完成。普通用户不应被要求自行判断这些文档冲突，最终产品入口需要只呈现经过核对的当前能力。

## 四、对叙事中介层的预评估

`NARRATIVE_LAYER_SPEC.md` 明确说明该层尚未实现，因此以下不是现成功能评价。

### 设计中值得保留的部分

1. 叙事层只消费角色合法可见的经历、说法、处境和记忆，不拥有事实写权限。
2. 故事感只影响候选排序，不驱动世界事件，不补造秘密、责任人、因果或结局。
3. “未解决”是合法结果，不要求每个故事单元都有高潮和完整收束。
4. 设计明确区分“发生了什么”“角色知道什么”“角色愿意讲什么”。
5. 候选、叙事单元、表达取舍、消费记录和审计结果都考虑了水位、回滚、分叉、重启和投递失败。
6. 后验检查不应只靠关键词，而要检查来源身份、获知时刻、确定性、范围、关系类型和当前处境。

### 需要在实现时守住的边界

- 不要让模型同时负责找素材、判断因果、决定意愿、组织故事和保证权限。
- 时间、水位、成员资格、来源引用和未来计划等内容优先使用程序硬校验。
- “同时发生”不能自动写成“因为某事所以某事”；编织需要结构化关系类型。
- 后验 LLM 审计不能取代来源和时间关系的硬校验。
- 叙事层应被定位为“叙事连续性和认知边界中介”，而不是自动编剧。

### 对用户体验的关键意义

没有叙事层，项目更像“世界状态查询器”：用户能问到发生过什么，但不一定感觉角色正在生活。

有了一个保守实现的叙事层，系统才可能把：

- 当前活动；
- 刚完成经历；
- 仍有效的后果；
- 角色未竟打算；
- 最近共同话题；
- 角色愿意表达的范围；

组织成用户能理解的自然入口。

## 五、最终判断

这个项目值得继续做，但当前最准确的产品定位是：

> 一个已经具备世界运行、角色认知、事件后果和版本管理能力的 OC 世界内核，正在补上把运行素材转化为连续故事体验的叙事层。

它还不适合直接交给不懂技术的用户，让用户完全自行理解世界包、实例、时间线和倍率。要成为真正的 OC 故事工具，优先级不是继续增加更多内部模拟字段，而是：

1. 把首次创作流程压缩成向导；
2. 修掉真实链路中的后台收尾异常；
3. 实现保守的候选排序和有限编织；
4. 给创作者提供不泄漏内部数据的自然语言反馈；
5. 用真实模型验证“发生了什么 / 角色知道什么 / 她愿意讲什么”能够保持区分。
