## 第 1 批：纯成本优化（不改语义，可立即做）

### T1-A1 记忆衰减：从「每批全量」改为「只结算本批到期」

- **原状**【实测/代码确证】：`store.memory_decay`（`store.py:4700-4725`）每批把 `decay_world` 推到**本批批界**（`:4722`），
  下一批批界更大 ⇒ `decay_world < to_world` 对**全部在位记忆**再次成立 ⇒ **O(在位记忆 × 批数)**。
  调用点在批循环内（`service.py:2891`，经 `service.decay_memories`）。实测 8000 条在位记忆 **+45~56 ms/批**。
- **改动**：引入**结算下界**。`decay_world` 只推到「本批批界」，但查询加上**只取尚未结算过的区间**：
  用 `decay_world < to_world` 之外再加一个**按时间排序的游标**（`ORDER BY decay_world` 已有，走 `ix_memory_timeline_decay`），
  并**限制单批处理量**（本批新到期 + 有界追赶）。关键：**同一次 advance 内不重复处理同一行**（记录本批已结算的 `decay_world` 上界）。
- **落点**：`store.py`（`memory_decay` 的 SQL 与循环）、`service.py:2891`（传批界与已结算下界）。
- **测试**：`tests/test_memory.py`、`tests/test_runtime.py`（衰减幂等 / 分批等价）。
- **验收**：8000 条在位记忆下每批 ≤ 2 ms；同一水位重跑幂等；小步与批量结算**结果等价**（新增断言）。
- **风险**：强度成为惰性值 ⇒ 所有读 `memory.strength` 的消费者必须走同一结算函数（见 T1-A1 的补充：统一读入口）。
- **状态**：**已完成**（2026-10-10）。实现：`memory_decay(limit=...)` + `memory.effective_strength/effective_state` + `rank` 惰性 + `memory_cite` 先结算再强化；实测 +43 ms → **+1.05 ms**。

### T1-A2 活跃后果集：单表维护 + 索引下推 + 只取本批到期

- **原状**【实测/代码确证】：`effect_window`（`store.py:5169-5185`）取 `active=1 AND from_world<=?`，**上界只由「已解除」决定**；
  默认 `expiry = until_cleared`（`events.py:209-211`）⇒ 未解除的后果永久留在候选集。
  用量：`_collect_batch` 对**每个角色**做 Python 过滤（`service.py:3014-3019`），`_propagate_and_clear` 再整体遍历（`:4161-4178`）。
  实测第 1520 日 **4,019 活跃 / 7,930 行**，profile 中 `region_of` **7,993 次/批**。
- **改动**：① `effect_window` 的 `targets` 参数**下推到 SQL**（`AND target IN (...)`），并加 `(instance_id, timeline_id, active, target)` 覆盖索引；
  ② `_collect_batch` 改为**按角色下推查询**（或每批取一次后按 target 建倒排字典，避免每角色全扫）；
  ③ `_propagate_and_clear` 只取**本批可能到期**的集合（`expiry='with_cause'` 且 `from_world + day <= to_world`，或 `natural_recovery` 同族有后续）。
- **落点**：`store.py`（`effect_window` + 建索引）、`service.py:3014-3019`、`service.py:4161-4178`。
- **测试**：`tests/test_events.py`、`tests/test_runtime_audit.py`、`tests/test_audit_fixes.py`。
- **验收**：第 1520 日每批不再出现全量 `region_of`；活跃后果集规模有界；**同一水位下后果的解除时刻与分批方式无关**。
- **风险**：「活跃集合」成为新的一致性边界 ⇒ 必须加一致性断言（活跃集合 ≠ 由事件推出的集合时报审计错误）。
- **状态**：**部分完成**（2026-10-10）。已做：`targets` 下推 + `ix_effect_target` 倒排 + `effects_due` + `ix_effect_expiry`（去掉 7,993 次/批的 `region_of` 与全部活跃后果遍历）。
  **未做：「活跃集合有界」**——实测第 1500 日活跃后果 4,337 条（4,334 为 `until_cleared`），它们按设计必须继续参与因果，
  所以「每批仍要碰 4,300+ 条」。这条**与 B-7 退休契约同源**，见「本轮实施记录 · 关键发现」。

### T1-A3 `reaction`：只取「可能迁移」的行，`expired` 有归档出口

- **原状**【实测/代码确证】：`store.apply_runtime_batch` 每批 `SELECT * FROM reaction WHERE timeline_id=?` **全表**（`store.py:3400-3402`），
  逐行 `_row_to_dict` + `reaction.advance`（`:3404`）。实测第 1520 日 **3,042 行全部仍是 active**。
  代码注释自陈「行数少，直接全算」（`store.py:3399`）。
- **改动**：**只改取数，不改判定**。`reaction.advance` 是纯函数，凡 `stage` 仍可能被它改变的行**一个都不能漏**：
  `candidate / adopted / active / fading`（以及调用方显式写 `paused` / 转长期的行）。
  在此基础上按 `(timeline_id, stage, started_world)` 走已有 `ix_reaction_stage` 下推；
  并给 `expired` 一个退出途径（归档 / 移出热表）。**禁止**用「只取 candidate/adopted/active」换速度。
- **落点**：`store.py:3399-3420`、`runtime/reaction.py:16`（阶段闭集作为单一真源）、`store.py:493`（索引）。
- **测试**：`tests/test_reaction.py`（若缺则补）、`tests/test_runtime.py`。
- **验收**：每批读取行数 = **可能迁移的行数**；`fading → expired` 的迁移在分批与整批下都发生且只发生一次。
- **风险**：全表重算隐含「纠正历史脏数据」的作用，改增量后旧脏数据不再自愈 ⇒ 加一条一次性审计断言。
- **状态**：**已完成**（2026-10-10）。只改取数不改判定：条件含 `candidate(已到水位)/adopted/(active,fading 且依据被解除)`，新增稳定排序；全量测试绿。

## B-2 / B-4 对比裁决书（裁决第 3 项：先给对比）

两项都**不是「实现难」，而是「规格立场」问题**：动了它们，就是在改「这个世界模拟什么、不模拟什么」的边界。

### B-2 关系模型（角色 ↔ 角色 / 角色 ↔ 组织）

**冲突原文**：`MEMORY_SPEC.md:134`「深度语义归并与其他整合可选，依据实际表现评估，**不引入用户模型 / 关系模型**」；
`WORLD_RUNTIME_INTERFACE_SPEC.md:566`「资源量与关系变化在闭集里没有对应项，如实 `rejected`」。

**现状的代价**：角色之间**零字段**——最近似物只有 `disclosure`（信息授权边，不是社会关系）与
`reaction.tendency`（自由文本，不可查询、不可比较）。**社会拓扑是星形**：所有角色只与用户相连，
角色之间没有边。而「世界为主体」要求角色生活在**同一个社会**里。

| 方向 | 做法 | 代价 / 风险 |
|---|---|---|
| **A 保持现状** | 关系继续不进闭集，只走 `knowledge_change`（说法） | 零风险、零工作量；但「同一个社会」在结构上永远表达不出来。社会性只能靠叙事文本暗示 |

## 第十三轮实施记录（2026-10-10 续 · B-5 的裁决与「不可半做」的判定）

**B-5 是什么**：致死与致伤进效果闭集（`casualty`：程度档 + 恢复条件 + 失效方式，**不是健康值系统**）。
规格依据明确——`EVENT_ENGINE_SPEC.md:125` 本就写明「身体类效果只按题材选择受支持的闭集（例如受伤、疾病或疲劳）」，
**规格允许受伤，是实现漏项**。

**本轮核对到的关键事实（决定了它不能半做）**：

| 落点 | 形态 | 含义 |
|---|---|---|
| `world/validate.py` `SUPPORTED_EFFECTS` | 8 类白名单 | 只是**校验入口** |
| `runtime/events.py` `EFFECT_PRIORITY` | 8 类优先级 + `DEFAULT_EFFECT_PRIORITY = 0` | 未列出的类**静默取 0**，不报错 |
| 各消费者 | `source_delay` / `rumor_spread` / `activity_constraint` / `route_blocked` / `environment_state` / `institution_state` / `custom_state` / `public_notice` **各有专属消费路径** | 效果类是**一整类的完整实现**，不是一个枚举值 |

⇒ **只把 `casualty` 加进闭集，会得到一个「包能声明、校验能通过、但没有任何东西消费它」的空效果**——
这与 A-9b（`+ []` 空列表静默丢弃打算行动的环境效果）是**同一类错误**：看着接了，实际不生效。
所以**我不做「只加枚举」的半版本**。

**裁决（提出，待复核）**：B-5 按**一整片**落地，三个部分必须同时到齐：

1. **声明**：`casualty` 进 `SUPPORTED_EFFECTS` + `EFFECT_PRIORITY`（档位取大于 `route_blocked=80`，
   因为死亡应压过通行受阻），取值域是**枚举**`轻伤/重伤/失能/死亡`——**不引入任何数值**（验收 ④）；
2. **消费**：程度档 → 生活线约束（沿用 `activity_constraint` 的效果范式）；死亡 → **与 `character_state.archived`
   同批原子置位**（复用既有死亡路径，验收 ②）；
3. **可解除 / 可恢复**：复用既有 `expiry` 三态（`with_cause` / `natural_recovery` / `until_cleared`），
   **不新建恢复机制**（验收 ①）。未声明的效果仍被拒绝（验收 ③）。

**规则版本登记（第三档：改语义）**：世界死亡率会上升 ⇒ **同种子不再产出同一世界** ⇒ **必须走规则版本**，
不能无版本合入。`WORLD_RUNTIME_INTERFACE_SPEC.md:44-53` 的边界不变：核心只提供
「可被裁定结果声明的后果」，**不提供伤害公式、属性、回合**（那是 TRPG 规则插件的事）。

**人工复核点（关键）**：`casualty` 的「程度档」极易被扩成 HP 系统（设计文档已标为**原则冲击**）。
建议在规格里写死一句：**「`casualty` 只接受枚举档位，核心不得据其推导任何数值型健康量，也不得随世界时间自动恶化」**——
这样 B-5 不会成为 HP 系统的入口。是否接受这条约束，请你裁定。

## 第九轮实施记录（2026-10-10 续 · A-4 第一片）

**改了什么**：`maybe_auto_commit` 在原有两条触发（现实 `autocommit_minutes`、或新增事件 `≥ autocommit_events`）
之外加一道**现实时间下界** `autocommit_min_gap_seconds`（默认 30 s，配置项已落到 `config.py`）。
原因：事件数阈值在**高倍率下每批都满足**，于是「一次推进」里反复触发提交，而提交是

| 配置 | 提交次数 | 墙钟 |
|---|---|---|
| `min_gap=0`（原行为） | **10** | **30.84 s** |
| `min_gap=30s`（新默认） | **1** | **0.72 s** |

⇒ 提交次数与墙钟都 **下降约 43×**。注意绝对值：这份 1500 日实例上**单次提交约 3 s**（`commit_log` 只增，
每次全量 dump + 物化），所以「每批提交一次」在高倍率下是**数量级**的开销，不只是几十毫秒。

**回归**：`pytest -q` = **621 passed / 46.2 s**，failure 0。

## 第八轮实施记录（2026-10-10 续 · A-9a 的实测判定）

**A-9a 的原始要求**：`intent.strength` 写入但 `decide` 不读，优先级实际由「遍历顺序 + `MAX_LIVE_INTENTS=3`」隐式决定；
要求把 `strength` 作为**谓词门比较输入**（不做总效用）。

**动手前先测「它今天能不能产生影响」**——对 1500+ 世界日的真实例统计打算分布，结果是决定性的：

```
('cc-堤禾', 'done', 1)
('cc-潮生', 'done', 1)
每角色「可行动/在办」数量（adopted+waiting）：空
```

即：**每角色只有 1 条打算，且已完结**。竞争集合为空 ⇒ **`strength` 在当前内容下不可能改变任何结果**。

**结论（写进清单，避免以后重复分析）**：

1. **今天不做**：实现 `strength` 谓词门在当前内容上**零观察差异**，却要走「改语义 + 规则版本」的完整发布流程——
   这是为仪式感付真实成本。
2. **但它是一条真实的**潜在**缺陷**，不是幻觉：`MAX_LIVE_INTENTS = 3` 允许 3 条在办，
   `planning.propose_intents` 也可能产出多条；一旦出现「同角色 ≥2 条可行动打算」，
   当前的「遍历顺序 + 上限」就是**不可解释的优先级**——正是 §3.2 B-1 规则树口径要消灭的东西。
3. **落地条件（触发即做）**：当同一角色出现 **≥2 条 `adopted`/`waiting`** 的打算时，
   必须把 `strength` 落成**谓词门的比较输入**（`intent_list` 已支持 `stages` 下推，排序键用
   `(-strength, id)` 保证确定性），并随规则版本发布。
4. **可测的落地前检查**：本清单的接续表里保留 `intent.strength` 的触发条件；
   实现时先加一条「同角色 ≥2 条在办打算」的行为测试（当前无此场景），否则改动无法被验证。

**人工复核点**：A-9a 由「待做」改为「**经实测判定当前无可观察影响；触发条件已写明**」。
如果你希望它现在就落地（例如为了让规则树口径一次成型），请告知，我会连同规则版本与行为测试一起做。

## 第七轮实施记录（2026-10-10 续 · A-9d 的评估与结论）

**A-9d 的原始要求**：把 `decay_memories` / `apply_due_pending_events` 从批事务**之外**移进
`store.apply_runtime_batch` 的同一事务，理由是「失败时不留下半批状态」。

**动手前先验证前提，结论是「不该改」**：

1. **两个操作都幂等且自愈**：
   - 记忆衰减从每行自己的 `decay_world` 起算，衰减**指数可组合** ⇒ 晚结算与逐批结算数值等价；
   - 预约事件用**稳定事件 id** 写入、INSERT 走 `ON CONFLICT DO NOTHING`、状态置位幂等 ⇒ 重跑不会重复施加。
2. **崩溃窗口的后果是「最多一批的延迟」，不是「半批状态」**——而这批延迟下一批自动补齐。
3. **反向成本真实**：把两者并入批事务会**拉长单事务的锁持有时间**，而推进的预算正是 200 ms 级（§2.6）；
   为消除一个「自愈的延迟」去吃掉确定性推进的时间预算，是负收益。

**验收（已落地）**：新增 `tests/test_advance_atomicity.py`——把后置衰减换成 no-op 推进一批（模拟「批已提交但后置没跑」），断言：
窗口内**读路径仍按当前水位惰性结算**（不会读到过期强度）；恢复后**一次补齐**到新水位且 `decay_world` 推进到位，
最终值与「从未跳过」逐值等价。

**回归**：`pytest -q` = **621 passed / 46.9 s**（620 + 1）。

**人工复核点**：A-9d 由「待做」改为「**已评估：不改，理由与证据如上下**」——

## 第二十四轮实施记录（2026-10-10 续 · B-7 受控 A/B：**判定为净负收益，默认停用**）

## 第三十四轮实施记录（B-1 v1：压力标量 → 候选权重，**写死线性形式**）

**关键设计取舍（决定了这一项的规模）**：v1 把压力量定义为**由世界时间确定的纯函数**
（`value = clamp(初始值 + drift × 世界日, 下限, 上限)`），因此
**不需要新增状态域、不需要持久化、也不需要注册表登记**，且天然满足确定性。
「由**事件效果**改变压力量」（需要持久状态 + A-7 登记）明确留给 v2 并写进清单。

**改动**：

**权重形式写死**：`weight = base × (1000 + k × pressure) // 1000`，`k` 是**千分比整数**，下限 0。
**`pressure` 只允许 `id` 与 `k` 两个键**——多一个键就拒绝。

> 为什么这条守卫重要：可自由编写的 `weight_expr` 等于在核心里开一个**脚本引擎入口**，
> 与「不做 HP 系统」是同类的滑坡。所以 v1 连「表达式」这个词都不引入，只留一个整数系数。

**测试**（`tests/test_pressures.py`，9 项）：纯函数确定性 + 区间夹取 / 写死形式（含未声明时**逐值不变**）/
权重不为负 / **机制真的生效**（逐日序列发生变化）/ 合法声明通过 / **多一个键即拒**（表达式入口）/
未声明引用被拒 / 非整数系数被拒 / 初始值越界被拒。

**过程中两个自我纠错（都写进测试注释，避免以后重犯）**：
1. `pressure_ids` 在模板校验函数里**不在作用域**（我把它加在了名册校验函数里）⇒ 改为本地取集合；
2. 「机制生效」那条测试首版比较**集合** → 两种情况下集合都是 `{et-a, et-b}`，永远相等。
   实为**测试设计错误**（比较集合太粗，且两个模板同系数调制会等比缩放、分布本就不变）。
   改为比较**逐日序列**并只对一个模板声明压力。

## 第四十七轮实施记录（读代码：弄清 A-4「增量物化」到底该改哪里）

**先读实现、再动手**（本轮不写生产代码）。链路如下：

| 环节 | 现状 |
|---|---|
| `service.commit`（`service.py:691`） | 调 `versioning.snapshot_of(...)` 取一致快照，再 `store.commit_add(record, snapshot=...)` |
| `versioning.snapshot_of` | **全量**：`runtime_dump`（26 分节）+ 该线**全部对话原文**（`history_page(limit=10000)`）+ 种子/规则版本元数据 |
| `store.commit_snapshot_*` | **差量在这里**：`SNAPSHOT_DELTA` / `MAX_DELTA_CHAIN` / `commit_snapshot_compress`（链超长时把某条物化成 `SNAPSHOT_FULL`，物化结果逐字段相同，且**不删祖先**——别的线引用的祖先照旧可读） |

**所以「增量落盘」已经实现了**（delta + 定期压缩 + 祖先可读性保护），
A-4 原文里的「增量物化」真正指的是**另一件事**：**每次提交都要先全量构造那份快照字典**
（`runtime_dump` 127 ms + 全量对话），再在存储层把它压成差量。
⇒ 优化点是「**直接算差量，不做全量物化**」，而不是「让落盘变成差量」。

**这一点很关键**：如果按字面去做「增量物化」，会去改已经实现好的存储层——白改。
本轮读代码的价值就是**避免一次方向性错误**（与前几轮 B-7、S-2 的教训同类，但这次在动手前就挡住了）。

**A-4 的准确剩余项（重述）**：
1. **避免全量构造快照字典**：按分节与上一条提交做增量，只取变化的分节/行（不动存储层的差量机制）；
2. **移出心跳同步路径**：提交不再卡在心跳里同步做完（`0.5 s` 的停顿对 1.0 s 时间盒是可观的）。

**不变量（动手前必须写进验收）**：① 重建出的快照与现状**逐字段相同**（存储层差量与 `commit_snapshot_compress` 都依赖这一点）；
② `MAX_DELTA_CHAIN` 与压缩路径不受影响；③ 回滚所用的基准快照仍可读；④ **不改语义**（第一档）。

### 4. 决定性发现：那条 UPDATE **用不上主键索引**

```
旧写法 WHERE id=? AND timeline_id=? AND active=1 AND (? IS NULL OR instance_id=?)
        → PLAN: SCAN effect_state                                  （全表 8,846 行）
新写法 WHERE instance_id=? AND id=? AND timeline_id=? AND active=1
        → PLAN: SEARCH effect_state USING INDEX sqlite_autoindex_effect_state_1
```

`instance_id` 被 `OR` 包住 ⇒ SQLite 无法把它当作索引前缀。该语句每批要跑 **2.4–2.9 条**
⇒ 约 **1.0 ms/世界日（占墙钟 ≈24%）**，纯粹是「每解除一条后果就整表扫一遍」。

**改动（第一档，不改语义）**：`store.apply_runtime_batch` 的 `clear_effects` 分支按
`instance_id_` 是否在场分两条语句——在场走主键全列等值，缺省时保留原来的兜底分支。
调用方 `service._propagate_and_clear`（`service.py:4356`/`:4362`）**本来就一直在传 `instance_id`**。

**第二条同类缺陷**：`reaction` 的阶段推进取数
`WHERE timeline_id=? AND stage IN ('active','fading') AND source_ref IN (…)`
只有 `(timeline_id, stage, started_world)` 索引 ⇒ 要**逐行过滤 3,406 条 active/fading**（返回 0–6 行）。
加 `CREATE INDEX ix_reaction_source_ref ON reaction(timeline_id, source_ref)`：

| | 计划 | 单条（7 轮 × 100 次中位数） |
|---|---|---|
| 加索引前 | `SEARCH … ix_reaction_timeline_stage (timeline_id=? AND stage=?)` | **0.4172 ms** |
| 加索引后 | `SEARCH … ix_reaction_source_ref (timeline_id=? AND source_ref=?)` | **0.0187 ms** |

⇒ **22.3×**。这条索引**默认创建**（S-4 的原则是「没有查询命中才是纯维护成本」——它有明确命中）。

## 第六十轮实施记录（**B-1 v2 落地**：由事件效果改变压力量 —— 累积增量 `Δ`，仍不给表达式）

**裁决书**：`docs/worldruntime/B1_V2_RULING_PRESSURE_STATE.md`（**先写后改**，本轮）。上游裁决见本文件第 401 行。

### 1. 设计（决定了规模的那个取舍）

| 项 | 决定 | 理由 |
|---|---|---|
| 存什么 | `pressure_state` 存**累积增量** `Δ`，不是绝对压力值 | 生效值 = `clamp(基线 + Δ, 下限, 上限)`，**基线仍是 `events.pressure_values` 单一真源**，不把 v1 公式复制成第二份实现 |
| `Δ` 从哪来 | 由**既有后果**（`effect_state` 里 `kind='pressure_change'`）确定性地折算 | 不新建第二事实源；后果行随回滚清空 ⇒ `Δ` 自然回到当时值 |
| 写法 | **覆盖写**（`ON CONFLICT DO UPDATE`），不是累加 | `Δ` 是后果的纯函数 ⇒ 重算幂等；「同一条后果算两次」在结构上不可能 |
| 权重 | **一个字都不改**（仍 `base × (1000 + k × pressure) // 1000`） | v2 只改 `pressure` 的**来源**，不引入任何表达式能力 |
| 效果 schema | `pressure_change` 只允许 `{kind, target, value}`，**多一个键即拒** | `target` 必须是已声明的压力量；`value` 必须是整数增量，且 `abs(value) ≤ 声明域宽度`（一条效果不得把世界掀翻） |

### 2. 改动（六处，缺一即「建了表没人写」）

| # | 落点 | 内容 |
|---|---|---|
| 1 | `store.py` | 新表 `pressure_state`（主键 `(instance_id, timeline_id, pressure_id)`）+ `pressure_list`（按线取 Δ）+ `pressure_apply`（幂等覆盖写） |
| 2 | `store_state_domains.py` | 按 A-7 纪律登记进 `CLEARED_ON_ROLLBACK`（**守卫会拦**，漏登记直接红灯）——已通过 |
| 3 | `runtime/service.py` | `advance` 接上**写入方**：`_pressure_delta`（折算）+ `pressure_apply`；并把 Δ 传给事件规划 |
| 4 | `runtime/events.py` | `pressure_values` / `draw_slot` / `plan_day` 接受可选 `pressure_delta`，并入基线与夹取；**缺省 ⇒ 与 v1 逐值相同** |
| 5 | `world/validate.py` | `pressure_change` 进 `SUPPORTED_EFFECTS`；`EFFECT_PRIORITY["pressure_change"] = 65`（在 `environment_state` 之上、`casualty` 之下） |
| 6 | `world/validate.py` | 效果校验：只允许 `kind/target/value`；`target` 必须在 `pressures[]` 里声明；`value` 必须是整数（**拒绝 float / str / bool**）；`abs(value)` 不得超过域宽；并让 `pressure_change` **豁免**「target 必须是在册对象」那条通用检查（压力量有自己的命名空间） |

### 3. 端到端测试抓到一个真缺陷（**单元测试抓不到**）

首版 `advance` 在给 `effect_constraints` 下推 `targets` 时（方案①的既有优化），
集合只由「角色 / 角色位 / 区域 ∪ 打算声明的效果目标」组成——**不含压力量**。
于是那条 `target IN (...)` 把 `pressure_change` 后果挡在取数之外，`active_effects` 是空的，
`pressure_state` **永远不会有行**——「表建了、写入方拿不到数据」，正是 A-9b 那一类错误。

**修法**：把**已声明的压力量**也并进下推集合（它们有自己的命名空间，且只被 `pressure_change` 消费）。
**这是「端到端测试比单元测试值钱」的实例**：`pressure_apply` / `pressure_list` / `_pressure_delta`
的单元测试**全部是绿的**，只有走真实 `advance` 的那一条才把它暴露出来。

## 第六十一轮实施记录（**B-3+B-9 v2 落地**：账本**推导式** —— 声明式纯函数，推导值**不落库**）

**裁决书**：`docs/worldruntime/B3_B9_V2_RULING_LEDGER_DERIVED.md`（**先写后改**，本轮）。
上游裁决见本文件第 402 行（「先做账本 + 点名规则，**推导式缓一步**」）——本轮做的是被缓的那一步里的**推导式**；
**阈值累加器挂钩点仍然缓做**（它需要「阈值」这个新概念，属另一项裁决）。

### 1. 设计（决定了规模的那个取舍）

| 项 | 决定 | 理由 |
|---|---|---|
| 形态 | `derived[]` 声明 `{id, scope_kind, scope_id, op, a, b, scale, unit}` | 与 `ledger[]` 同段同形，作者不必学第二套语法 |
| 算子 | **闭集只有四种**：`和` / `差` / `积` / `比` | 可自由编写的表达式 = 在核心里开一个脚本引擎入口（与「不做 HP 系统」「不给 `weight_expr`」「不引入坐标」同一条滑坡） |
| 推导值 | **不落库、不进快照、不被推进读取**；`ledger_derived(...)` 读时算出 | **单一事实源**：账本数字只能经 `ledger_put` 变更；落库会制造第二份可被写坏的事实 |
| 引用 | 只允许引用**存储键**或**更早声明的**推导键 | 结构上无环 ⇒ 单趟求值、不需要拓扑排序或迭代收敛 |
| 除零 | `比` 的分母为 0 ⇒ 回 **0**（不抛错） | 账本要能被稳定读取，0 是「无意义值」的保守表达 |
| 多余键 | **一律拒绝**（`expr` / `formula` / `sql` …） | 同一条纪律：不给表达式语言 |
| 与存储键重名 | **拒绝** | 重名会让「哪个是真的」不可解释 |
