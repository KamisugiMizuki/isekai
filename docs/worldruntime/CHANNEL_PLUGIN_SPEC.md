## 一、模块职责与边界

**职责**：统一消息出入口、能力适配、插件宿主、进程生命周期与协议兼容。

- 内容生成不依赖具体通道；适配器不参与世界事实、角色认知或时间线管理。
- **UMP 只承载消息流**，不出现世界实例、核心会话或时间线内部标识，不传提示词、中间推理、记忆简报或实情。
- 内建聊天与第三方插件走同一消息语义；官方壳的管理权限另行认证，不因自称 builtin 获得。
- 核心不依赖任何插件；停用或卸载通道不删除角色历史。

## 二、统一消息协议（UMP）

### 2.1 原则与信封

同一信封可承载于 stdio 或本地 WebSocket；v1 基线仅文本、非流式，先完整校验再发最终回复；
**附件与流式 2026-09-22 落地为可选能力位**（§七）：增量 `reply_delta` 只是预览，正文仍以校验后的最终 `reply` 帧为准。

```json
{
  "ump": "1.0",
  "type": "user_message",
  "id": "e-8f3a1c",
  "ts": 1789803972.99,
  "thread": {"id": "dm-42", "binding_token": "route-17"},
  "payload": {"text": "今天过得怎么样？"}
}
```

- `id` 为信封标识；`ts` 是发送方现实时间戳，仅用于展示 / 诊断，不决定世界时刻、倍率归属或权限。
- `thread` 是通道侧不透明标识，消息 / 回执 / 重试必须携带；握手、心跳等连接级信封不要求 thread。
- 字段类型、必填、枚举与最大长度须在解析时校验；未知必要类型报协议错误，不拿自由文本执行管理操作。

### 2.2 持久身份、顺序与幂等

- **连接是临时承载，不是通道实例身份**。核心给安装 / 配置的通道实例持久身份，重连继续使用；插件名与 hello 自报信息只是元数据。
- 握手完成后核心持久记录协商结果：协议版本、能力交集、限额、通道实例、绑定版本与连接世代。连接断开只使承载失效，不清除该结果；插件升级、核心升级或能力声明变化必须重新握手并重新确认交集。
- 路由键为「已认证通道实例 + thread」；入站去重键再加 `id`。不同插件可以使用相同 thread/id 而不互相冲突。
- 用户消息与重试还须回传核心签发的、不透明 `binding_token`；它只表示 thread 当前有效绑定，不含世界 / 角色标识，也不代替认证。握手返回已有 thread 的令牌；管理面初次绑定或换代时经 `binding` 通知更新，普通断线重连保持令牌。
- 重绑、目标回滚 / 冻结 / 删除时令牌换代或撤销；旧令牌的排队消息即使此前未被核心接受，也必须拒绝，不能套用新绑定。客户端保留原令牌，不自动给旧队列换上新令牌；用户确认重新发送才作为新输入。
- 用户消息与处理状态持久化后才确认接收。相同键且正文相同返回既有状态 / 结果；相同键但正文不同报冲突，不能静默丢弃或再执行。
- 传输重发只是查询 / 恢复原处理，不等于要求模型重新生成；显式重试走 §2.3 的 `retry`。
- 同 thread 按核心接受顺序；多个 thread 指向同一核心会话时由会话层统一串行。不同会话不承诺全局顺序。
- 回滚 / 删除 / 重绑使旧请求失效时保留作废记录，重连重发返回取消，不得把被撤销输入重新灌入新状态。去重控制记录不随世界历史回滚倒退，也不随实例导出。
- 合并回复不合并输入身份：批内每条入站保留自己的 id 与接受状态；重发其中一条仍查该输入所属批次的结果，不重复生成或重复计数。

### 2.3 消息类型（v1 基线）

| 方向 | type | 用途 |
|---|---|---|
| 通道 → 核心 | `hello` | 声明协议版本与能力；身份来自受信连接上下文 |
| 核心 → 通道 | `hello_ack` | 协商版本、能力和限额；认证成功后才允许正常消息 |
| 核心 → 通道 | `binding` | 通知 thread 的不透明绑定令牌更新 / 撤销；不包含世界内部标识 |
| 通道 → 核心 | `user_message` | 用户文本，带发送时取得的绑定令牌 |
| 核心 → 通道 | `accepted` | 关联入站 id，表示已持久接收及当前处理状态，不等于已生成回复 |
| 核心 → 通道 | `reply` | 已固化最终回复；普通回复或主动消息 |
| 核心 → 通道 | `system_notice` | 核心生成的管理 / 归档说明；不是角色发言，不进入角色记忆提取 |
| 通道 → 核心 | `delivery` | 关联出站 id，报告 accepted / failed / unknown；不是用户已读 |
| 通道 → 核心 | `retry` | 引用原输入或出站 id，显式请求重试可重试阶段；自身也幂等 |
| 核心 → 通道 | `status` | 思考中 / 空闲 / 中断等操作状态，只发给支持者 |
| 核心 → 通道 | `error` | 有限、脱敏的错误结果（实现按 `ump.SERVER_TYPES` 收窄为单向：通道侧的问题走 `delivery` 状态回报，不走 `error`） |
| 双向 | `ping` / `pong` | 心跳 |

- `accepted` 的处理状态至少区分排队、处理中、完成、失败、取消；重复输入查询返回相同逻辑轮次的最新状态。接收 / 生成状态与投递状态分开保存；`unknown` 不等于成功，不能被迟到回执倒退覆盖。
- 已完成输入可回送既有 `reply`，沿用出站标识；客户端也须去重，不能显示两份。
- `retry` 若引用生成失败且可重试的输入，恢复同一逻辑轮次的新尝试；若引用投递失败的回复，只重发固化结果。已完成、不可重试或被回滚作废的操作不得再次执行。
- `retry` 必须引用当前认证通道实例、thread、绑定版本和原输入 / 出站标识；同一逻辑轮次最多一个活动生成尝试，不同 retry 请求合并查询该尝试。生成中断、投递失败和投递未知分别返回可重试阶段；unknown 的人工重试须明确可能重复。
- 投递回执按原出站标识和绑定令牌核对，只更新原投递记录；旧回执不能作用于新绑定。未发送的旧回复不因重绑改投新会话。
- 发送结果未知时不宣称成功，也不盲目自动重发。外部平台没有幂等能力时，人工重试提示可能重复；不承诺跨平台 exactly-once。
- **合并回复（多入一回）**：一条 `reply` 可覆盖同一会话的一段连续入站；`reply_to` 关联批内最后一条，并显式携带本批覆盖的输入标识集合（字段名实现级确定）。查询或重试批内任一输入返回同一批状态与同一 `message_id`，不逐条补发。
- **初次联络**：独立开场与主动消息同形（`reply_to = null`），一次投递到触发视图；不伪造入站，也不因此改变长期投递目标。

### 2.4 能力与分段

握手能力示意：

```json
{
  "channel": {"id": "builtin", "name": "内建聊天窗口", "version": "0.1.0"},
  "capabilities": {"segments": true, "status": true, "max_text_len": 4000, "max_parts": 10}
}
```

普通回复 payload 示例：

```json
{
  "message_id": "m-27",
  "reply_to": "e-8f3a1c",
  "batch_index": 0,
  "batch_count": 1,
  "parts": [{"text": "刚结束今天的工作。"}]
}
```

- 主动消息的 `reply_to` 为 `null`；它有自己的 message_id，不伪造入站消息。
- `message_id` 标识同一逻辑文本，多个批次各有独立信封 id；批次数与序号在发送前确定。重试不重排分段或生成新 message_id。
- 每个批次独立记录 accepted / failed / unknown / delivered 结果；整条消息只有所有批次确认成功才为 delivered，部分成功不重发已确认批次，迟到回执不能倒退已确认状态。分段计划不符合新协商能力时只报告投递能力不兼容，保留历史，不能重排、裁剪或重新生成。
- 回复及其回执的 thread 沿用原目标的 `binding_token`；主动消息在固化时捕获目标令牌。客户端不能把旧令牌的回复插入新绑定视图，核心也不能给旧回复换上新令牌后继续发送。
- 核心按协商长度 / 分段数拆分；不支持多段时每批一段，超出一批则发送多个有序批次。**不得以“裁剪”丢弃正文尾部**。
- 协商限额取双方支持范围，须为有效正值；字符计数方式与帧字节上限在实现级字段表统一。
- 分段、回执仅影响投递；历史保存一份规范回复，不因分批被当作多轮记忆或多条主动额度。

### 2.5 承载与认证

| 场景 | 承载与边界 |
|---|---|
| 第三方插件 | 核心创建子进程；stdin/stdout 为 UTF-8 NDJSON，stderr 为受限日志；该进程管道绑定其通道身份 |
| 官方桌面聊天 | 核心监听 `127.0.0.1` 随机端口，本地 WS JSON 帧；端点经受信父子进程启动通路交给壳 |
| 安卓内建 | 保持 UMP 消息语义；可采用进程内传输，实际路线待评估，不强制复制桌面 WS |

- 认证材料由核心签发，经受信启动 / 管理通路交壳，再由壳交指定客户端；不写 URL 查询串、普通日志或插件环境。
- 一次性引导令牌消费后，重连由受信壳重新获取连接凭据；不能反复复用一次性令牌或降级为无认证。
- 回环监听不是授权本身：验证凭据与允许的连接来源，拒绝普通网页及其他未授权客户端。管理操作需独立的壳权限。
- 会话与世界切换由管理面改变 thread 路由；通道只处理相同协议，不感知目标世界。
- 受信管理面负责创建通知和解析通知定位，UMP 不承载实例 / 时间线 / 角色内部标识。通知固定引用固化 message_id 与原会话版本；回滚、删除或目标失效后点击只返回管理错误，不改投、不激活冻结线。

## 三、插件模型

### 3.1 形态与安装

独立进程 + 目录制 manifest，语言不限。manifest 只描述入口参数、标识、版本、协议范围和作者，不是启动脚本。

```json
{
  "id": "my-channel",
  "name": "某通道",
  "version": "0.1.0",
  "ump": "1.x",
  "entry": ["python", "main.py"],
  "description": "通道适配器",
  "author": "作者"
}
```

- 上例仅说明参数数组结构，不保证系统存在相应解释器；启用前检查入口、工作目录与依赖，失败明确提示。
- 扫描 / 登记只读清单、不运行代码；用户明确启用后才启动，不经 shell 拼接执行。

### 3.2 生命周期

| 操作 | 契约 |
|---|---|
| 启用 | 启动 → 有限时间内完成认证握手 → 运行中 |
| 停用 | 停接新消息 → 关闭连接 → 有界等待退出 → 必要时结束所属进程树 |
| 崩溃 / 无响应 | 标记失败、记录脱敏原因并提示；不自动重启风暴 |
| 手工更新 | 先停止旧进程，再校验新清单，重新启用并握手；不删除持久通道身份 |
| 卸载 | 停用并移除插件登记 / 绑定；保留核心会话与角色历史 |
| 核心退出 | 所有插件及所属子进程一并停止，不留后台孤儿 |

握手、心跳和发送等待均有有限超时；帧、队列与日志有容量上限。恶意大帧、持续无效消息或堵塞输出不能耗尽核心；违规仅停止该插件。

### 3.3 隔离与兼容

- 独立进程提供**故障隔离**，不等于权限沙箱。v1 不强制 CPU / 内存配额，不能保证抵御恶意进程耗尽整机资源。
- 协议版本变化时提示用户并尝试**握手协商**；可兼容则运行，不可兼容 / 协商失败则反馈并停止。不能以“试试看”跳过认证或输入校验。
- 协商失败进入持久的 `incompatible` 通道状态：不接受普通消息、不消费重试、不自动降级为未协商能力；用户更新插件 / 核心或明确停用后才清除。已有历史和固化回复保留，待投递结果按原投递失败 / 未知语义处理。
- 第三方交付包含协议字段、生命周期、收发、错误 / 重试、兼容说明与 Python 参考实现；不要求插件以 Python 编写。

### 3.4 安全与信任

- 插件以当前用户权限运行，可能访问操作系统允许的文件与网络；首次启用明确提示只安装信任代码。
- 「不修改核心 / 实例」是插件开发契约，协议不提供写入接口，**不是对恶意代码的 OS 级防护承诺**。
- 默认子进程环境只传必要变量及该插件自身配置，不继承核心 LLM Key、管理令牌或其他插件凭据；这降低误泄漏，不替代沙箱。
- 不自建插件商店、签名服务器、自动更新器或通用权限框架；安全沙箱留待确有需求时另行设计。

## 四、内建聊天窗口

- 内建聊天是随应用发行的官方 UMP 通道客户端；UI 在 Tauri 壳，业务在 Python 核心，不再表述为 UI 与核心“同一个进程”。
- 消息能力与插件同语义；角色选择、世界 / 时间线选择、历史分页、世界时钟由受信管理面提供，不把内部标识塞进 UMP。
- 状态只显示连接 / 生成 / 世界就绪等操作信息，**不显示角色内部状态、活动面板或记忆数值**。
- 桌面端可停用内建聊天但保留管理面；未来拆为插件后桌面只保留该插件形态。安卓始终内建且独立维护，不开放插件。
- 停用、断线与重新启用均不重置世界、角色或历史。

## 五、壳与核心接线

- 壳负责拉起 / 监督核心、接收就绪信息、管理连接凭据；核心签发端点与认证上下文。
- 就绪不是只有端口已开，还须认证握手完成及目标会话可用；世界追赶中另报状态。
- 本地管理接口受壳权限保护，仅返回必要元数据和对话原文；第三方通道不能靠自报名称取得管理面。
- 历史补读走会话管理接口，不通过自由查询世界数据实现。v1 不开放第三方任意历史查询。

## 六、错误与可观测性

所有错误携带 `code`、脱敏 `message`、`retryable`、相关信封 `ref`；明确属于接收、生成或投递阶段。

- 协议 / 认证错误：拒绝或断连并提示，永久错误不无限重连。
- 核心暂时不可用 / 网络断线：客户端有界退避重连，保留原请求 id；不清空历史。
- 生成失败：保留输入与失败状态，显式重试恢复该轮。
- 投递失败 / 未知：保留固化回复及回执，不重新跑模型；无回执不能假称用户已读。
- 日志记录错误码、阶段、关联标识、耗时与进程状态；默认不记录消息正文、实情、prompt、记忆简报、完整服务响应或凭据。插件 stderr 有容量限制与脱敏要求，不能保证净化恶意插件自行写出的全部内容。

- **更后置**：附件、富媒体、流式表达、资源配额及分发渠道。
  - **附件 / 富媒体已落地（2026-09-22）**：能力位 `attachments`（握手取交集）+ 配额 `max_attachments` / `max_attachment_bytes`；
    帧格式见 `CHANNEL_PROTOCOL_APPENDIX.md` ② `user_message` 行；未声明的通道给附件仍是**显式拒绝**（`unsupported_capability`）。
    行为验收 `tests/test_attachments.py`（真 WS + 真 SQLite）；客户端侧（壳的选文件与渲染）随桌面壳排期。
  - **资源配额已落地**：通道侧容量闸（连接数 / 入站队列 / 限速 / 附件字节）见 §九；插件级 CPU / 内存配额按 §3.3 明确不做。
  - **流式表达已落地（2026-09-22）**：能力位 `streaming`；增量帧 `reply_delta`（与最终 `reply` 同 `message_id`、按 `index` 有序）

    行为验收 `tests/test_streaming.py`（真 WS + 真 SQLite），真机链路 `cli --say`（真实模型下增量边收边打）。
  - **分发渠道仍后置**（插件目录制 manifest 已定；压缩包分发 / 安装入口未做）。

## 八、与其它模块的接口

| 对方 | 契约 |
|---|---|
| 会话核心 | thread 路由、接受顺序、生成 / 投递分离、主动唯一目标 |

## 十、行为验收

1. 两插件使用相同 thread/id 不串线；重连身份稳定；冒充 builtin 不能取得管理权限。断线期间排队的旧消息在重绑后被令牌校验拒绝，不能泄露给新角色。
2. 相同输入重发只返回既有状态 / 结果，不同正文复用 id 报冲突；回滚作废的输入不能重放复活。
3. 生成完成后连接中断，重连能恢复同一回复；投递重试不再调用模型、不重复记忆。
4. 超长回复被完整、有序分批，不丢尾部；主动消息无伪造 reply_to，分批不重复计数。
5. 插件握手超时、坏帧、阻塞或崩溃不拖死核心；停止 / 更新 / 退出不留所属孤儿进程。
6. 普通网页、错误凭据、自报通道身份均不能调用管理面；凭据不进入日志、插件环境或导出包。
7. 外部发送结果未知时不误报成功，永久协议错误不重连风暴；内建聊天停用后管理面仍可用。
8. 合并回复：一条回复覆盖的每条输入都能查到同批结果；跨 thread 不合并；重发批内任一条不重复生成或重复计数；独立开场不伪造入站。
9. 握手成功后重连复用持久协商结果；协议 / 能力变化重新协商。协商失败后普通消息被拒且不循环重连、不绕过能力检查，恢复兼容后可显式重新启用。
10. `system_notice` 在内建客户端与插件中保持非角色作者分类；归档说明不进入角色记忆提取，导出 / 导入和回滚保持其分类与生命周期。
